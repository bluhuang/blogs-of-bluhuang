什么是 Agent？

📌 本章重点总结（Agent 基础） Agent 定义：以大模型为“大脑”，能自主感知、决策、调用工具、完成多步骤任务的程序。核心公式：Agent = 大模型 + 工具 + 记忆 + 执行循环。 为什么需要 Agent：弥补大模型的三大短板（无执行能力、知识过期、无持久记忆），让大模型从“只能说”变成“能干”。 核心四组件： 大模型（大脑）：理解任务、推理决策。 工具（双手）：调用真实函数（查库、搜网页、发通知等）。 记忆（记事本）：短期（上下文窗口）+ 长期（外部存储）。 执行循环（节拍器）：不断重复“思考-行动-观察”。 主流工作模式： ReAct：边想边做，每一步实时决策，适合短任务（≤3步）。 Plan and Execute：先一次性规划完整步骤清单，再逐步执行，适合长任务（≥5步）。支持 Re‑planning 动态调整。 ReAct vs Plan & Execute： ReAct：灵活、适合步骤少、目标模糊；token 消耗随步数增长。 Plan & Execute：全局视野、适合步骤多、目标明确；规划阶段集中消耗 token。 实际生产常混合使用：外层 Plan & Execute，内层子任务用 ReAct。 Agent vs Workflow： Workflow：决策者是你（硬编码），执行路径固定，适合重复性高、步骤明确的场景。 Agent：决策者是大模型（实时推理），执行路径动态，适合开放式、需动态决策的任务。 常见架构：Workflow 做骨架，Agent 负责需要判断的环节。 真实挑战与应对： 幻觉传导 → 工具结果可验证，高风险操作加人工确认。 工具调用失败 → 定义错误返回格式，在 System Prompt 中说明处理方式。 成本和速度 → 设置最大轮数，能用 Workflow 不用 Agent。 循环风险 → 设置最大迭代次数，强制模型判断“是否已足够”。 极简 Agent 骨架：while 循环 → 调用 LLM 决策 → 若完成则退出 → 否则执行工具 → 结果追加到消息列表 → 继续循环。 正文：

什么是 Function Call？（协议）

📌 本章重点总结（Function Calling） Function Calling 是什么：大模型与 Agent 之间的标准化工具调用协议，解决“大模型做出决策后如何精准传递指令给 Agent”的问题。 为什么需要 Function Calling：传统方式用自然语言在 System Prompt 里描述工具，导致大模型回复格式不可控（参数错乱、编造答案、不调用工具等），开发者需大量解析和纠错代码。Function Calling 用固定 JSON 格式彻底告别“猜谜”。 Function Calling 的三部分结构： 工具定义（Tool Definition）：开发者提供标准 JSON，包含 name、description、parameters（含类型、格式、必填项）。大模型据此判断是否调用及如何调用。 AI 调用格式（Function Call）：大模型返回固定 JSON（如 {"function_call": {"name": "...", "parameters": {...}}}），Agent 直接解析，无需猜测。 工具返回结果（Tool Response）：Agent 执行工具后，将结果按规范格式回传大模型，用于下一步决策。 对应 Agent 执行循环中的三步： 第1步 → 工具定义（Agent 传工具清单给大模型） 第2步 → AI 调用格式（大模型返回调用指令） 第4步 → 工具返回结果（Agent 回传执行结果） （第3步“执行工具”不属于 Function Calling 范围） 核心优势对比：工具描述规范、调用格式固定、参数错误率极低、开发成本低、模型兼容性好（主流大模型通用）。 与 Tool 的关系： Tool 是“能力层”（定义有什么工具、能做什么）。 Function Calling 是“协议层”（规定大模型和 Agent 之间怎么传递调用指令）。 上一章你已经知道了，一个工具 = 函数本体 + 名称 + 描述 + 参数定义，大模型靠工具描述来判断要不要调这个工具。

什么是 RAG？

📌 本章重点总结（RAG） RAG 是什么：Retrieval-Augmented Generation（检索增强生成）。先检索私有知识库中最相关的内容，再将其注入 Prompt，让大模型基于有据可查的资料生成回答。 为什么需要 RAG：大模型知识静态、封闭（截止日期、无私有数据、无实时数据），全量塞入 Prompt 受限于上下文窗口、成本高、注意力稀释。RAG 实现“按需检索 + 动态注入”。 核心思路：不把所有数据都塞进 Prompt，而是每次回答前，先从知识库中检索最相关的几段内容，再将这几段注入 Prompt。 两大阶段： 离线建库：加载文档 → 文本切块（Chunking）→ 向量化（Embedding）→ 存入向量数据库。 在线检索生成：问题向量化 → 语义搜索（取最相似 chunk）→ 构造增强 Prompt → 大模型生成回答。 关键概念： 向量（Vector）：文字的“语义坐标”，语义相近的内容向量距离近。 语义搜索：不依赖关键词匹配，而是通过向量相似度找到意思相关的内容，即使词语不同也能召回。 RAG 在 Agent 中的位置：RAG 本质上是一个特殊的“知识库检索工具”，通过 Function Calling 被 Agent 调用，成为 Agent 能力体系的一部分。 对比优势：可访问私有数据、知识更新快（更新文档即生效）、Token 消耗低、回答有据可查、扩展性好。 前几章我们把 Agent 的工具体系搭清楚了：Function Calling 让大模型能开口下指令，MCP 让工具标准化接入，Skills 让专业知识按需加载。到这里，Agent 能干活了，工具也能跑起来了。

什么是 Skills？

📌 本章重点总结（Skills） Skills 出现的背景：有了 Function Calling（底层机制）和 MCP（标准化接口）后，AI 能调用工具了，但每次执行复杂任务（如生成日报）仍需用户反复用自然语言指导执行步骤，沟通成本高、流程无法沉淀复用。 Skill 的定义：一份“标准作业程序（SOP）”，将解决特定任务所需的 背景设定（Prompt）、执行步骤 和 所需工具（MCP） 打包成一个可复用的代码文件（通常为 Markdown + YAML）。 Skill 的内部结构： 头部配置（Frontmatter）：YAML 格式，定义技能名称、描述，声明需要挂载的 MCP 工具。 技能主体（Body）：具体的指令、工作流、规则限制和模板，用自然语言指导 AI 如何按步骤使用工具完成任务。 Skill vs Prompt： Prompt 只控制“嘴”（输出文本），无法真正执行操作；Skill 通过绑定工具让 AI 能“动手”。 Prompt 是临时的一次性指令；Skill 是项目目录中的可提交、可复用的代码资产，可团队共享。 Skill vs MCP vs Function Calling 的三角关系： Function Calling：底层技术，让大模型拥有调用外部工具的能力。 MCP：接口标准，统一工具的接入规格，相当于 AI 的“Type‑C 通用插口”。 Skills：上层业务封装，将 Prompt 和 MCP 工具组合成标准工作流，实现工程化沉淀与复用。 实战示例（Claude Code）：在项目 .claude/skills/ 目录下按结构放置 SKILL.md 和辅助脚本，AI 可通过触发技能自动执行多步骤任务（如图片压缩、转换格式、移动文件）。 核心价值：Skills 让 AI 从“临时问一句”升级为“按标准化流程自动执行”，降低重复沟通成本，实现经验沉淀和团队协作。 第一阶段：AI 的“破壁人” ， Function Calling（函数调用） 我们先回想一下早期的 ChatGPT。那时的它就像是一个 被关在小黑屋里的超级学霸：虽然上知天文下知地理，但它没网（没法查实时数据），也没手（没法帮你真正去执行操作，比如发邮件、查数据库）。

什么是 Tool？

📌 本章重点总结（Tool 基础） 问题背景：大模型被“关在盒子里”，只能输入输出文字，无法与外部世界交互。Tool 给大模型“装上手”，让它能执行真实操作。 Agent、大模型、Tool 的关系： 大模型：决策者（动脑），决定下一步做什么、调用哪个工具。 Tool：执行者（动手），真正去查数据库、发通知、读写文件等。 Agent：调度员，协调用户、大模型、工具之间的任务传递和流程推进。 Tool 的完整组成（四要素）： 函数本体：具体实现功能的代码（大模型看不到，Agent 执行）。 name（名称）：大模型识别工具的标签，需望名知意。 description（描述）：最重要的字段，写清楚工具能做什么、什么场景用、返回什么信息。 parameters（参数定义）：用 JSON Schema 定义参数名、类型、必填项、示例，类似“填写表单”。 大模型如何“认识”工具：Agent 在每次对话开始时，将所有可用工具的 name + description + parameters 打包成工具清单，通过 API 的 tools 参数传给大模型。大模型根据清单判断调用哪个工具。 工具分类（按风险从低到高）： 查询类（只读）：查天气、读文件、搜索网页 → 风险低，可自主调用。 写入类（有副作用）：发通知、写数据库、改配置 → 风险中，高风险操作需人工确认。 执行类（高风险）：执行 shell 命令、重启服务、部署代码 → 风险高，必须人工审批。 AI 辅助类：RAG 检索、调用子模型 → 风险低～中，通常可自主，需关注结果质量。 核心原则：工具描述的清晰度决定了 Agent 选工具的准确率，而不是模型本身的聪明程度。description 必须写清楚使用场景，否则模型可能误选或漏选。 你有没有遇到过这种情况。

什么是Harness工程？

📌 本章重点总结（Harness Engineering） 概念来源：由一位工程师在 2026 年 2 月提出，随后某知名机构官方博客推广。核心思想是“设计一套包裹模型的外部环境，让 Agent 稳定交付”。 AI 工程重心的三次演进： Prompt Engineering：让模型“听懂”任务（表达）。 Context Engineering：让模型“知道”该用什么信息（供给）。 Harness Engineering：让模型在真实执行中“持续做对”（驾驭）。 三者是包含关系：Prompt ⊂ Context ⊂ Harness。 Harness 的简洁定义：Agent 系统里除了模型本身之外，所有决定稳定性的东西。 Harness 六层核心组件（六问对应）： ① 上下文精细化：模型这一轮该看到什么？ ② 工具系统：模型用什么动手？ ③ 任务执行编排：模型下一步该干啥？ ④ 记忆与状态：模型跨轮该记住什么？ ⑤ 评估与观测：模型做得好不好有没有尺子？ ⑥ 约束与恢复：模型出错了能不能爬起来？ 五大难题与典型解法（对应五条原则）： 难题1：Agent 跑久了越走越偏 → 解决方案：Context Reset，状态外化到文件系统，每轮用干净上下文接手。原则：重启胜过修补，状态沉到文件里。 难题2：Agent 自评总是偏乐观 → 解决方案：Planner + Generator + Evaluator 三角分工，验收与生产分离。原则：生产和验收必须分家，验收方要能摸到真实世界。 难题3：Agent 反复失败，工程师该干啥 → 解决方案：不调提示词，而是补环境能力（如接 lint、单测、运行环境）。原则：别问模型能不能更努力，要问环境还缺什么。 难题4：规范文件越写越长，Agent 反而更糊涂 → 解决方案：渐进式披露，主文件只保留索引（约100行），详细内容按需加载。原则：规则宁缺毋滥，少即是多。 难题5：Agent 写的代码越堆越烂（AI slop），技术债怎么还 → 解决方案：将人类经验写成“Golden Principles”，用后台 Agent 定期自动扫描修复。原则：技术债不是攒一堆集中还，而是每天让 Agent 自动偿还一点。 反直觉发现：Agent 对“老技术”（稳定、文档齐全、训练数据多）掌握更好，选技术栈不必追新。 工程师角色转变：从“写代码”转向“设计 Agent 的运行环境（写规则、流程、校验、评估）”。未来主战场是 Harness 工程。 核心公式：Agent Quality ≈ Model Capability + Harness Design。模型决定天花板，Harness 决定落地稳定性。 这个新词到底从哪儿冒出来的？ 在开讲之前，先带你「追个源」。

什么是MCP？

📌 本章重点总结（MCP） MCP 是什么：推出的开放标准协议（Model Context Protocol），定义了 AI 应用与工具服务之间的标准化通信方式，被誉为“AI 工具世界的 USB‑C”。 为什么需要 MCP：解决没有统一标准时，每个工具需单独集成、多模型场景下 N×M 套重复代码的问题。MCP 使工具写一次、全平台可用，将工作量降为 N+M。 三大核心角色： Host：用户使用的 AI 应用（如 Claude Desktop、VS Code），负责发起任务。 Client：Host 内置的连接器，负责管理 MCP Server 的连接与请求路由。 Server：暴露工具能力的轻量服务程序，负责实际执行工具。 MCP Server 的三种能力： Tools（工具）：可主动调用的函数（发邮件、查数据库等），有副作用。 Resources（资源）：只读的数据访问（文件、数据库记录等），无副作用。 Prompts（提示模板）：预定义的可复用提示词模板。 MCP 与 Function Calling 的关系： 配合关系，非替代。Function Calling 负责“大模型→Agent”的调用指令标准化；MCP 负责“Agent→工具服务”的连接与执行标准化。 两者在调用链中分工明确：Function Calling 说“调什么”，MCP 做“怎么找到并执行”。 核心价值：彻底解耦工具实现与 AI 调用决策，降低开发成本，促进生态共享。工具 API 升级只需更新对应 Server，所有 Host 自动受益。 为什么需要两者配合，缺一不可？ 只有 Function Calling，没有 MCP： 大模型能说出“调用天气工具”，但 Host 还是要自己写代码去连接天气 API、处理各种工具的特殊协议。换一个工具又得重写，无法复用。

什么是Prompt？

📌 本章重点总结（Prompt基础） Prompt定义：你发给大模型的所有输入内容，包括指令、背景、示例、格式要求等（不只是一句问题）。 Prompt的重要性：大模型是 next-token 预测机器，输入越精准，输出越稳定。在 Agent 开发中，输出稳定性直接决定流水线可靠性。 User Prompt三要素：目标明确、背景充足、输出要求。缺一不可。 System Prompt三大用途：身份设定、行为规则、输出格式约束。它比 User Prompt 更“稳”，是 Agent 行为可预测的核心保障。 ==写好Prompt的6个核心原则：== ==给模型角色 → 缩小搜索空间，输出更专业== ==正向约束优于负向禁止 → 明确“要做什么”== ==喂足背景信息 → 减少幻觉== ==指定输出格式（最好给JSON示例）→ Agent 解析的关键== ==使用 Few-shot（给例子）→ 胜过写规则== ==要求“先思考再回答”（思维链）→ 提升复杂问题准确率== Prompt迭代调试：多准备典型输入，每次只改一个变量，观察输出变化。常见问题有对应排查方法。 总结：Prompt 是 Agent 的控制面板。System Prompt 定义身份边界，User Prompt 提供具体任务。后续的 Function Calling、RAG、Agent 都依赖于 Prompt 的设计质量。 正文： 上一章你已经搞清楚了大模型的底层逻辑：它是一个超级助理，你通过 messages 列表把内容传给它，它根据你给的上下文预测并生成回答。

Application-Defined SQL Functions

[[programming interfaces]] source: https://sqlite.org/appfunc.html 1 简介 SQLite 支持用户实现自定义回调方法，以扩展特殊功能，类似于用户自定义函数（UDF）。 自定义的 SQLite UDF 可以是标量函数、聚合函数，也可以是窗口函数。 这些函数可在 SQL 查询中直接使用，支持用 C 语言编写，也可通过绑定在其他语言（如 Python、Java 等）中实现。 2 相关接口 sqlite3_create_function 家族 1 sqlite3_create_function() 基本信息 int sqlite3_create_function( sqlite3 *db, /* 数据库连接 */ const char *zFuncName, /* 函数名 (UTF-8) */ int nArg, /* 参数个数 (-1 = 可变) */ int eTextRep, /* 首选文本编码 */ void *pApp, /* 应用数据指针 */ void (*xFunc)(sqlite3_context*,int,sqlite3_value**), /* 标量函数 */ void (*xStep)(sqlite3_context*,int,sqlite3_value**), /* 聚合 step 函数 */ void (*xFinal)(sqlite3_context*) /* 聚合 finalize 函数 */ ); 特点 最基础版本：最早引入的函数注册接口。 编码指定：通过 eTextRep 参数指定文本编码偏好。 函数类型： 若 xFunc 非 NULL，则注册标量函数。 若 xStep 和 xFinal 非 NULL，则注册聚合函数。 应用数据：通过 pApp 传递用户数据。 内存管理：无自动清理机制，需要手动管理内存。 2 sqlite3_create_function16() 基本信息 int sqlite3_create_function16( sqlite3 *db, /* 数据库连接 */ const void *zFuncName, /* 函数名 (UTF-16) */ int nArg, /* 参数个数 */ int eTextRep, /* 首选文本编码 */ void *pApp, /* 应用数据指针 */ void (*xFunc)(sqlite3_context*,int,sqlite3_value**), void (*xStep)(sqlite3_context*,int,sqlite3_value**), void (*xFinal)(sqlite3_context*) ); 特点 UTF-16 支持：函数名使用 UTF-16 编码。 向后兼容：为需要 UTF-16 函数名的应用提供支持。 功能相同：与 sqlite3_create_function() 功能相同，仅函数名编码不同。 使用场景： Windows API 集成（Windows 原生使用 UTF-16）。 需要处理宽字符的遗留系统。 3 sqlite3_create_function_v2() 基本信息 int sqlite3_create_function_v2( sqlite3 *db, /* 数据库连接 */ const char *zFuncName, /* 函数名 (UTF-8) */ int nArg, /* 参数个数 */ int eTextRep, /* 首选文本编码 */ void *pApp, /* 应用数据指针 */ void (*xFunc)(sqlite3_context*,int,sqlite3_value**), void (*xStep)(sqlite3_context*,int,sqlite3_value**), void (*xFinal)(sqlite3_context*), void (*xDestroy)(void*) /* 析构函数 */ ); 特点 增强版本：在基础版本上增加了析构函数。 自动清理：通过 xDestroy 回调自动清理 pApp 数据。 内存安全：避免内存泄漏，更加安全。 推荐使用：SQLite 官方推荐使用此版本。 4 sqlite3_create_window_function 基本信息 int sqlite3_create_window_function( sqlite3 *db, /* 数据库连接 */ const char *zFuncName, /* 函数名 */ int nArg, /* 参数个数 */ int eTextRep, /* 首选文本编码 */ void *pApp, /* 应用数据指针 */ void (*xStep)(sqlite3_context*,int,sqlite3_value**), /* step 函数 */ void (*xFinal)(sqlite3_context*), /* finalize 函数 */ void (*xValue)(sqlite3_context*), /* value 函数 */ void (*xInverse)(sqlite3_context*,int,sqlite3_value**), /* inverse 函数 */ void (*xDestroy)(void*) /* 析构函数 */ ); 特点 窗口函数专用：专门用于注册窗口函数（SQLite 3.25.0+）。 额外回调：需要实现更多回调函数。 反向处理：支持 xInverse，用于优化窗口函数性能。 复杂功能：支持滑动窗口、排序、分组等高级功能。 3 UDF 类型 3.1 标量函数 (Scalar Functions) 接受参数，返回单个值。 对每一行数据独立计算。 示例：UPPER(), ABS(), DATE()。 3.2 聚合函数 (Aggregate Functions) 跨多行数据操作，返回聚合结果。 需要维护状态信息。 示例：SUM(), AVG(), COUNT()。 3.3 窗口函数 (Window Functions) SQLite 3.25.0+ 支持。 在窗口帧上执行计算。 示例：ROW_NUMBER(), RANK()。 4 参数含义 int sqlite3_create_function_v2( sqlite3 *db, /* 数据库连接 */ const char *zFuncName, /* 函数名 (UTF-8) */ int nArg, /* 参数个数 */ int eTextRep, /* 首选文本编码 */ void *pApp, /* 应用数据指针 */ void (*xFunc)(sqlite3_context*,int,sqlite3_value**), void (*xStep)(sqlite3_context*,int,sqlite3_value**), void (*xFinal)(sqlite3_context*), void (*xDestroy)(void*) /* 析构函数 */ ); 4.1 zFunctionName 该参数传入函数名：第二个参数是要创建的 SQL 函数的名称。通常使用 UTF-8 编码，但对于 sqlite3_create_function16()，名称应以本机字节序的 UTF-16 编码。 函数名长度限制为 255 字节：SQL 函数名的最大长度为 255 字节的 UTF-8。任何尝试创建超过此长度的函数都会导致 SQLITE_MISUSE 错误。 UDF 注册支持重载：同一函数名可以多次调用 SQL 函数创建接口。例如，若两次调用参数数量不同，则注册该 SQL 函数的两种变体，分别接受不同数量的参数。 4.2 nArg 表示参数数量，类型为 int。 参数范围：最小值 -1（表示可变参数），最大值默认为 127，实际最大为 SQLITE_MAX_FUNCTION_ARG (32767)。 4.3 eTextRep 文本编码 类型：int — 位掩码。 作用：指定函数的文本编码偏好。 取值： SQLITE_UTF8 (0x01)：UTF-8 编码。 SQLITE_UTF16LE (0x02)：UTF-16 小端序。 SQLITE_UTF16BE (0x03)：UTF-16 大端序。 SQLITE_UTF16 (0x04)：使用本地字节序的 UTF-16。 SQLITE_ANY：接受任何编码（已废弃）。 组合标志：可与确定性标志组合使用。 4.4 pApp 详细说明 类型：void* — 任意类型指针。 作用：传递用户自定义数据到函数。 生命周期：由 xDestroy 回调管理。 使用场景： 传递配置参数。 传递共享资源（如缓存、文件句柄）。 传递状态信息。 4.5 xFunc 标量函数指针 详细说明 类型：函数指针 void (*)(sqlite3_context*, int, sqlite3_value**)。 作用：标量函数的实现。 调用时机：每次 SQL 查询需要函数值时调用。 参数： sqlite3_context*：函数上下文，用于设置结果和错误。 int：实际参数个数。 sqlite3_value**：参数值数组。
