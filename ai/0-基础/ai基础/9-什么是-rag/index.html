什么是 RAG？

  • Home /
  • AIs /
  • 什么是 RAG？

📌 本章重点总结（RAG）

  1. RAG 是什么：Retrieval-Augmented Generation（检索增强生成）。先检索私有知识库中最相关的内容，再将其注入 Prompt，让大模型基于有据可查的资料生成回答。
  2. 为什么需要 RAG：大模型知识静态、封闭（截止日期、无私有数据、无实时数据），全量塞入 Prompt 受限于上下文窗口、成本高、注意力稀释。RAG 实现“按需检索 + 动态注入”。
  3. 核心思路：不把所有数据都塞进 Prompt，而是每次回答前，先从知识库中检索最相关的几段内容，再将这几段注入 Prompt。
  4. 两大阶段：
    • 离线建库：加载文档 → 文本切块（Chunking）→ 向量化（Embedding）→ 存入向量数据库。
    • 在线检索生成：问题向量化 → 语义搜索（取最相似 chunk）→ 构造增强 Prompt → 大模型生成回答。
  5. 关键概念：
    • 向量（Vector）：文字的“语义坐标”，语义相近的内容向量距离近。
    • 语义搜索：不依赖关键词匹配，而是通过向量相似度找到意思相关的内容，即使词语不同也能召回。
  6. RAG 在 Agent 中的位置：RAG 本质上是一个特殊的“知识库检索工具”，通过 Function Calling 被 Agent 调用，成为 Agent 能力体系的一部分。
  7. 对比优势：可访问私有数据、知识更新快（更新文档即生效）、Token 消耗低、回答有据可查、扩展性好。

前几章我们把 Agent 的工具体系搭建清楚了：Function Calling 让大模型能开口下指令，MCP 让工具标准化接入，Skills 让专业知识按需加载。到这里，Agent 能执行任务，工具也能顺畅运行。

但有一个根本问题，前面几章都没有正面回答： 大模型无法访问私有数据，怎么办？

一个组织内部有数千页运维手册、几百个历史故障报告、一套仅内部知晓的排查 SOP，这些数据大模型从未接触过。让它协助进行 OnCall 排查，它能给出通用思路，但无法针对特定系统给出精准答案。

这就是 RAG 要解决的核心问题。

一、大模型为什么无法访问私有数据？

我们先梳理问题所在，有三类“无法访问”的情况，每类原因各不相同。

第一类：知识截止日期

大模型使用历史数据训练，训练完成后其知识便冻结了。例如某个大模型训练数据截止到 2025 年某个时间点，之后的事件它无法知晓。向它询问“系统今天凌晨发生了什么故障”，它缺乏相关信息，只能推测。

第二类：私有数据

组织内部的文档、产品设计方案、运维手册、客服问答库等均为保密内容，不会出现在大模型的训练数据中。模型从未见过这些内容，自然无法基于它们回答问题。

第三类：实时数据

刚刚完成的技术方案、新产生的 bug 日志、刚更新的配置文件等动态变化的信息，即使大模型更新训练数据也难以追上。Agent 需要访问的常常正是这类“最新鲜”的数据。

三类问题的共同点： 大模型的知识是静态的、封闭的，而业务数据是动态的、私有的。

二、暴力解法为什么行不通？

遇到这个问题，很多开发者的第一反应是： 直接将数据塞进 Prompt 不就行了？

听起来直接，但这个方案有三个致命问题。

问题一：上下文窗口有上限

大模型一次能处理的文本量有限，这个限制称为上下文窗口。即使目前最大的模型，一次也只能处理数十万 token，换算成中文约几十万字。

组织内部的文档可能有几百个文件，仅运维手册就几十万字，根本无法全部塞入。更不用说那些有数千个历史工单的故障数据库了。

问题二：费钱又慢

Token 是需要付费的。若塞入 10 万 token 的背景资料，每次提问都要支付那 10 万 token 的费用。每天询问数百次，成本急剧上升。此外，token 越多，模型推理越慢，用户等待时间越长。

问题三：注意力稀释

这是最容易被忽视的问题。当大模型处理很长的上下文时，注意力会被稀释，相关内容掩埋在数万字的堆料中，模型可能无法聚焦重点，导致表现下降。塞入越多，有时回答质量反而越低。

三、RAG 的核心思路：先检索，再回答

直接塞数据行不通，那么 RAG 如何解决这个问题？

核心思路非常简洁，一句话即可概括：

不把所有数据都塞进 Prompt，而是在每次回答之前，先去找到最相关的那几段，再将这几段塞进 Prompt。

这就是 RAG 名称的含义：

  • Retrieval（检索）：从知识库中找出与当前问题最相关的内容
  • Augmented（增强）：将检索到的内容加入 Prompt，增强大模型的上下文
  • Generation（生成）：大模型基于增强后的上下文生成回答

类比考试时查字典：考试时不需要背下整本字典，只需知道去字典中查哪个词，找到那一页，看完再写答案。

RAG 正是这一思路，大模型不需要“记住”所有知识，只需在需要时从知识库中检索相关内容，然后基于这些内容回答。

四、RAG 的两大阶段

RAG 的整个工作流程分为两个阶段： 离线建库 与 在线检索生成。

离线建库是一次性的准备工作（数据更新时重新执行），在线检索是每次用户提问时触发的实时流程。

离线阶段

该阶段的目标是将私有数据处理为大模型能快速检索的格式，存入向量数据库。共四步：

Step 1：加载文档

将数据源统一接入，包括 PDF 文档、Word 文件、Markdown 笔记、网页内容、数据库记录、代码文件等，统一解析为纯文本。

Step 2：文本切块（Chunking）

获取文本后，不能直接整篇存储，需先切成小块。原因有二：一是单篇文档可能涉及多个主题，检索时可能仅需其中某个主题的内容，无需召回整篇；二是每个 chunk 将被转化为向量存储，若 chunk 过长，向量难以准确代表该段文字的核心含义，检索准确性会下降。

切块类似于图书馆整理书籍：不是将整本书放在一个标签下，而是按章节、按小节分别标注，方便读者直接找到相关页面，而不必翻阅整本书。

Step 3：向量化（Embedding）

这是 RAG 中最关键的一步，需要重点说明。

每个切好的 chunk 通过一个 Embedding 模型转换为一串数字，这串数字称为 向量（Vector）。

这串数字的作用是什么？它编码了这段文字的 语义含义。意思相近的文字，转化出的向量在数学空间中的距离也相近。

可用城市坐标类比：每个城市都有经纬度，北京约北纬 40°、东经 116°；天津约北纬 39°、东经 117°，两组坐标很接近，在地图上两座城市相邻。广州北纬 23°、东经 113°，坐标差异大，与北京相距较远。

向量就是文字的“语义坐标”。“数据库响应慢”与“查询性能问题”虽词语不同，但意思相近，转化出的向量在空间中也相邻；而“数据库响应慢”与“今天天气不错”意思毫不相关，向量距离则很远。

Step 4：存入向量数据库

转化好的向量，连同对应的原文，一起存入向量数据库（如 Milvus、Pinecone、Weaviate 等）。向量数据库专门优化了“在海量向量中找最近邻”的操作，能在几毫秒内从百万级向量中找出最相似的几条。

在线阶段

每次用户提问，实时触发以下四步：

Step 1：问题向量化

使用同一个 Embedding 模型，将用户的问题也转化为向量。

Step 2：语义搜索

拿着问题向量，去向量数据库中寻找“最相似的几个 chunk 的向量”，这就是语义搜索。找到后，将对应的原文 chunk 取出，通常取 3-5 个最相关的片段。

注意，这里查找的不是“包含相同关键词”的内容，而是“语义最相近”的内容。这是语义搜索与传统关键词搜索的本质区别。

Step 3：构造增强 Prompt

将检索回的几段原文，加上用户的原始问题，拼成一个增强后的 Prompt：

以下是相关背景资料：

[检索到的 chunk 1]

[检索到的 chunk 2]

[检索到的 chunk 3]

根据以上资料，请回答：[用户的原始问题]

Step 4：大模型生成回答

将此 Prompt 发送给大模型，大模型基于提供的背景资料生成有据可查的精准回答。

五、关键概念再讲透：语义搜索与关键词搜索的差别

这里展开说明语义搜索，因为这是 RAG 能工作的核心，也是最容易混淆的地方。

传统关键词搜索（如 SQL 的 LIKE 查询）：逐字匹配。搜索“数据库慢”，便查找包含“数据库慢”这几个字的文档，找不到则返回空。若文档写的是“query performance degradation”或“查询响应时间过长”，关键词搜索便找不到，即使说的是同一件事。

语义搜索：查找意思相近的内容，不要求字面相同。搜索“数据库慢”，语义搜索能找到“查询性能问题”、“SQL 响应延迟”、“慢查询优化”等片段，因为它们的向量距离近，语义上相关。

再举一个对比例子：

用户的问题文档里的原文关键词搜索能找到？语义搜索能找到？
数据库连接失败connection pool exhausted✗（没有相同关键词）✓（语义相关）
如何重启服务service restart procedure✗✓
昨晚报警原因2024-01-15 23:00 alert: high latency✗✓（若时间对应）

语义搜索使 RAG 能够真正“理解”问题，而不只是机械地匹配字符串。这也是为什么 RAG 系统的检索准确率通常远高于普通关键词搜索。

七、RAG 在 Agent 中处于什么位置？

学完 RAG 原理后，你可能会问：它与之前学习的 Agent、MCP、Function Calling 是什么关系？

答案很简单： RAG 本质上就是一个特殊的工具。

回顾 Agent 章节：Agent = 大模型（大脑）+ 工具（双手）+ 执行循环。“查询知识库”这个动作被封装为 Agent 中的一个 Tool。

当 Agent 接到一个需要私有知识的任务时，大模型通过 Function Calling 下达“调用知识库检索工具，查询：XXX”的指令，Agent 执行此工具调用，触发 RAG 的在线流程，检索结果回传至大模型，大模型基于检索结果继续推理。

这就是 MCP 和 Agent 中预告 RAG 时所说的： “将知识库检索封装成工具”。

八、一张表看懂：没有 RAG vs 有 RAG

对比维度没有 RAG有 RAG
私有数据访问无法访问，模型只有通用知识可以访问，基于私有知识库生成回答
知识更新需要重新训练模型，慢且贵更新文档重新建库即可，快速生效
Token 消耗要么全量塞入（超限），要么放弃只召回相关的几段，token 消耗极低
回答准确性依赖训练数据，私有领域容易生成错误信息基于检索到的真实文档，有据可查
可追溯性无法知道回答依据是什么每个回答都可以附上来源文档
扩展性知识库扩大 = 重新训练直接往向量数据库里加数据即可

总结

整理一下本章的核心认知：

  • RAG 是什么：Retrieval-Augmented Generation，检索增强生成。先从知识库中找到相关内容，再将内容加入 Prompt，使大模型基于私有数据生成有据可查的回答。

  • 为什么需要它：大模型的知识是静态的、封闭的，而业务数据是动态的、私有的。将数据全量塞进 Prompt 行不通，受 token 限制、成本高、注意力稀释。RAG 通过“按需检索 + 动态注入”绕开了这一困境。

  • 两大阶段：离线阶段建知识库（加载→切块→向量化→存库），在线阶段查询生成（问题向量化→语义搜索→构造增强 Prompt→大模型生成回答）。

  • 向量化与语义搜索：文字转化为代表语义的数字坐标（向量），语义相近的内容向量距离近。语义搜索不靠关键词匹配，靠语义相似度，能发现“意思相关但词语不同”的内容。

  • 在 Agent 中的位置：RAG 就是一个特殊的工具，“检索知识库”被封装为一次 Function Call，是 Agent 能力体系的重要组成部分。
