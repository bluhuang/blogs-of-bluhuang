什么是大模型？

  • Home /
  • AIs /
  • 什么是大模型？

📌 本章重点总结（大模型基础）

  1. 大模型本质：一个基于海量数据训练、通过预测下一个词来生成文本的“超级助理”。
  2. Token：大模型处理文本的最小单位（非字非词），决定模型输入上限和API费用。
  3. ==上下文窗口：模型单次能“看到”的Token总量（如128K），相当于一块固定大小的白板，写满后会遗忘早期内容。==
  4. ==无状态性：大模型本身没有记忆，每次调用都是全新开始；多轮对话的“记忆”全靠应用代码传递历史消息列表。==
  5. 对话角色：消息列表包含 system（系统提示，设定身份和规则）、user（用户输入）、assistant（模型历史回复）。
  6. 大模型的四大能力：
    • 听懂人话，精准理解意图
    • 逻辑思考，拆解任务、做决策
    • 生成符合要求的各类内容
    • 看懂规则，严格按要求执行
  7. ==大模型的三大短板：==
    • ==无执行能力，不能与外部世界交互 → 需要 Agent + 工具调用==
    • ==知识有保质期，容易产生幻觉 → 需要 RAG==
    • ==上下文窗口有限 → 需要 RAG 按需检索==
  8. 学习意义：后续的Prompt、Function Calling、RAG、Agent等技术，都是在弥补大模型的这些短板。

正文： 学习Agent开发，首先需要认识其"大脑"：大模型。

你不需要先掌握其背后的数学原理，但必须清楚它能做什么、不能做什么，以及它如何处理你发送的文字。理解这些，后续学习Prompt、Function Calling、RAG、Agent时，你才能明白"为什么要这么做"。

大模型是什么

通常所说的「AI对话」「AI助手」，核心都是 大模型，英文称为 LLM（Large Language Model，大语言模型）。 通俗地说，大模型就像一个 从小博览群书、见识广博、逻辑严谨的超级助理。

其"大"体现在两方面：

  • 参数量大：模型内部包含数千亿个参数，可理解为它"记住"了海量知识的精华
  • 训练数据大：研发人员提前为其输入了互联网上的书籍、文章、新闻、代码、论坛讨论等大量内容，使其掌握了语言规律、通用常识及各行业的基础知识

学会之后，它的核心能力是 根据给定的上下文，预测接下来最合理的文字。你问它「今天天气怎么样」，它并非真正查询天气，而是根据过去学到的语言模式，生成一个"看起来最合理的回答"。

我们日常使用的ChatGPT、豆包、通义千问、文心一言，其背后核心都是此类大模型。

Token：大模型处理文字的方式

在探讨大模型能力之前，必须先理解一个基础概念，因为它贯穿所有后续内容，即 Token。

Token是大模型处理文本的"基本单位"，它既不是一个字，也不是一个词，可以理解为将文字"切碎"后的一个个小片段。

例如，「我今天心情很好」这句话，大模型不是逐字阅读，而是先将其切分为若干个Token，比如「我」「今天」「心情」「很好」，每个碎片就是一个Token。

英文的切分更直观："Hello world" 通常被切分为 ["Hello", " world"]，大致每个单词对应1个Token。中文切分方式不同，通常每个汉字对应1～2个Token。

了解Token的原因有二：

  1. 决定模型能处理的文本长度上限：每个大模型都有"最多能处理多少Token"的限制，后续会详细说明
  2. 决定API调用费用：调用大模型的API按Token计费，发送的文字越长，模型的回复越多，费用越高

记住这个概念，我们继续。

上下文窗口：大模型的"短期记忆"

理解Token后，便能理解大模型最重要的限制之一：上下文窗口（Context Window）。

上下文窗口，指大模型每次对话时，能"看到"的内容总量上限，以Token衡量。

你可以将其想象为 一块固定大小的白板。每次对话，你说的话、模型的回复、系统提示、工具调用结果……全部要写在这块白板上。白板写满后，就得从最开头擦除旧内容，为新内容腾出空间。

因此，与大模型聊天时间越长，它越容易"遗忘"之前发生的事情，因为早期的对话内容已被从白板上擦除。

这块白板的大小因模型而异：

  • GPT-4 有128K Token的窗口，约相当于10万汉字，大约是一本中等厚度的小说
  • Claude 3.5 的上下文窗口为200K Token，更大一些
  • 部分面向长文档场景的模型，窗口可达1M Token以上

听起来似乎很大？但这块白板内装载的内容不少：你发出的所有消息 + 模型所有的回复 + 开头的系统提示词 + 每次工具调用的结果……全部需要占用空间。

实际影响：

  • 聊天时间久了，模型会"失忆"，遗忘对话前期的细节
  • 将一本几百页的产品手册直接传入，模型要么记不全，要么读了后面忘了前面，回答错漏百出
  • 即使知识库内容再多，也无法全部塞入这个窗口

这就是后续要学习的 RAG（检索增强生成） 的意义：不将全部知识塞入上下文窗口，而是每次使用时，按需检索最相关的片段放入。上下文窗口的限制，是RAG存在的根本原因。

大模型是"无状态"的，没有任何记忆

理解上下文窗口后，还需明确一点，许多初学者在此会犯错。

大模型本身没有任何记忆。

它是完全"无状态"的。每次通过API调用它，对它而言都是第一次见面，它完全不记得之前的对话、你的名字或偏好。

那为何使用ChatGPT聊天时，它似乎能记住之前的对话？

因为 是你的应用代码在负责"记忆"。每次发送消息，应用会将你们之前所有的对话历史打包成一个列表，一并传给大模型。大模型是"当场"阅读完这份历史记录后，才"看起来"记住了之前的内容。

类比一下：就像一个每次见面都失忆的助理。你必须每次见面时，将之前聊过的所有内容重新告诉他，他才能"接着上次"继续工作。你以为他记住了，其实是你每次都递给他一份完整的"历史记录"。

这直接解释了如下两点：

  • 为何上下文窗口会写满：历史对话越来越多，白板自然越来越满
  • 为何Agent需要管理记忆：Agent在执行长任务时，必须主动决定"将哪些历史传进去"，否则窗口会迅速填满

对话的角色结构：system、user、assistant

既然多轮对话是通过"传递历史列表"实现的，那么这个列表是什么样的？

调用大模型API时，传入的不是一段裸文字，而是一个有结构的消息列表，每条消息都有一个 角色（role）：

  • system：系统提示，用于设置模型的"身份和行为规则"。例如「你是一个OnCall助理，只能回答与系统故障相关的问题，回答必须简洁」。用户看不到这部分，但模型会严格遵守
  • user：用户的输入，即你说的话
  • assistant：模型之前的回复，多轮对话时，将历史回复一并打包，模型才能知道"之前说了什么"

用伪代码表示大致如下：

messages = [
  { role: "system",    content: "你是一个OnCall助理，回答必须简洁" },
  { role: "user",      content: "昨晚数据库报警是什么原因？" },
  { role: "assistant", content: "是慢查询导致的连接池耗尽。" },
  { role: "user",      content: "如何预防？" },   // 当前问题
]

模型看到整个列表后，才能理解"用户问的是什么、之前说过什么、应该如何回答"。

这个结构非常重要，后续学习Prompt时，会专门讲解如何用好 system 角色，它是控制模型行为最核心的手段。

大模型能帮我们做什么

有了上述基础认知，现在来看大模型真正的擅长领域。其核心是4件事，也是后续开发中会反复用到的能力：

1. 听懂人话，精准理解意图

无需编写复杂的代码指令或严格的格式，仅用日常白话表达需求，模型就能准确理解意图。

例如，你说「帮我把这段生硬的概念，改成小白能听懂的口语化教程」，模型能立刻明白你的要求，无需定义"生硬"“小白"“口语化"等概念，它自身就能理解。

这是所有AI应用能运转的基础。

2. 具备逻辑思考能力，能拆解任务、做出决策

给定明确目标，模型能拆解出执行步骤，并判断"下一步该做什么”。

例如，你说「帮我规划一场周末短途旅行」，它能拆解出查天气、定路线、找住宿、做预算等步骤，并按顺序推进。这种拆解任务和决策的能力，正是后续Agent的"决策大脑”。

3. 能生成符合要求的各类内容

撰写文案、编写代码、总结内容、回答问题、梳理逻辑，只要给出明确的要求和参考信息，模型就能生成贴合需求的内容。

这是它最终为用户"交付结果"的核心能力。

4. 能看懂规则，严格按要求执行

为其制定明确的规则，如「必须严格按照我提供的参考资料回答，不得自行编造」或「必须按照固定格式，告诉我应调用哪个工具」，模型便会严格遵守，不会随意发挥。

这一能力是后续学习Function Calling、RAG的核心前提，若模型不能严格按规则执行，整个系统将无法正常工作。

大模型做不到什么

这部分尤为重要，因为它直接对应了后续学习的所有技术的价值。

理解大模型的短板，就能立刻明白「为什么要开发Agent」「为什么需要学习这么多技术」。

1. 没有执行能力，无法与外部世界交互

这是最核心的短板。大模型只有"嘴"，没有"手"。你让它读取电脑文件、查询今日实时天气、给客户发送邮件、在数据库中检索记录，它只能提供执行步骤，无法亲自完成。它也无法主动连接数据库、调用第三方API、浏览网页，或与任何外部系统交互，只能在其自身的"脑海"中运转。

这就是后续学习 Agent + Tool工具调用、Function Calling和MCP协议 的核心原因：为大模型配备能执行操作的工具，打通它与真实世界之间的通道，使其从只能出主意，变为能够实际完成任务。

2. 知识具有"保质期"，且易产生幻觉

大模型的知识库在特定时间点截止，训练截止日期之后的事件它无法得知。此外，公司内部的产品手册、专属制度文档、个人笔记等私有数据，模型从未见过，更不知晓。

更棘手的是，面对未知内容，模型不一定说"我不知道"，而是很可能一本正经地编造出看似专业、实则错误的内容。行业内称其为 「幻觉」（Hallucination）。

这就是后续学习 RAG（检索增强生成） 的核心原因：将最新、专属的知识存储起来，让模型在回答时能够调取正确的参考资料，而非依赖"记忆"进行猜测。

3. 上下文窗口有上限，无法记住过长内容

前面已提及。白板空间有限，将一本数百页的电子书或产品手册传入，模型无法全部记住，会读了后面忘了前面，回答错漏百出。

这也是 RAG 要解决的问题：不将全部内容塞入窗口，而是按需检索最相关的片段。

总结

至此，整个画面已清晰：

大模型是一个 能够思考、理解、生成内容的"大脑"。

但它没有"手"（无法执行操作、对接外部世界），没有"专属知识库"（不了解私有数据），没有持久记忆（每次调用都是全新开始），且单次对话能涵盖的内容有上限（上下文窗口）。

仅凭自身，它只能进行聊天、出主意等任务，无法落地完成复杂、具体的任务。

而我们要学习的 Agent开发，本质上就是在弥补这些短板：

后续学习的每一项技术，都是为了补足大模型的某个短板。带着这一认知继续学习，你会发现每件事都有"为什么要这么做"的清晰答案。
