什么是 Skills？

📌 本章重点总结（Skills）

  1. Skills 出现的背景：有了 Function Calling（底层机制）和 MCP（标准化接口）后，AI 能调用工具了，但每次执行复杂任务（如生成日报）仍需用户反复用自然语言指导执行步骤，沟通成本高、流程无法沉淀复用。
  2. Skill 的定义：一份“标准作业程序（SOP）”，将解决特定任务所需的 背景设定（Prompt）、执行步骤 和 所需工具（MCP） 打包成一个可复用的代码文件（通常为 Markdown + YAML）。
  3. Skill 的内部结构：
    • 头部配置（Frontmatter）：YAML 格式，定义技能名称、描述，声明需要挂载的 MCP 工具。
    • 技能主体（Body）：具体的指令、工作流、规则限制和模板，用自然语言指导 AI 如何按步骤使用工具完成任务。
  4. Skill vs Prompt：
    • Prompt 只控制“嘴”（输出文本），无法真正执行操作；Skill 通过绑定工具让 AI 能“动手”。
    • Prompt 是临时的一次性指令；Skill 是项目目录中的可提交、可复用的代码资产，可团队共享。
  5. Skill vs MCP vs Function Calling 的三角关系：
    • Function Calling：底层技术，让大模型拥有调用外部工具的能力。
    • MCP：接口标准，统一工具的接入规格，相当于 AI 的“Type‑C 通用插口”。
    • Skills：上层业务封装，将 Prompt 和 MCP 工具组合成标准工作流，实现工程化沉淀与复用。
  6. 实战示例（Claude Code）：在项目 .claude/skills/ 目录下按结构放置 SKILL.md 和辅助脚本，AI 可通过触发技能自动执行多步骤任务（如图片压缩、转换格式、移动文件）。
  7. 核心价值：Skills 让 AI 从“临时问一句”升级为“按标准化流程自动执行”，降低重复沟通成本，实现经验沉淀和团队协作。

第一阶段：AI 的“破壁人”—— Function Calling（函数调用）

回顾早期的 ChatGPT，它就如同 被关在小黑屋里的超级学霸：虽然上知天文下知地理，但它没有网络（无法查实时数据），也没有手（无法真正执行操作，比如发邮件、查数据库）。

为了让大模型能够连接外部世界， Function Calling 应运而生。

简而言之，它就是 大模型与外部世界交互的一种底层机制。

假设你想让 AI 查询今天深圳的天气，它自身无法完成，但你可以提供一个 get_weather 的函数说明。AI 看到你的需求与说明后，不会直接回答天气，而是输出一段 JSON 代码：“我决定调用 get_weather，参数是 深圳”。然后你的代码利用这个参数真正调用 API，获取结果后再反馈给 AI，最后由 AI 总结成人类语言回复你。

关键点： Function Calling 是最基础的机制，它赋予了 AI 使用工具的“潜能”。

第二阶段：大一统的“Type-C 接口”—— MCP（模型上下文协议）

借助 Function Calling，大家开始积极为 AI 编写各种工具（查天气、查 MySQL、读 Github 等）。

然而，新的问题出现了：接口完全不兼容。

张三用 Python 编写了查数据库的工具，李四用 Java 实现了读本地文件的工具。由于缺乏统一标准，你的 AI 应用要接入这些现成工具，必须逐一适配它们千差万别的数据格式和通信逻辑。这就像买了一部新手机，却发现充电线有圆头、扁头、方头，令人崩溃。

这时，MCP（Model Context Protocol，模型上下文协议） 登场。

用通俗的话说，MCP 就是 AI 世界里的 “Type-C 接口标准”。

它是一套通用的开源协议。只要外部工具（数据源、数据库、代码仓库）按照 MCP 标准开发成 MCP Server，那么无论前端是哪个大模型（MCP Client），都可以 无缝、零代码修改 地直接接入使用。MCP 将 Function Calling 的能力彻底标准化了。

第三阶段：终极进化—— Skills（技能）为什么会出现？

现在，AI 拥有了底层机制（Function Calling）和标准化的工具箱（MCP）。这就能解决一切问题了吗？

并非如此。随着我们要求 AI 完成的任务越来越复杂，2026 年初，一个极其突出的问题暴露出来：每次让 AI 干活，沟通成本太高！

举例来说，假设你要 AI 帮你撰写一份项目日报。尽管你已经拥有 MCP 提供的“读取数据库”和“读取 Jira”的标准化工具，但每次与 AI 交流时，依然需要像唐僧一样反复叮嘱。

来看一下没有 Skills 之前的现状：

用户："帮我按XX格式生成报告"
用户："生成报告前，先去调用数据库工具获取今天的数据"
用户："记得要包含数据分析和总结部分"
用户："别忘了图表的排版细节..."
（每次生成报告，都要重复这段痛苦的念经过程）

发现问题了吗？ 工具虽然标准化了，但“使用工具的流程和大脑的思考方式（Prompt）”并没有被沉淀下来。

为了解决这一痛点，Skills（技能） 应运而生！

什么是 Skill？ Skill 就像是为 AI 定制的一份 “标准作业程序 (SOP)”。它将解决特定问题所需的 背景设定 (Prompt)、执行步骤 和 所需的工具 (MCP) 打包成一个干净利落的代码文件。

来看一下使用 Skills 之后的方案：

---
name: report-generator
description: 按照公司标准格式自动收集数据并生成报告
tools: 
  - mcp-jira-reader      # 挂载所需的 MCP 工具
  - mcp-database-query
---

# 报告生成流程

1. 包含封面页（模板见 templates/cover.md）
2. 执行数据分析（自动调用 mcp-database-query 获取今日核心指标）
3. 提取任务进度（自动调用 mcp-jira-reader 获取任务状态）
4. 生成图表和摘要
...

有了这个 Skill 文件，下次你只需对 AI 说：“帮我生成今天的日报”。AI 会自动加载 report-generator 这个技能，按顺序调用 MCP 工具，按规定格式输出。一步到位，神清气爽！

拆解：一个 Skill 的内部结构长什么样？

从上文的对比图可以看出，一个优秀的 Skill 结构非常清晰，通常分为两部分：

  1. 头部配置（Frontmatter）： 通常用 YAML 语法写在最前面（被 --- 包裹）。这里定义技能的名称、描述，最重要的是，声明它需要挂载哪些 MCP 工具（Tools）。这就好比一位电工师傅出门前，先在工具箱里挑好今天要使用的螺丝刀和万用表。

  2. 技能主体（Body）： 这里编写具体的指令、工作流（Workflow）、规则限制和模板。这些自然语言指令指导大模型“拿到工具后，第一步做什么，第二步做什么”。

灵魂拷问：Skills 不就是高级一点的 Prompt 吗？

可能有人会疑惑：“你看这 SKILL.md 里，主体部分不还是一堆自然语言步骤吗？这跟长一点的 Prompt（提示词）有什么区别？跟我在对话框里敲字有什么不同？”

这个问题问得很好。很多人初次接触时也会有类似错觉。我们来详细对比一下两者的关系与区别：

  • 从关系上看：包含与被包含。 Prompt 是 Skill 的“灵魂核心”，但不是全部。一个完整的 Skill = Prompt（指令与流程） + 挂载的工具列表（MCP） + 触发条件 + 上下文状态。

  • 从能力上看：动嘴与动手。 Prompt 只能控制大模型的“嘴”。即使你写一万字的 Prompt 教它如何查数据库，它也只能输出一段文字说明。而 Skill 赋予了 AI “手”。通过配置文件中绑定的 tools，AI 在阅读 Prompt 的同时，能够真正在后台调用代码、拉取数据。

  • 从工程上看：临时工与标准资产。 你在对话框里敲的 Prompt 是“临时工”，上下文一长就可能被遗忘，下次还需重敲。而 Skill 是写在项目目录里的配置文件（通常是 YAML 或 Markdown），它可以提交到 Git 仓库中成为 代码资产。它将个人经验转化为整个团队都能直接复用的 标准作业程序 (SOP)。

打个通俗的比方：

  • Prompt 是你站在厨房门口喊：“去给我炒个鱼香肉丝，先放葱姜蒜，再放肉丝！”

  • Skill 是你将《鱼香肉丝菜谱》写好，连带厨房里自动炒菜机的【启动钥匙】，一起装进一个信封。以后谁饿了，拿着这个信封扫一下，菜就自动炒出来了。

实战加餐：以最近爆火的 Claude Code 为例，看看 Skills 到底有多强？

光说不练假把式。2026 年 Anthropic 发布的终端编程神器 Claude Code 将 Skills 机制带火了。我们以此为例，看看真实项目中如何运用 Skills。

假设你正在开发一个前端网站，经常需要将设计稿中的大图片压缩、转换为 WebP 格式，然后移动到 public 文件夹。如果每次都让大模型现写一段 Python 脚本来执行，既费时又容易出错。

有了 Skills 之后，你可以在项目目录下专门创建一个“图片优化技能”。

  1. 目录结构如下：
your-web-project/
├── src/
├── .claude/                   # Claude Code 的专属配置目录
│   └── skills/                # 💡 技能大本营
│       └── image-optimizer/   # 自定义的“图片优化技能”
│           ├── SKILL.md       # 技能的说明书和工作流
│           └── optimize.py    # 真正执行任务的 Python 压缩脚本
  1. SKILL.md 中写了什么？ 如前所述，一个优秀的 Skill 包含“头部配置”和“技能主体”。在 Claude Code 中，它的写法如下：
---
name: image-optimizer
description: 专门用于将大尺寸图片压缩并转换为 webp 格式，输出到 public/assets 目录。
tools: 
  - mcp-python-runner  # 声明需要运行 Python 代码的工具能力
---

# 任务流程
当你收到优化图片的指令时，请严格按照以下步骤执行：
1. 读取用户指定的原图片文件。
2. 调用同目录下的 `optimize.py` 脚本，将原图转换为高质量的 webp 格式。
3. 将转换后的图片移动到项目的 `public/assets/` 目录下。
4. 在终端打印出压缩前后的文件大小对比。
  1. 如何使用？ 配置完成后，你在 Claude Code 的终端里只需像聊天一样发一句话（或者直接输入内置指令 /image-optimizer ）：

Claude 会自动扫描 skills/ 目录，读取 SKILL.md 理解整个工作流，然后在后台默默调用脚本、压缩图片、移动文件，最后在终端中回复你：“搞定了！图片大小从 631KB 压缩到了 56KB，已经放在 public 目录啦！”

可以发现，这种目录结构最大的好处是“热插拔”。有了 Skill，你实际上是在给 AI “教流程”、“写 SOP”。

以后遇到类似重复性任务，AI 就能像一位熟练的老员工一样，直接按照目录中的 SOP 帮你高效完成！

总结：理清它们的三角关系

最后，我们用一句话总结这三个核心概念之间的关系：

  • Function Calling（函数调用）：是底层技术，让大模型拥有了“伸手”调用外部工具的 能力。

  • MCP（模型上下文协议）：是接口标准，统一了各类工具的接入规格，让 AI 拥有了“Type-C”通用 插口。

  • Skills（技能）：是上层的业务封装（2026 年初的新宠），它将 Prompt 指令和 MCP 工具组合在一起，按清晰的 目录结构 管理起来，使 AI 可以随拿随用、彻底告别重复劳动的 标准工作流。

技术的发展总是从“能干活”（Function Calling），到“统一标准”（MCP），再到“工程化沉淀和管理”（Skills）。
