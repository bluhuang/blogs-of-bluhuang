什么是向量数据库？

上一章 RAG 里，在介绍 RAG 工作阶段的时候，提到将向量存入「向量数据库」，当时仅一笔带过。

读者可能会问： 为什么要专门用向量数据库？MySQL 不能存吗？

本章专门把这个问题讲清楚。

一、普通数据库能否存储向量？

能存，但存在一个显著问题。

普通数据库存储向量并没有障碍，向量本质上是浮点数序列，MySQL 中建立字段存储完全可行。

真正的困难在于 查询。

二、普通数据库为何无法高效查询向量？

我们先看 MySQL 的查询机制。

执行 SELECT * FROM users WHERE id = 5 时，MySQL 利用 B+ 树索引，经过几次分支定位即可完成，速度极快。执行 WHERE age > 18 时，同样借助索引进行范围扫描，效率也很高。

MySQL 的索引主要针对两类操作优化： 精确匹配 和 范围比较。

但向量搜索是另一种场景。

向量搜索的目标是： 给定一个向量，找出与之最相似的 top-k 个向量。

「最相似」需要计算距离，如余弦相似度、欧氏距离等。这需要将查询向量与库中每个向量逐一计算距离，然后排序，取最小的若干个。

MySQL 的 B+ 树索引对此无能为力，它无法在多维空间中执行「最近邻」查找。

那么能否暴力遍历？

我们来估算一下计算量。

OpenAI 的 text-embedding-ada-002 模型，每个 chunk 对应的向量维度为 1536。如果知识库中有 100 万条 chunk，每次查询需要进行的浮点运算量为：

1536 维 × 100 万条 = 15.36 亿次浮点运算

这还仅仅是计算距离这一步。每次用户提问都需要执行这样的计算，普通数据库难以承受。

如果数据量增加到 1 亿条，则为 1536 亿次浮点运算，一次查询可能需要数秒，完全不可用。

总结：普通数据库存储向量没有问题，但在查询向量相似度方面缺少优化，一旦规模扩大就会失效。

三、向量数据库是什么

向量数据库正是为了解决上述问题而设计的， 在海量向量中，实现毫秒级查找最相似的 top-k 条。

它存储的内容与普通数据库类似：向量 + 对应的原文（元数据）。但其索引结构专为向量搜索优化，能够将「15.36 亿次浮点运算」的暴力遍历，优化至几十毫秒甚至几毫秒完成。

关键问题是： 它是如何做到的？

四、向量数据库如何实现「又快又准」

秘诀是 ANN（Approximate Nearest Neighbor，近似最近邻） 搜索。

注意这里的 近似。

向量数据库并不保证找到绝对最相似的记录，而是找到「近似最相似的」几条，以精度换取速度。但在实际应用中，「近似最相似的」与「绝对最相似的」效果几乎没有差别，因为语义检索本身不需要极端精确。

目前最主流的算法是 HNSW（Hierarchical Navigable Small World，分层可导航小世界图）。

名称复杂，但通过一个例子可以清晰说明其原理。

图书馆的多级目录类比

你去一家大型图书馆，想找一本名为《MySQL 索引优化》的书。

笨方法：从第一排书架的第一本书开始，依次翻阅，直到找到目标。面对 100 万本书的图书馆，这种方法耗时极长。

图书馆的实际做法：

  • 第一步，查看大类目录牌：理工科 → 计算机科学 → 数据库技术。三步跳转后，已经排除了 90% 的书架区域。

  • 第二步，查看中类目录：性能优化 → 索引与查询。再经两步，进一步缩小范围。

  • 第三步，直接在这一小块书架上检索。扫视几眼，找到书籍。

整个过程不超过 2 分钟，而实际只查看了几十本书的标签，而不是 100 万本。

HNSW 遵循同样的逻辑。

它将所有向量组织成一个多层图结构：

  • 高层（稀疏层）：仅包含少量「节点」，每个节点连接若干「邻居」。高层负责大范围快速跳转，帮助缩小搜索区域。

  • 低层（稠密层）：包含所有向量，用于精细定位最终的近邻候选。

查询时，从高层入口开始，快速跳转至大致区域，然后下到低层进行精细扫描。整个过程只访问图的一小部分节点，而非全部。

结果： 牺牲极少量精度（通常召回率 95%+），换来 100 倍以上的速度提升。对于 100 万条向量，查询可在几毫秒内完成。

五、主流向量数据库介绍

市面上已有多种向量数据库可供选择，以下是五种最常见的。

Chroma

本地轻量级向量数据库，提供 Python 原生 API，仅需几行代码即可运行，无需任何部署配置。

适用场景： 本地开发、功能验证、快速原型搭建。若想快速体验 RAG 完整流程，Chroma 是最低门槛的选择，通过 pip 安装即可使用。

缺点：不适合生产环境，缺乏高可用、分布式等特性。

Pinecone

全托管的云向量数据库，用户无需管理基础设施（服务器、扩容、备份等），只需调用 API。

适用场景： 快速上线，避免自行运维。对于创业公司或小团队，希望将 RAG 功能部署到生产环境但缺乏专职 DBA 时，Pinecone 是最快捷的路径。

缺点：数据存储在第三方，存在数据合规顾虑的场景不适用；按用量收费，规模较大时成本较高。

Milvus

开源的生产级向量数据库，功能全面，支持多种索引类型、分布式部署、数据持久化。由 Zilliz 公司（国产）维护，社区活跃，文档完善。

适用场景： 需要私有化部署的生产环境。当数据不能出内网、需要精细控制且规模较大时，Milvus 是目前开源中功能最完整的选择。

缺点：部署和运维有一定复杂度，学习曲线较 Chroma 更陡。

Weaviate

开源向量数据库，特色是内置 Embedding 集成，用户可以直接输入原始文本，Weaviate 自动调用 Embedding 模型转换为向量，无需手动处理。同时支持图片、音频等多模态数据。

适用场景： 需要多模态搜索，或希望简化 Embedding 步骤 的场景。

Qdrant

基于 Rust 实现的高性能向量数据库，内存占用低，查询速度快，适合资源受限或高并发场景。接口设计简洁，同时支持 HTTP 和 gRPC。

适用场景： 对性能和资源消耗敏感 的生产环境，例如在有限硬件上运行大规模向量检索。

六、如何选择

下面给出一个明确的决策路径，避免模糊表述：

学习 / 原型开发 → 使用 Chroma

零配置，pip 安装，几行代码即可运行完整 RAG 流程。目前正在学习 RAG，直接使用 Chroma 即可。

生产环境，希望免运维 → 使用 Pinecone

无需操心服务器、扩容、备份等问题，数据放在云端即可，Pinecone 即开即用。

生产环境，需要私有化部署 → 使用 Milvus 或 Qdrant

数据必须保留在自有服务器上，选择这两种方案。若团队具备运维能力、需要最全功能，选 Milvus；若对性能和资源敏感、希望部署更简便，选 Qdrant。

用厨房来类比这四个选择：

  • Chroma：家用厨房。够用、方便，无需专门装修，家庭烹饪首选。

  • Pinecone：叫外卖。只需点餐，后厨、配送、洗碗全不用管，但需支付外卖费。

  • Milvus：专业餐厅厨房。功能齐全、可定制，但需要专业厨师管理。

  • Qdrant：高效快餐厨房。出餐快、省资源，适合高并发大量出餐的场景。

七、普通数据库 vs 向量数据库

对比维度普通数据库（MySQL）向量数据库（Milvus/Pinecone…）
核心用途结构化数据存储和精确查询向量存储和相似度搜索
索引结构B+ 树（适合精确匹配/范围查询）ANN 索引，如 HNSW（适合近邻搜索）
查询类型id = 5、age > 18、LIKE 匹配找 top-k 个最相似向量
向量相似度查询不支持（只能暴力全表扫描）原生支持，毫秒级
百万级向量查询速度数秒（暴力遍历，不可用）毫秒级（ANN 索引加速）
数据形式表格（行列结构）向量 + 元数据
适合 RAG 吗存储可行，查询不可行专为这个场景设计

总结

本章的核心要点：

  • 普通数据库存储向量没有问题，但查询向量相似度缺乏优化。对于百万级向量、高维（1536 维）的暴力遍历，每次查询需要数十亿次浮点运算，根本无法高效运行。

  • 向量数据库专门解决「海量向量中毫秒级查找最近邻」的问题，依赖 ANN 索引。

  • HNSW 是最主流的 ANN 索引，核心思想是多层图结构：高层大范围快速跳转，低层精细定位，类似图书馆的多级目录，无需遍历所有书籍即可找到目标区域。代价是牺牲极少量精度，换取 100 倍以上的速度提升。

  • 选型建议：学习阶段使用 Chroma；生产环境希望免运维使用 Pinecone；生产环境需要私有化部署使用 Milvus 或 Qdrant。

理解了向量数据库，RAG 的离线建库链路就完整了：文档 → 切块 → 向量化 → 存入向量数据库。
