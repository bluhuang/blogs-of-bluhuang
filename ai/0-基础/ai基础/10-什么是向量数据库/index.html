    上一章 RAG 里，在介绍 RAG 工作阶段的时候，说把向量存进「向量数据库」，当时一带而过。

    你可能当时就想问： 为什么要专门用向量数据库？传统的关系型数据库不能存吗？

    这章就专门把这个问题讲清楚。

    一、先别急，普通数据库能不能存向量？#

    能存，但有个很大的问题。

    普通数据库存储向量并没有难度，向量本质上就是一组浮点数，在关系型数据库中建个字段存下来完全可行。

    真正困难的是 查询。

    二、普通数据库为什么查不了向量？#

    先来看看关系型数据库是如何查找数据的。

    当你执行 SELECT * FROM users WHERE id = 5，数据库会利用 B+ 树索引，经过几次查找就能定位，速度极快。执行 WHERE age > 18 时，同样能利用索引进行范围扫描，效率也很高。

    数据库的索引本质上针对两类操作优化： 精确匹配 和 范围比较。

    但向量搜索完全是另一回事。

    向量搜索要解决的核心问题： 给定一个向量，找出与它最相似的 top-k 个向量。

    「最相似」意味着需要计算距离，例如余弦相似度、欧氏距离等。这类计算要求用查询向量与库中的每一条向量逐一计算距离，然后排序，选出最小的几个。

    关系型数据库的 B+ 树索引在这种场景下毫无帮助，它无法在多维空间中寻找「最近邻」。

    那是不是只能暴力遍历？

    来感受一下数据规模：

    常用的文本嵌入模型，每个文本块转化出的向量维度是 1536 维。假设知识库中有 100 万条文本块，那么每次查询需要进行的浮点运算量为：

    1536 维 × 100 万条 = 15.36 亿次浮点运算

    这还只是计算距离这一步。每次用户提问，都需要触发这个计算量，普通数据库根本无法承受。

    如果数据量增长到 1 亿条呢？1536 亿次浮点运算，一次查询可能需要好几秒，完全不可用。

    总结：普通数据库可以存储向量，但无法高效进行向量相似度查询，数据规模一大就会崩溃。

    三、向量数据库是什么#

    向量数据库正是为解决此问题而设计的， 能够在大规模向量中，毫秒级地找到最相似的 top-k 条。

    它存储的内容与普通数据库类似：向量 + 对应的原文（元数据）。但它的核心区别在于拥有专门为向量搜索优化的索引结构，能够将刚才提到的「15.36 亿次浮点运算」暴力遍历，优化到几十毫秒甚至几毫秒完成。

    关键问题来了： 它是如何做到的？

    四、向量数据库如何实现「又快又准」#

    秘诀是 ANN（Approximate Nearest Neighbor，近似最近邻） 搜索。

    注意这个词： 近似。

    向量数据库并不保证找到绝对最相似的几条记录，而是找到「差不多最相似的」几条。这是一种用精度换速度的策略。然而在大多数实际场景中，「差不多最相似的」与「绝对最相似的」在效果上几乎没有差别，因为语义检索本身并不要求极端精确。

    那么它使用的是什么算法？目前最主流的算法是 HNSW（Hierarchical Navigable Small World，分层可导航小世界图）。

    名字听起来复杂，但通过一个例子就能理解其原理。

    图书馆的多级目录类比#

    假设你来到一个大型图书馆，想找一本叫《关系数据库索引优化》的书。

    低效方法：从第一排书架的第一本书开始，一本一本翻阅，直到找到它。面对 100 万本书的图书馆，这种做法耗时极长。

    图书馆的实际做法：

    • 第一步，查看大类目录牌：理工科 → 计算机科学 → 数据库技术。三步就能排除 90% 的书架区域。
    • 第二步，查看中类目录：性能优化 → 索引与查询。再两步，进一步缩小范围。
    • 第三步，直接在这一块书架上寻找。扫视几眼，就能拿到书。

    整个过程不超过 2 分钟，而实际上你总共只「浏览」了几十本书的标签，而不是 100 万本。

    HNSW 就是这个逻辑。

    它将所有向量组织成一个多层的图结构：

    • 高层（稀疏层）：仅有少量的「节点」，每个节点连接着几个「邻居」。高层负责快速的大范围跳转，帮助你迅速缩小搜索范围。
    • 低层（稠密层）：包含所有向量，在低层进行精细的局部搜索，确定最终的近邻候选。

    查询时，从高层的入口进入，快速跳转几步找到大致区域，然后下到低层进行精细扫描。整个过程只需要访问整个图的一小部分节点，而不是全部节点。

    结果： 牺牲极少量精度（通常可达到 95%+ 的召回率），换来 100 倍以上的速度提升。对于 100 万条向量，几毫秒即可完成。

    五、主流向量数据库介绍#

    目前市面上已有多种向量数据库可供选择，下面介绍几种常见的。

    轻量级本地数据库#

    本地轻量级向量数据库，提供 Python 原生 API，几行代码就能运行，无需任何部署配置。

    适用场景： 本地开发、功能验证、快速原型。如果你想快速跑通 RAG 的完整流程，这是最低摩擦的选择，安装一个包就能直接使用。

    缺点：不适合生产环境，缺乏高可用、分布式等特性。

    全托管云数据库#

    全托管的云向量数据库，用户无需管理任何基础设施，服务器、扩容、备份均由服务方负责，只需调用 API 即可。

    适用场景： 希望快速上线，不想自己运维。对于创业公司或小团队，想要将 RAG 功能上线生产环境但缺乏专业运维人员，这是最快速的路径。

    缺点：数据存储于第三方，存在数据合规顾虑时需谨慎；按用量收费，规模较大时成本不低。

    开源生产级数据库#

    开源的生产级向量数据库，功能全面，支持多种索引类型、分布式部署和数据持久化。

    适用场景： 需要私有化部署的生产环境。当数据不能离开内网、需要精细控制且规模较大时，这是目前开源功能最完整的选择。

    缺点：部署和运维有一定复杂度，学习曲线较陡。

    内置嵌入集成的数据库#

    开源向量数据库，特色是内置了嵌入集成功能，可以直接将原始文本传入，由系统自动调用嵌入模型生成向量，无需自己处理转换步骤。同时支持图片、音频等多模态数据。

    适用场景： 需要多模态搜索，或希望简化嵌入步骤 的场景。

    高性能数据库#

    基于高性能语言实现的高性能向量数据库，内存占用低，查询速度快，适合资源受限或高并发场景。接口设计简洁，同时支持 HTTP 和 gRPC。

    适用场景： 对性能和资源消耗敏感 的生产环境，例如在有限硬件上运行大规模向量检索。

    六、如何选择？#

    介绍了这几种，该如何选择？提供一个清晰的决策思路：

    学习 / 跑原型 → 使用轻量级本地数据库

    零配置，安装即用，几行代码可跑通完整 RAG 流程。如果你正在学习 RAG，直接选择它，不必犹豫。

    生产环境，不想管运维 → 使用全托管云数据库

    不想操心服务器、扩容、备份等事务，且数据上云没有顾虑，可以直接选择全托管服务。

    生产环境，需要私有化部署 → 使用开源生产级数据库或高性能数据库

    数据必须保留在自己的服务器上，选择这两个方向。团队具备运维能力且需要最全功能，选择开源生产级数据库；对性能和资源敏感、希望部署简单些，选择高性能数据库。

    用厨房来类比这几种选择：

    • 轻量级本地数据库：家用厨房。够用，方便，无需专门装修，在家做饭的首选。
    • 全托管云数据库：叫外卖。你只管点菜，后厨、配送、洗碗全都不用管，但要支付外卖费。
    • 开源生产级数据库：专业餐厅厨房。功能齐全、可定制，但需要有专业厨师来打理。
    • 高性能数据库：高效快餐厨房。出菜快、节省资源，适合高并发大量出餐的场景。

    七、普通数据库 vs 向量数据库#

    对比维度普通数据库（关系型）向量数据库（专用向量数据库）
    核心用途结构化数据存储和精确查询向量存储和相似度搜索
    索引结构B+ 树（适合精确匹配/范围查询）ANN 索引，如 HNSW（适合近邻搜索）
    查询类型id = 5、age > 18、LIKE 匹配找 top-k 个最相似向量
    向量相似度查询不支持（只能暴力全表扫描）原生支持，毫秒级
    百万级向量查询速度数秒（暴力遍历，不可用）毫秒级（ANN 索引加速）
    数据形式表格（行列结构）向量 + 元数据
    适合 RAG 吗存储可以，查询不行专为此场景设计

    总结#

    这章的核心认知：

    • 普通数据库可以存储向量，但无法高效进行向量相似度查询。百万级向量加上高维度（1536 维）的暴力遍历，每次查询需要几十亿次浮点运算，根本无法运行。
    • 向量数据库专门解决「在海量向量中毫秒级找到最近邻」的问题，其核心在于 ANN 索引。
    • HNSW 是目前最主流的 ANN 索引，核心思路是多层图结构：高层进行大范围快速跳转，低层进行精细定位，如同图书馆的多级目录，无需翻阅所有书籍就能找到目标区域。代价是牺牲极少量精度，换来 100 倍以上的速度提升。
    • 选型建议：学习用轻量级本地数据库，生产环境不想运维用全托管云数据库，生产环境需要私有化部署用开源生产级数据库或高性能数据库。

    理解了向量数据库，RAG 的离线建库链路就完整了：文档 → 切块 → 向量化 → 存入向量数据库。
