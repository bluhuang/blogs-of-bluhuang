### 📌 本章重点总结（Skills）

1. **Skills 出现的背景**：有了 Function Calling（底层机制）和 MCP（标准化接口）后，AI 能调用工具了，但每次执行复杂任务（如生成日报）仍需用户反复用自然语言指导执行步骤，沟通成本高、流程无法沉淀复用。
2. **Skill 的定义**：一份“标准作业程序（SOP）”，将解决特定任务所需的 **背景设定（Prompt）**、**执行步骤** 和 **所需工具（MCP）** 打包成一个可复用的代码文件（通常为 Markdown + YAML）。
3. **Skill 的内部结构**：
   - **头部配置（Frontmatter）**：YAML 格式，定义技能名称、描述，**声明需要挂载的 MCP 工具**。
   - **技能主体（Body）**：具体的指令、工作流、规则限制和模板，用自然语言指导 AI 如何按步骤使用工具完成任务。
4. **Skill vs Prompt**：
   - Prompt 只控制“嘴”（输出文本），无法真正执行操作；Skill 通过绑定工具让 AI 能“动手”。
   - Prompt 是临时的一次性指令；Skill 是项目目录中的可提交、可复用的**代码资产**，可团队共享。
5. **Skill vs MCP vs Function Calling 的三角关系**：
   - **Function Calling**：底层技术，让大模型拥有调用外部工具的**能力**。
   - **MCP**：接口标准，统一工具的接入规格，相当于 AI 的“Type‑C 通用插口”。
   - **Skills**：上层业务封装，将 Prompt 和 MCP 工具组合成**标准工作流**，实现工程化沉淀与复用。
6. **实战示例（Claude Code）**：在项目 `.claude/skills/` 目录下按结构放置 `SKILL.md` 和辅助脚本，AI 可通过触发技能自动执行多步骤任务（如图片压缩、转换格式、移动文件）。
7. **核心价值**：Skills 让 AI 从“临时问一句”升级为“按标准化流程自动执行”，降低重复沟通成本，实现经验沉淀和团队协作。

***
### 第一阶段：AI 的“破壁人”——Function Calling（函数调用）

回想早期的 ChatGPT，它就像一个 **被关在小黑屋里的超级学霸**：虽然上知天文下知地理，但它没网（无法查实时数据），也没手（无法真正执行操作，如发邮件、查数据库）。

为了让大模型能连接外部世界， **Function Calling** 诞生了。

简单来说，这就是 **大模型与外部世界打交道的“底层暗号”**。

![](<attachments/什么是 Skills？-a10fb66149c1f8fb11a6fff656333a74.png>)

如果你想查询今天深圳的天气，AI 自身无法获取，但你可以提供一个 `get_weather` 的函数说明。AI 看到需求与说明后，不会直接回答天气，而是输出一段 JSON 代码：“我决定调用 `get_weather`，参数是 `深圳`”。然后你的代码拿着这个参数去真正调用 API，获取结果后喂给 AI，AI 最后总结成人类语言回复你。

**重点：** Function Calling 是最基础的机制，它赋予了 AI 使用工具的“潜能”。

***

### 第二阶段：大一统的“Type-C 接口”——MCP（模型上下文协议）

有了 Function Calling，大家开始给 AI 疯狂编写各种工具（查天气、查 MySQL、读 Github 等）。

但很快，新问题出现了： **接口完全不兼容。**

张三用 Python 写了一个查数据库的工具，李四用 Java 写了一个读本地文件的工具。由于没有统一的标准，你的 AI 应用想要接入这些现成的工具，就得逐个适配它们千奇百怪的数据格式和通信逻辑。这就像你买了一个新手机，却发现大家用的充电线有圆头、扁头、方头，令人崩溃。

这时， **MCP（Model Context Protocol，模型上下文协议）** 登场。

![](<attachments/什么是 Skills？-ea7ead105944bf47f68b97c69bdf0ade.png>)

用大白话说，MCP 就是 AI 世界里的 **“Type-C 接口标准”**。

它是一套通用的开源协议。只要外部工具（数据源、数据库、代码仓库）按照 MCP 标准开发成 MCP Server，那么无论前端是哪个大模型（MCP Client），都可以 **无缝、零代码修改** 地直接插上使用。MCP 将 Function Calling 的能力彻底标准化了。

***

### 第三阶段：终极进化——Skills（技能）的出现

AI 已经拥有了底层机制（Function Calling）和标准化的工具箱（MCP），但还远远不够。

随着让 AI 执行的任务日益复杂，2026 年初，一个极其突出的问题暴露出来： **每次让 AI 干活，沟通成本太高！**

假设你要让 AI 帮你写一份项目日报。你虽然已经拥有了 MCP 提供的“读取数据库”和“读取 Jira”的标准化工具，但每次与 AI 对话，仍得像唐僧一样反复叮嘱。

**回顾没有 Skills 之前的现状：**

```plaintext
用户："帮我按XX格式生成报告"
用户："生成报告前，先去调用数据库工具获取今天的数据"
用户："记得要包含数据分析和总结部分"
用户："别忘了图表的排版细节..."
（每次生成报告，都要重复这段痛苦的念经过程）
```

**问题所在：** 工具虽然标准化了，但“使用工具的流程和大脑的思考方式（Prompt）”并没有被沉淀下来。

为了解决这个痛点， **Skills（技能）** 应运而生！

**什么是 Skill？** Skill 就像是为 AI 定制的一份 **“标准作业程序（SOP）”**。它把解决特定问题所需的 **背景设定（Prompt）**、 **执行步骤** 和 **所需工具（MCP）**，打包成一个清晰简洁的代码文件。

![](<attachments/什么是 Skills？-d2e8432578bc86d22d07dbe3805045bd.png>)

**应用 Skills 之后的方案：**

```markdown
---
name: report-generator
description: 按照公司标准格式自动收集数据并生成报告
tools: 
  - mcp-jira-reader      # 挂载所需的 MCP 工具
  - mcp-database-query
---

# 报告生成流程

1. 包含封面页（模板见 templates/cover.md）
2. 执行数据分析（自动调用 mcp-database-query 获取今日核心指标）
3. 提取任务进度（自动调用 mcp-jira-reader 获取任务状态）
4. 生成图表和摘要
...
```

有了这个 Skill 文件，下次只需对 AI 说一句：“ **帮我生成今天的日报**”。 AI 就会自动加载 `report-generator` 技能，自动按顺序调用 MCP 工具，按照规定格式输出。一步到位，神清气爽！

***

### 拆解：一个 Skill 的内部结构

从上面的对比图可以看出，一个优秀的 Skill 结构清晰，通常分为两部分：

1. **头部配置（Frontmatter）：** 通常用 YAML 语法写在最前面（由 `---` 包裹）。这里定义技能的名称、描述， **最重要的是声明需要挂载哪些 MCP 工具（Tools）**。这好比一个电工师傅出门前，先在工具箱里挑好今天要用的螺丝刀和万用表。

2. **技能主体（Body）：** 这里包含具体的指令、工作流（Workflow）、规则限制和模板。这些自然语言指令，指导大模型“拿到工具后，第一步做什么，第二步做什么”。

***

### 灵魂拷问：Skills 不就是高级一点的 Prompt 吗？

可能有同学会想：“`SKILL.md` 的主体部分不还是写了一堆自然语言的步骤吗？这不就是个长一点的 Prompt（提示词）吗？与在对话框里敲字有什么区别？”

这个疑问很常见。我们来梳理一下两者的关系与区别：

* **从关系上看：包含与被包含。** Prompt 是 Skill 的“灵魂核心”，但不是全部。一个完整的 Skill = **Prompt（指令与流程） + 挂载的工具列表（MCP） + 触发条件 + 上下文状态**。

* **从能力上看：动嘴与动手。** Prompt 只能控制大模型的“嘴”。即使你写一万字的 Prompt 教它如何查数据库，它也只能输出一段如何查的文本。而 Skill 给 AI 赋予了“手”。通过配置文件里绑定的 `tools`，AI 在阅读 Prompt 的同时，真的能去后台调用代码、拉取数据。

* **从工程上看：临时工与标准资产。** 你在对话框里输入的 Prompt 是“临时工”，上下文一长就会遗失，下次需要重新输入。而 Skill 是写在项目目录里的配置文件（通常是 YAML 或 Markdown），可以提交到 Git 仓库中成为 **代码资产**。它将个人经验转化为整个团队都能直接复用的 **标准作业程序（SOP）**。

打个比方：

* **Prompt** 是你站在厨房门口喊：“去给我炒个鱼香肉丝，先放葱姜蒜，再放肉丝！”

* **Skill** 是你把《鱼香肉丝菜谱》写好，连带厨房里自动炒菜机的【启动钥匙】，一起装进一个信封里。以后谁饿了，拿着这个信封扫一下，菜就自动炒出来了。

### 实战加餐：以 Claude Code 为例，看 Skills 的强大之处

光说不练假把式。2026 年 Anthropic 发布的终端编程神器 **Claude Code**，将 Skills 机制推向了热潮。我们以它为例，看看真实项目中如何运用 Skills。

假设你在开发一个前端网站，经常需要将设计稿中的大图片压缩、转换为 WebP 格式，再移动到 `public` 文件夹。如果每次都让大模型临时编写 Python 脚本来执行，既费时又容易出错。

有了 Skills，你可以直接在项目目录下创建一个专门干这个活的“图片优化技能”。

1. **目录结构如下：**

```plaintext
your-web-project/
├── src/
├── .claude/                   # Claude Code 的专属配置目录
│   └── skills/                # 💡 技能大本营
│       └── image-optimizer/   # 自定义的“图片优化技能”
│           ├── SKILL.md       # 技能的说明书和工作流
│           └── optimize.py    # 真正干活的 Python 压缩脚本
```

2. **SKILL.md 的内容：** 一个优秀的 Skill 分为“头部配置”和“技能主体”。在 Claude Code 中，写法如下：

```markdown
---
name: image-optimizer
description: 专门用于将大尺寸图片压缩并转换为 webp 格式，输出到 public/assets 目录。
tools: 
  - mcp-python-runner  # 声明需要用到运行 Python 代码的工具能力
---

# 任务流程
当你收到优化图片的指令时，请严格按照以下步骤执行：
1. 读取用户指定的原图片文件。
2. 调用同目录下的 `optimize.py` 脚本，将原图转换为高质量的 webp 格式。
3. 将转换后的图片移动到项目的 `public/assets/` 目录下。
4. 在终端打印压缩前后的文件大小对比。
```

3. **如何使用？** 配置完成后，在 Claude Code 的终端中，你只需像聊天一样发一句话（或直接输入内置指令 `/image-optimizer`）：

Claude 会自动扫描 `skills/` 目录，读取 `SKILL.md` 理解整个工作流，然后在后台默默调用脚本、压缩图片、移动文件，最后在终端回复：“搞定了！图片大小从 631KB 压缩到了 56KB，已放在 public 目录！”

这种目录结构最大的优势是“热插拔”。 **有了 Skill，你实际上是在给 AI“教流程”、“写 SOP”。**

以后再遇到类似的重复性任务，AI 就能像一个经验丰富的员工一样，直接按照目录中的 SOP 高效完成工作。

***

### 总结：理清三角关系

最后，用一句话总结这三个核心概念：

![](<attachments/什么是 Skills？-dfad3afaf804be85f0b24b74e803a2e4.png>)

* **Function Calling（函数调用）：** 是底层技术，赋予大模型“伸手”调用外部工具的 **能力**。

* **MCP（模型上下文协议）：** 是接口标准，统一了全网工具的接入规格，让 AI 拥有了“Type-C”通用 **插口**。

* **Skills（技能）：** 是上层的业务封装（2026 年初的新宠），它将 Prompt 指令和 MCP 工具组合在一起，通过清晰的 **目录结构** 管理起来，变为 AI 可随拿随用、彻底告别重复劳动的 **标准工作流**。

技术的发展永远遵循这样的路径：从“能干活”（Function Calling），到“统一标准”（MCP），再到“工程化沉淀和管理”（Skills）。
