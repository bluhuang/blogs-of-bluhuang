### 📌 本章重点总结（大模型基础）

1. **大模型本质**：一个基于海量数据训练、通过预测下一个词来生成文本的“超级助理”。
2. **Token**：大模型处理文本的最小单位（非字非词），决定模型输入上限和API费用。
3. ==**上下文窗口**：模型单次能“看到”的Token总量（如128K），相当于一块固定大小的白板，写满后会遗忘早期内容。==
4. ==**无状态性**：大模型本身没有记忆，每次调用都是全新开始；多轮对话的“记忆”全靠应用代码传递历史消息列表。==
5. **对话角色**：消息列表包含 `system`（系统提示，设定身份和规则）、`user`（用户输入）、`assistant`（模型历史回复）。
6. **大模型的四大能力**：
   - 听懂人话，精准理解意图
   - 逻辑思考，拆解任务、做决策
   - 生成符合要求的各类内容
   - 看懂规则，严格按要求执行
7. ==**大模型的三大短板**：==
   - ==无执行能力，不能与外部世界交互 → 需要 **Agent + 工具调用**==
   - ==知识有保质期，容易产生幻觉 → 需要 **RAG**==
   - ==上下文窗口有限 → 需要 **RAG** 按需检索==
8. **学习意义**：后续的Prompt、Function Calling、RAG、Agent等技术，都是在弥补大模型的这些短板。

正文：

学习Agent开发，首先需要认识它的“大脑”：**大模型**

你无需深究其背后的数学原理，但必须清楚它能做什么、不能做什么，以及它是如何“理解”你发送的文字的。搞清这些，后续学习Prompt、Function Calling、RAG、Agent时，你才能明白“为什么要这样做”。

## 大模型是什么

我们日常所说的「AI对话」「AI助手」，核心都是**大模型**，英文称**LLM**（Large Language Model，大语言模型）。
通俗地讲，大模型就像一个**从小阅读海量书籍、见识广博、逻辑清晰的超级助理**。

![](什么是大模型？-b705b8c12f49b00982a7087315749e0f.png)

它“大”在两点：

- **参数量大**：模型内部有数千亿个参数，可以理解为它“记住了”海量知识的精华。
- **训练数据大**：研发人员提前喂入互联网上的书籍、文章、新闻、代码、论坛讨论等大量内容，让它学会了语言规律、通用常识和各行各业的基础知识。

学会之后，它能做什么？简而言之，就是**根据你提供的上下文，预测接下来最合理的文字是什么**。你问它「今天天气怎么样」，它并非真的去查询天气，而是依据过去学过的语言模式，生成一个“看起来最合理的回答”。

我们平时使用的ChatGPT、豆包、通义千问、文心一言等，其核心都是这样的大模型。

---

## Token：大模型读取文字的方式

在讲解大模型的能力之前，有一个基础概念必须明确，因为后续所有内容都与之相关，那就是**Token**。

**Token是大模型处理文本的“基本单位”**，它既不是一个字，也不是一个词，可以理解为将文字“切碎”后的小碎片。

![](什么是大模型？-2c33ce44947270329f9fc8f4ea558fcf.png)

例如，「我今天心情很好」这句话，大模型并非逐字读取，而是先将其切分为若干个Token，比如可能切成：「我」「今天」「心情」「很好」，每个碎片就是一个Token。

英文的切分更直观：`"Hello world"` 通常被切分为 `["Hello", " world"]`，大约每个单词对应1个Token。中文切分有所不同，通常每个汉字对应1～2个Token。

了解Token的原因有二：

1. **决定模型能处理的文本长度上限**：每个大模型都有“最多能处理多少Token”的上限，这一点后续会详细说明。
2. **决定API调用费用**：调用大模型的API按Token计费，发送的文字越长、模型回复越多，费用越高。

记住这个概念，我们继续。

---

## 上下文窗口：大模型的“短期记忆”

理解了Token，就能理解大模型最重要的一个限制，即**上下文窗口（Context Window）**。

**上下文窗口**指大模型每次对话时能“看到”的内容总量上限，用Token衡量。

可以将其想象成**一块固定大小的白板**。每次对话，你说的话、模型的回复、系统提示、工具调用结果等，全部要写在这块白板上。白板写满后，必须从最开头擦掉，为新内容腾出空间。

因此，与大模型聊天时间越长，它越容易“遗忘”此前的内容，因为早期对话已被擦除。

这块白板有多大？不同模型差异显著：

- GPT-4拥有128K Token的窗口，约相当于10万汉字，差不多是一本中等厚度的小说。
- Claude 3.5的上下文窗口为200K Token，更大一些。
- 某些面向长文档场景的模型，窗口可达1M Token以上。

听起来很大？但这块白板中装的内容可不少：你发出的所有消息、模型所有的回复、开头的系统提示词、每次工具调用的结果……全部要占用空间。

![](什么是大模型？-9de9a2ca83477affff0185fbbd871bad.png)

**实际影响是什么？**

- 聊天时间长了，模型会“失忆”，忘记对话前期的细节。
- 你把一本几百页的产品手册直接丢给它，它要么记不全，要么读了后面忘了前面，回答错漏百出。
- 知识库内容再多，也无法全部塞进这个窗口。

这也是我们后续要学习**RAG（检索增强生成）**的原因，其核心思路是：不将全部知识塞入上下文窗口，而是每次使用时按需检索最相关的片段放进去。上下文窗口的限制，是RAG存在的根本原因。

---

## 大模型是“无状态”的，没有任何记忆

理解了上下文窗口，还有一点必须说清楚，因为很多初学者在此处容易踩坑。

**大模型本身没有任何记忆。**

它是完全“无状态”的。每次通过API调用它，对它来说都是初次见面，它完全不记得之前聊过什么、你叫什么名字、你有什么偏好。

![](什么是大模型？-469699ec7b1dbe8a03e1ab91b104c4e5.png)

那为什么使用ChatGPT聊天时，它似乎能记住之前说过的话？

因为**是你的应用代码在负责“记忆”**。每次发消息，应用都会将之前所有的对话历史打包成一个列表，一同传给大模型。大模型是“当场”看完这份历史记录后，才“看起来”记住了你说过的话。

类比一下：就像一个每次见面都失忆的助理，你必须在每次见面时将之前聊过的所有内容重新告诉他，他才能“接着上次”继续工作。你以为他记住了，其实是你每次都递给他一份完整的“历史记录”。

这直接解释了两件事：

- **为什么上下文窗口会写满**：历史对话越来越多，白板自然越来越满。
- **为什么Agent需要管理记忆**：Agent在执行长任务时，必须主动决定“将哪些历史传进去”，否则窗口很快会被塞满。

---

## 对话的角色结构：system、user、assistant

既然多轮对话是通过“传递历史列表”实现的，那么这个列表长什么样？

调用大模型API时，你传入的不是一段纯文字，而是一个有结构的消息列表，每条消息都有一个**角色（role）**：

- `system`：**系统提示**，给模型的“身份设定和行为规则”。例如「你是一个OnCall助理，只能回答与系统故障相关的问题，且回答必须简洁」。这部分用户看不见，但模型会严格遵守。
- `user`：**用户的输入**，即你说的话。
- `assistant`：**模型之前的回复**，多轮对话时，将历史回复也打包进来，模型才能知道“之前说了什么”。

用伪代码表示如下：

```json
messages = [
  { role: "system",    content: "你是一个OnCall助理，回答必须简洁" },
  { role: "user",      content: "昨晚数据库报警是什么原因？" },
  { role: "assistant", content: "是慢查询导致的连接池耗尽。" },
  { role: "user",      content: "怎么预防？" },   // 当前问题
]
```

模型看到整个列表后，才能知道“用户问什么、之前说过什么、应该如何回答”。

这个结构非常重要，后续学习Prompt时，我们会专门讲解如何用好 `system` 角色，它是控制模型行为最核心的手段。

## 大模型能帮我们做什么

有了上述基础认知，我们来看大模型真正擅长什么。核心是4件事，也是后续开发全程都会用到的能力：

![](什么是大模型？-dda70cc2ca9cf31a9e8faab6338754d4.png)

### 1. 听得懂人话，精准理解意图

你不用编写复杂的代码指令，不需要抠严谨的格式，只需用日常大白话表达需求，它就能精准理解你的意图。

例如，你说「帮我把这段生硬的概念，改成小白能听懂的口语化教程」，它能立刻明白你的要求，无需定义“生硬”“小白”“口语化”等概念，它自己就能理解。

这是所有AI应用能够运转的基础。

### 2. 会逻辑思考，能拆解任务、做决策

给它一个明确的目标，它能拆解出一步步的执行步骤，还能判断“下一步该做什么”。

例如，你说「帮我规划一场周末的短途旅行」，它能拆解出查天气、定路线、找住宿、做预算等步骤，并按顺序推进。这种拆解任务和做决策的能力，就是我们后续Agent的“决策大脑”。

### 3. 能生成符合要求的各类内容

写文案、写代码、写总结、回答问题、梳理逻辑，只要你给出明确的要求和参考信息，它就能生成贴合需求的内容。

这是它最终向用户“交付结果”的核心能力。

### 4. 能看懂规则，严格按要求执行

你给它定好明确的规矩，比如「必须严格按照我给的参考资料回答，不许自己瞎编」，或者「必须按照我给的固定格式，告诉我要调用哪个工具」，它就能严格遵守，不会随意发挥。

这个能力是我们后续学习Function Calling、RAG的核心前提，如果模型不能严格按规则执行，整个系统就会乱套。

## 大模型做不到什么

这部分尤为重要，因为它直接对应了我们后续要学的所有技术的价值。

理解了大模型的短板，就能立刻明白“我们为什么要开发Agent”“为什么要学这么多技术”。

![](什么是大模型？-316ac57f160b55b86c007560f73d3df9.png)

### 1. 没有执行能力，不能和外部世界交互

这是最核心的短板。大模型只有“嘴”，没有“手”。你让它帮你读取电脑中的文件、查询今天的实时天气、给客户发送一封邮件、在数据库中查询一条记录，它只能为你写出步骤，无法亲自完成这些操作。它也无法主动连接数据库、调用第三方API、浏览网页，或与外部任何系统交互，只能在自己的“大脑”中运转。

这就是我们后续要学习**Agent + Tool工具调用、Function Calling和MCP协议**的核心原因：给大模型配备能动手的工具，打通它和真实世界之间的通道，使其从只会出主意变成能干活。

### 2. 知识有“保质期”，还容易瞎编

大模型的知识库在某个时间点截止，训练截止日期之后发生的事情它不知道。而且你公司内部的产品手册、专属的制度文档、你自己的私人笔记，它根本没见过，也不知道。

更麻烦的是，遇到它不知道的内容，它不一定会说“我不知道”，而是很可能一本正经地编出一堆看起来专业、实际全是错误的内容。行业内称之为**「幻觉」（Hallucination）**。

这就是我们后续要学习**RAG（检索增强生成）**的核心原因：将最新的、专属的知识存储起来，让模型在回答时能够调取正确的参考资料，而不是靠“记忆”胡乱猜测。

### 3. 上下文窗口有上限，记不住太长的内容

前面已经讲过。白板就这么大，你将一本几百上千页的电子书或产品手册扔给它，它根本记不住，会读了后面忘前面，回答错漏百出。

这也是**RAG**要解决的问题：不将全部内容塞入窗口，而是按需检索最相关的片段。

---

## 总结

至此，整个画面就清晰了：

大模型是一个**能够思考、理解、生成内容的“大脑”**。

但它没有“手”（不能执行操作，不能对接外部世界），没有“专属知识库”（不知道你的私有数据），没有持久记忆（每次调用对它都是全新的），而且单次对话能看到的内容也有上限（上下文窗口）。

单靠它自己，只能完成聊天、出主意等任务，无法落地完成复杂的、具体的任务。

而我们要学习的**Agent开发**，本质上就是：

后续要学习的每一个技术，都是在弥补大模型的某块短板。带着这个认知继续学习，你会发现每件事都有“为什么要这么做”的清晰答案。
