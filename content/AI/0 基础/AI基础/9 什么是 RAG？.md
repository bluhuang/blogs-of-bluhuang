### 📌 本章重点总结（RAG）

1. **RAG 是什么**：Retrieval-Augmented Generation（检索增强生成）。先检索私有知识库中最相关的内容，再将其注入 Prompt，让大模型基于有据可查的资料生成回答。
2. **为什么需要 RAG**：大模型知识静态、封闭（截止日期、无私有数据、无实时数据），全量塞入 Prompt 受限于上下文窗口、成本高、注意力稀释。RAG 实现“按需检索 + 动态注入”。
3. **核心思路**：不把所有数据都塞进 Prompt，而是每次回答前，先从知识库中检索最相关的几段内容，再将这几段注入 Prompt。
4. **两大阶段**：
   - **离线建库**：加载文档 → 文本切块（Chunking）→ 向量化（Embedding）→ 存入向量数据库。
   - **在线检索生成**：问题向量化 → 语义搜索（取最相似 chunk）→ 构造增强 Prompt → 大模型生成回答。
5. **关键概念**：
   - **向量（Vector）**：文字的“语义坐标”，语义相近的内容向量距离近。
   - **语义搜索**：不依赖关键词匹配，而是通过向量相似度找到意思相关的内容，即使词语不同也能召回。
6. **RAG 在 Agent 中的位置**：RAG 本质上是一个特殊的“知识库检索工具”，通过 Function Calling 被 Agent 调用，成为 Agent 能力体系的一部分。
7. **对比优势**：可访问私有数据、知识更新快（更新文档即生效）、Token 消耗低、回答有据可查、扩展性好。

***
前几章将 Agent 的工具体系搭建清楚：Function Calling 让大模型能发出指令，MCP 使工具标准化接入，Skills 让专业知识按需加载。至此，Agent 能够执行任务，工具也能正常运行。

但有一个根本问题尚未正面回答：**大模型看不到私有数据，该如何处理？**

公司内部的几千页运维手册、几百个历史故障报告、一套内部独有的排查 SOP，大模型从未见过。当需要其执行 OnCall 排查时，它能给出通用思路，却无法给出针对具体系统的精准答案。

这正是 **RAG** 要解决的核心问题。

***

## 一、大模型为何无法「看到」你的数据？

首先明确问题，存在三类「看不到」，每类成因不同。

![](<attachments/什么是 RAG？-36e920b9eec4dde61012702484969045.png>)

**第一类：知识截止日期**

大模型基于历史数据训练，训练后知识冻结。例如 Claude 的训练数据截止到 2025 年某个时间点，之后发生的事件它无法获知。若询问“我们系统今天凌晨发生了什么故障”，模型缺乏该信息，只能猜测。

**第二类：私有数据**

公司内部文档、产品设计方案、运维手册、客服问答库等均为保密信息，不会出现在大模型训练数据中。模型从未接触这些内容，自然无法据此回答问题。

**第三类：实时数据**

刚完成的技术方案、新产生的 bug 日志、刚更新的配置文件等动态变化的数据，即使大模型更新训练数据也难以实时追踪。Agent 需要访问的，往往正是这类「最新鲜」的数据。

三类问题的共同点：**大模型的知识静态、封闭，而业务数据动态、私有**。

***

## 二、为什么暴力解法不可行？

面对此问题，许多人的第一反应是：**直接将数据塞入 Prompt 中**。

听起来直接，但此方案存在三个致命问题。

**问题一：Context Window 有上限**

大模型一次能处理的文本量有限，即 Context Window（上下文窗口）。即使当前最大的模型，一次也只能处理几十万 token，对应中文约几十万字。

公司内部文档可能有数百个文件，仅运维手册就几十万字，无法完整塞入。更不必提包含数千条工单的故障数据库。

**问题二：成本高且速度慢**

Token 需要付费。若塞入 10 万 token 的背景资料，每次提问都需支付相应费用。若一天提问数百次，成本迅速攀升。同时，token 数量越多，模型推理越慢，用户等待时间越长。

**问题三：注意力稀释**

这是最易被忽视的问题。大模型处理长上下文时，注意力会被稀释，相关内容埋在大量文本中，模型可能无法聚焦，反而表现下降。塞入越多信息，有时回答质量反而越低。

***

## 三、RAG 的核心思路：先检索，再回答

直接塞数据行不通，RAG 如何解决？核心思路非常简洁，一句话即可概括：

**不将所有数据塞入 Prompt，而是在每次回答前，先找到最相关的几段内容，再将这几段塞入 Prompt。**

![](<attachments/什么是 RAG？-a359fff0264c2cd81a17d249068fa360.png>)

这就是 RAG 名称的含义：

* **Retrieval（检索）**：从知识库中找出与当前问题最相关的内容
* **Augmented（增强）**：将检索到的内容加入 Prompt，增强大模型的上下文
* **Generation（生成）**：大模型基于增强后的上下文生成回答

类比考试时查字典：无需背下整本字典，只需知道去查哪个词，查到那一页，看完再写答案。

RAG 采用此思路：大模型无需「记住」全部知识，只需在需要时从知识库检索相关内容，并据此回答。

***

## 四、RAG 的两大阶段

RAG 的整个工作流程分为两个阶段：**离线建库** 和 **在线检索生成**。

![](<attachments/什么是 RAG？-97d0546d6a6f5b74a3ba238e84b646e6.png>)

离线建库为一次性准备工作（数据更新时重新执行），在线检索为每次用户提问触发的实时流程。

### 离线阶段

此阶段目标是将私有数据处理成大模型能快速检索的格式，存入向量数据库。共四步：

![](<attachments/什么是 RAG？-9d45b0f41b7d675e798b88062c47f188.png>)

**Step 1：加载文档**

将所有数据源统一接入，包括 PDF 文档、Word 文件、Markdown 笔记、网页内容、数据库记录、代码文件等，统一解析为纯文本。

**Step 2：文本切块（Chunking）**

文本不能整篇存储，需切分为小块。原因有二：首先，一篇文档可能包含多个主题，检索时可能只需要其中一部分，无需整篇召回；其次，每个 chunk 需转化为向量存储，若 chunk 过长，向量无法精确代表该段文字的核心含义，影响检索准确率。

切块类似图书馆整理书籍：不将整本书视为一个标签，而是按章节、小节分别标注，以便读者直接找到具体知识点所在页面。

**Step 3：向量化（Embedding）**

这是 RAG 中最关键的一步。每个切好的 chunk 通过一个「Embedding 模型」转化为一串数字，这串数字称为 **向量（Vector）**。

这串数字编码了这段文字的 **语义含义**。语义相近的文字，转化后的向量在数学空间中距离相近。

类比城市坐标：每个城市有经度和纬度，北京约北纬 40°、东经 116°；天津约北纬 39°、东经 117°，两组坐标接近，表明两座城市相邻。广州约北纬 23°、东经 113°，坐标差异大，与北京距离远。

向量即为文字的「语义坐标」。「数据库响应慢」与「查询性能问题」虽词语不同，但语义相近，其向量在空间中也相邻；而「数据库响应慢」与「今天天气不错」语义不相关，向量距离较远。

**Step 4：存入向量数据库**

转化后的向量及对应原文一同存入向量数据库（如 Milvus、Pinecone、Weaviate 等）。向量数据库专门优化了「在海量向量中寻找最近邻」的操作，能在几毫秒内从百万级向量中找出最相似的几条。

***

### 在线阶段

每次用户提问时实时触发以下四步：

![](<attachments/什么是 RAG？-442c6cd39f19bfc5d5b47040ec7d6c30.png>)

**Step 1：问题向量化**

使用同一 Embedding 模型，将用户问题也转化为向量。

**Step 2：语义搜索**

使用问题的向量，在向量数据库中查找「最相似的几个 chunk 的向量」，即语义搜索。找到后，取出对应的原文 chunk，通常取 3-5 个最相关的片段。

注意，此处并非查找「包含相同关键词」的内容，而是「语义最相近」的内容。这是语义搜索与关键词搜索的本质区别。

**Step 3：构造增强 Prompt**

将检索到的几段原文与用户原始问题拼接，形成增强后的 Prompt：

```json
以下是相关背景资料：

[检索到的 chunk 1]

[检索到的 chunk 2]

[检索到的 chunk 3]

根据以上资料，请回答：[用户的原始问题]
```

**Step 4：大模型生成回答**

将该 Prompt 发送给大模型，大模型基于提供的背景资料生成有据可查的精准回答。

## 五、关键概念再讲透：语义搜索与关键词搜索的差异

此处重点讲解语义搜索，因为它是 RAG 工作的核心，也最容易混淆。

**传统关键词搜索（如 SQL 的 LIKE 查询）**：逐字匹配，搜索「数据库慢」时，会查找包含「数据库慢」这几个字的文档，找不到则返回空。若文档中写的是「query performance degradation」或「查询响应时间过长」，关键词搜索无法匹配，即使表达同一含义。

**语义搜索**：查找意思相近的内容，不要求字面相同。搜索「数据库慢」时，语义搜索能定位到「查询性能问题」「SQL 响应延迟」「慢查询优化」等片段，因为这些片段的向量距离近，语义相关。

再举一个对比示例：

| 用户的问题   | 文档里的原文                               | 关键词搜索能否找到？ | 语义搜索能否找到？ |
| ------- | ------------------------------------ | ------------ | ------------ |
| 数据库连接失败 | connection pool exhausted            | ✗（无相同关键词）   | ✓（语义相关）     |
| 如何重启服务  | service restart procedure            | ✗            | ✓            |
| 昨晚报警原因  | 2024-01-15 23:00 alert: high latency | ✗            | ✓（若时间匹配）    |

语义搜索使 RAG 能真正「理解」问题，而非机械地匹配字符串。这也是 RAG 系统检索准确率通常远高于普通关键词搜索的原因。

## 七、RAG 在 Agent 中的定位

学习 RAG 原理后，可能会问：它与我们之前学习的 Agent、MCP、Function Calling 有何关系？

答案非常简单：**RAG 本质上就是一个特殊工具**。

回顾 Agent 章节：Agent = 大模型（大脑）+ 工具（双手）+ 执行循环。「查询知识库」这一动作被封装为 Agent 中的一个 Tool。

当 Agent 接到需要私有知识的任务时，大模型通过 Function Calling 发出「调用知识库检索工具，查询：XXX」的指令，Agent 执行工具调用，触发 RAG 的在线流程，检索结果回传给大模型，大模型据此继续推理。

这正是之前预告 RAG 时所说的：**「将知识库检索封装成工具」**。

## 八、对比表：无 RAG 与有 RAG

| 对比维度   | 无 RAG                    | 有 RAG                             |
| -------- | ------------------------- | ---------------------------------- |
| 私有数据访问 | 无法访问，模型仅具备通用知识         | 可访问，基于私有知识库生成回答               |
| 知识更新   | 需重新训练模型，周期长且成本高        | 更新文档后重新建库即可，快速生效              |
| Token 消耗 | 要么全量塞入（超限），要么放弃        | 仅召回相关片段，Token 消耗极低            |
| 回答准确性  | 依赖训练数据，私有领域易编造         | 基于检索到的真实文档，有据可查              |
| 可追溯性   | 无法获知回答依据                | 每个回答均可附带来源文档                 |
| 扩展性    | 知识库扩大需重新训练              | 直接向向量数据库添加数据即可               |

## 总结

整理本章核心认知：

* **RAG 是什么**：Retrieval-Augmented Generation，检索增强生成。先从知识库中找到相关内容，再将内容加入 Prompt，使大模型基于私有数据生成有据可查的回答。

* **为什么需要它**：大模型知识静态、封闭，而业务数据动态、私有。全量数据塞入 Prompt 不可行，受限于 token 上限、成本高、注意力稀释。RAG 通过「按需检索 + 动态注入」绕开此困境。

* **两大阶段**：离线阶段建立知识库（加载→切块→向量化→存库），在线阶段查询生成（问题向量化→语义搜索→构造增强 Prompt→大模型生成回答）。

* **向量化与语义搜索**：文字转化为代表语义的数字坐标（向量），语义相近的内容向量距离近。语义搜索不依靠关键词匹配，而依赖语义相似度，能发现「意思相关但词语不同」的内容。

* **在 Agent 中的定位**：RAG 即一个特殊工具，「检索知识库」被封装为一次 Function Call，是 Agent 能力体系的重要组成部分。
