### 📌 本章重点总结（RAG）

1. **RAG 是什么**：Retrieval-Augmented Generation（检索增强生成）。先检索私有知识库中最相关的内容，再将其注入 Prompt，让大模型基于有据可查的资料生成回答。
2. **为什么需要 RAG**：大模型知识静态、封闭（截止日期、无私有数据、无实时数据），全量塞入 Prompt 受限于上下文窗口、成本高、注意力稀释。RAG 实现“按需检索 + 动态注入”。
3. **核心思路**：不把所有数据都塞进 Prompt，而是每次回答前，先从知识库中检索最相关的几段内容，再将这几段注入 Prompt。
4. **两大阶段**：
   - **离线建库**：加载文档 → 文本切块（Chunking）→ 向量化（Embedding）→ 存入向量数据库。
   - **在线检索生成**：问题向量化 → 语义搜索（取最相似 chunk）→ 构造增强 Prompt → 大模型生成回答。
5. **关键概念**：
   - **向量（Vector）**：文字的“语义坐标”，语义相近的内容向量距离近。
   - **语义搜索**：不依赖关键词匹配，而是通过向量相似度找到意思相关的内容，即使词语不同也能召回。
6. **RAG 在 Agent 中的位置**：RAG 本质上是一个特殊的“知识库检索工具”，通过 Function Calling 被 Agent 调用，成为 Agent 能力体系的一部分。
7. **对比优势**：可访问私有数据、知识更新快（更新文档即生效）、Token 消耗低、回答有据可查、扩展性好。

---

前几章我们搭建了 Agent 的工具体系：Function Calling 让大模型能开口下指令，MCP 让工具标准化接入，Skills 让专业知识按需加载。至此，Agent 能执行任务了，工具也能正常运转。

但有一个根本问题，前几章都没有正面回答：**大模型看不到你的私有数据，该怎么办？**

例如，公司内部有几千页运维手册、几百个历史故障报告、一套只有内部才知道的排查 SOP，这些大模型从未见过。让它做 OnCall 排查，它只能给出通用思路，却无法给出针对你们系统的精准答案。

这就是 **RAG** 要解决的核心问题。

## 一、大模型为什么「看不到」你的数据？

先理清问题，有三类「看不到」，原因各不相同。

![](<attachments/什么是 RAG？-36e920b9eec4dde61012702484969045.png>)

**第一类：知识截止日期**

大模型基于历史数据训练，训练完成后知识便冻结。例如 Claude 的训练数据截止到 2025 年某时间点，之后的事情它一概不知。如果问“我们系统今天凌晨发生了什么故障”，它没有这份信息，只能瞎猜。

**第二类：私有数据**

公司的内部文档、产品设计方案、运维手册、客服问答库等保密内容，不会出现在训练数据中。模型从未见过，自然无法据此回答。

**第三类：实时数据**

刚写完的技术方案、刚产生的 bug 日志、刚更新的配置文件，这些动态变化的内容，即使模型更新训练数据也来不及追赶。Agent 需要访问的，往往正是这类“最新鲜”的数据。

三类问题的共同点：**大模型的知识是静态、封闭的，而业务数据是动态、私有的**。

---

## 二、暴力解法为什么行不通？

遇到这个问题，许多人的第一反应是：**直接把数据塞进 Prompt 里不就行了？**

听起来直接，但方案有三个致命问题。

**问题一：Context Window 有上限**

大模型一次能处理的文本有限，这个限制称为 Context Window（上下文窗口）。即便是当前最大的模型，一次也只能处理几十万 token，换算成中文约几十万汉字。

公司内部文档可能有几百个文件，仅运维手册就几十万字符，根本塞不进去；更别提几千个历史工单的故障数据库。

**问题二：费钱又慢**

Token 需要成本。塞入 10 万 token 背景资料，每次提问都要消耗这些 token 的费用。一天询问数百次，成本迅速上升。而且 token 越多，模型推理越慢，用户等待时间越长。

**问题三：注意力稀释**

这是最容易被忽视的问题。大模型处理长上下文时，注意力会被稀释，相关内容埋藏在几万字的信息中，模型难以聚焦，反而表现变差。塞入越多，有时回答质量反而越低。

---

## 三、RAG 的核心思路：先检索，再回答

直接塞数据行不通，那么 RAG 如何解决？

核心思路非常简单，一句话即可说明：

**不把所有数据塞入 Prompt，而是在每次回答前，先去找到最相关的那几段，再将这些段塞入 Prompt。**

![](<attachments/什么是 RAG？-a359fff0264c2cd81a17d249068fa360.png>)

这就是 RAG 名称的含义：

* **Retrieval（检索）**：从知识库中找出与当前问题最相关的内容。
* **Augmented（增强）**：将检索到的内容加入 Prompt，增强大模型的上下文。
* **Generation（生成）**：大模型基于增强后的上下文生成回答。

可以类比考试时查字典：不需要背整本字典，只需要知道去查哪个词，查到那一页，看完再写答案。

RAG 正是这个思路——大模型不需要“记住”所有知识，只需在需要时从知识库中检索相关内容，然后据此回答。

## 四、RAG 的两大阶段

RAG 的完整工作流程分为两个阶段：**离线建库** 和 **在线检索生成**。

![](<attachments/什么是 RAG？-97d0548d6a6f5b74a3ba238e84b646e6.png>)

离线建库是一次性准备工作（数据更新时重做），在线检索是每次用户提问时触发的实时流程。

### 离线阶段

这个阶段的目标是将私有数据处理成大模型能快速检索的格式，存入向量数据库。共四步：

![](<attachments/什么是 RAG？-9d45b0f41b7d675e798b88062c47f188.png>)

**Step 1：加载文档**

统一接入数据源：PDF 文档、Word 文件、Markdown 笔记、网页内容、数据库记录、代码文件等各类格式的数据，统一解析为纯文本。

**Step 2：文本切块（Chunking）**

拿到文本后，不能直接整篇存储，需要先切成小块。为什么要切？两个原因：一是文档可能很长，涉及多个主题，检索时可能只需要其中一个主题的内容；二是每个 chunk 要转化为向量存储，chunk 过长会导致向量无法精确代表核心含义，降低检索准确率。

切块类似于图书馆整理书籍：不是整本书一个标签，而是按章节、小节分别标注，这样读者想找某个具体知识点，能直接找到那几页，而无需翻阅整本书。

**Step 3：向量化（Embedding）**

这是 RAG 中最难理解的一步，重点说明。

每个切好的 chunk 通过一个“Embedding 模型”转化为一串数字，这串数字称为 **向量（Vector）**。

这串数字的奥妙在于：它编码了这段文字的 **语义含义**。意思相近的文字，转化出的向量在数学空间中距离也相近。

用城市坐标类比：每个城市有经度和纬度，北京约北纬 40°、东经 116°；天津约北纬 39°、东经 117°，坐标接近，在地图上两城相邻。广州约北纬 23°、东经 113°，坐标差异大，与北京相距甚远。

向量就是文字的“语义坐标”。“数据库响应慢”和“查询性能问题”虽然词语不同，但语义相近，转化出的向量在空间中也邻近；而“数据库响应慢”和“今天天气不错”意思不相关，向量距离很远。

**Step 4：存入向量数据库**

转化好的向量连同对应原文，一起存入向量数据库（如 Milvus、Pinecone、Weaviate 等）。向量数据库专门优化了“在海量向量中找最近邻”的操作，能在几毫秒内从百万级向量中找出最相似的几个。

### 在线阶段

每次用户提问，实时触发以下四步：

![](<attachments/什么是 RAG？-442c6cd39f19bfc5d5b47040ec7d6c30.png>)

**Step 1：问题向量化**

使用同一个 Embedding 模型，将用户的问题也转化为向量。

**Step 2：语义搜索**

用问题的向量到向量数据库中寻找“最相似的几个 chunk 的向量”，这就是语义搜索。找到后，取出对应的原文 chunk，通常取 3-5 个最相关的片段。

注意，这里寻找的不是“包含相同关键词”的内容，而是“语义最相近”的内容。这是语义搜索与关键词搜索的本质区别。

**Step 3：构造增强 Prompt**

将检索到的几段原文与用户原始问题组合成增强后的 Prompt：

```json
以下是相关背景资料：

[检索到的 chunk 1]

[检索到的 chunk 2]

[检索到的 chunk 3]

根据以上资料，请回答：[用户的原始问题]
```

**Step 4：大模型生成回答**

将此 Prompt 发送给大模型，模型基于提供的背景资料生成有据可查的精准回答。

## 五、关键概念再讲透：语义搜索和关键词搜索的差别

这里展开说明语义搜索，因为这是 RAG 能工作的核心，也是最容易混淆的地方。

**传统关键词搜索（如 SQL 的 LIKE 查询）**：逐字匹配。搜索“数据库慢”，就找包含“数据库慢”这几个字的文档，找不到则返回空。如果文档中写的是“query performance degradation”或“查询响应时间过长”，关键词搜索无法找到，即使说的是同一件事。

**语义搜索**：寻找意思相近的内容，不要求字面相同。搜索“数据库慢”，语义搜索能找到“查询性能问题”“SQL 响应延迟”“慢查询优化”等片段，因为它们的向量距离近，语义相关。

再举一个对比示例：

| 用户的问题   | 文档里的原文                               | 关键词搜索能否找到？ | 语义搜索能否找到？ |
| ------- | ------------------------------------ | ------------ | ------------ |
| 数据库连接失败 | connection pool exhausted            | ✗（无相同关键词）   | ✓（语义相关）     |
| 如何重启服务  | service restart procedure            | ✗            | ✓            |
| 昨晚报警原因  | 2024-01-15 23:00 alert: high latency | ✗            | ✓（若时间对应）    |

语义搜索让 RAG 能真正“理解”问题，而不只是机械地匹配字符串。这也是 RAG 系统的检索准确率通常高于关键词搜索的原因。

## 七、RAG 在 Agent 里处于什么位置？

学完 RAG 原理后，可能会问：它和之前学习的 Agent、MCP、Function Calling 是什么关系？

答案很简单：**RAG 本质上就是一个特殊的工具**。

回忆 Agent 章节的内容：Agent = 大模型（大脑）+ 工具（双手）+ 执行循环。“查询知识库”这个动作被封装为 Agent 中的一个 Tool。

当 Agent 接到需要私有知识的任务时，大模型通过 Function Calling 下达“调用知识库检索工具，查询：XXX”的指令，Agent 执行此工具调用，触发 RAG 的在线流程，检索结果回传给大模型，大模型基于检索结果继续推理。

这正是 MCP 和 Agent 章节中预告 RAG 时所说的：**“将知识库检索封装成工具”**。

## 八、一张表看懂：没有 RAG vs 有 RAG

| 对比维度     | 没有 RAG          | 有 RAG               |
| -------- | --------------- | ------------------- |
| 私有数据访问   | 无法访问，模型只有通用知识   | 可以访问，基于私有知识库生成回答    |
| 知识更新     | 需重新训练模型，慢且昂贵    | 更新文档重新建库即可，快速生效     |
| Token 消耗 | 要么全量塞入（超限），要么放弃 | 仅召回相关几段，Token 消耗极低 |
| 回答准确性    | 依赖训练数据，私有领域容易杜撰 | 基于检索到的真实文档，有据可查     |
| 可追溯性     | 无法知道回答依据         | 每个回答可附带来源文档         |
| 扩展性      | 知识库扩大需重新训练      | 直接向向量数据库添加数据即可      |

## 总结

整理本章核心认知：

* **RAG 是什么**：检索增强生成。先从知识库中找到相关内容，再将这些内容加入 Prompt，让大模型基于私有数据生成有据可查的回答。

* **为什么需要它**：大模型知识静态、封闭，业务数据动态、私有。将数据全量塞入 Prompt 不可行——超 token 限制、费用高、注意力分散。RAG 通过“按需检索 + 动态注入”绕开此困境。

* **两大阶段**：离线阶段建知识库（加载→切块→向量化→存库），在线阶段查询生成（问题向量化→语义搜索→构造增强 Prompt→大模型生成回答）。

* **向量化和语义搜索**：文字转化为代表语义的数字坐标（向量），语义相近的内容向量距离近。语义搜索不靠关键词匹配，依靠语义相似度，能找出“意思相关但词语不同”的内容。

* **在 Agent 里的位置**：RAG 是一个特殊的工具，“检索知识库”被封装成一次 Function Call，是 Agent 能力体系的重要组成部分。
