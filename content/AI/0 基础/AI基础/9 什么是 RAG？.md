### 📌 本章重点总结（RAG）

1. **RAG 是什么**：Retrieval-Augmented Generation（检索增强生成）。先检索私有知识库中最相关的内容，再将其注入 Prompt，让大模型基于有据可查的资料生成回答。
2. **为什么需要 RAG**：大模型知识静态、封闭（截止日期、无私有数据、无实时数据），全量塞入 Prompt 受限于上下文窗口、成本高、注意力稀释。RAG 实现“按需检索 + 动态注入”。
3. **核心思路**：不把所有数据都塞进 Prompt，而是每次回答前，先从知识库中检索最相关的几段内容，再将这几段注入 Prompt。
4. **两大阶段**：
   - **离线建库**：加载文档 → 文本切块（Chunking）→ 向量化（Embedding）→ 存入向量数据库。
   - **在线检索生成**：问题向量化 → 语义搜索（取最相似 chunk）→ 构造增强 Prompt → 大模型生成回答。
5. **关键概念**：
   - **向量（Vector）**：文字的“语义坐标”，语义相近的内容向量距离近。
   - **语义搜索**：不依赖关键词匹配，而是通过向量相似度找到意思相关的内容，即使词语不同也能召回。
6. **RAG 在 Agent 中的位置**：RAG 本质上是一个特殊的“知识库检索工具”，通过 Function Calling 被 Agent 调用，成为 Agent 能力体系的一部分。
7. **对比优势**：可访问私有数据、知识更新快（更新文档即生效）、Token 消耗低、回答有据可查、扩展性好。

***
前几章把 Agent 的工具体系搭清楚了：Function Calling 让大模型能开口下指令，MCP 让工具标准化接入，Skills 让专业知识按需加载。到这里，Agent 能干活了，工具也能跑起来了。

但有一个根本问题，前面几章都没正面回答： **大模型看不到私有数据，怎么办？**

公司内部有几千页运维手册、几百个历史故障报告、一套只有内部才知道的排查 SOP，这些大模型从未见过。让它做 OnCall 排查，它能给出很通用的思路，但无法针对系统给出精准答案。

这就是 **RAG** 要解决的核心问题。

***

## 一、大模型为什么「看不到」数据？

先把问题说清楚，有三类「看不到」，每类原因不同。

![](<什么是 RAG？-36e920b9eec4dde61012702484969045.png>)

**第一类：知识截止日期**

大模型用历史数据训练，训练后知识冻结。例如训练数据截止到某个时间点，之后发生的事一概不知。询问「系统今天凌晨发生了什么故障」，它没有信息，只能瞎猜。

**第二类：私有数据**

内部文档、产品设计方案、运维手册、客服问答库等都保密，不会出现在训练数据中。模型从未见过，自然无法据此回答。

**第三类：实时数据**

刚写完的技术方案、刚产生的 bug 日志、刚更新的配置文件，动态变化，即便模型更新训练数据也追不上。Agent 需要访问的往往是这些「最新鲜」的数据。

三类问题的共同点： **大模型的知识静态封闭，但业务数据动态私有**。

***

## 二、暴力解法为什么行不通？

遇到这个问题，很多同学第一反应是： **直接把数据塞进 Prompt 不就行了？**

听起来直接，但这个方案有三个致命问题。

**问题一：Context Window 有上限**

大模型一次能处理的文本有限，这个限制叫 Context Window（上下文窗口）。目前最大的模型一次也只能处理几十万 token，换算成中文约几十万字。

内部文档可能有几百个文件，仅运维手册就几十万字，根本塞不进去。更别提有几千个历史工单的故障数据库。

**问题二：费钱又慢**

Token 是要花钱的。塞入 10 万 token 的背景资料，每次提问都要耗费相应 token。一天问几百次，成本直接爆炸。而且 token 越多，模型推理越慢，用户等待时间越长。

**问题三：注意力稀释**

这是最容易被忽视的问题。大模型处理长上下文时，注意力会被稀释，相关内容埋在数万字的堆料里，模型很可能找不到重点，表现反而变差。塞入越多，有时回答质量越低。

***

## 三、RAG 的核心思路：先检索，再回答

直接塞数据行不通，RAG 如何解决？

核心思路非常简单，一句话就能说明白：

**不把所有数据都塞进 Prompt，而是在每次回答之前，先去找到最相关的那几段，再把这几段塞进 Prompt。**

![](<什么是 RAG？-a359fff0264c2cd81a17d249068fa360.png>)

这就是 RAG 名字的含义：

* **Retrieval（检索）**：从知识库里找出与当前问题最相关的内容。
* **Augmented（增强）**：把检索到的内容加进 Prompt，增强大模型的上下文。
* **Generation（生成）**：大模型基于增强后的上下文生成回答。

打个考试查字典的比方：考试时不需要把整本字典背下来，只需知道去字典里查哪个词，查到那页，看完再写答案。

RAG 就是这个思路，大模型不需要「记住」所有知识，只需在需要时从知识库检索相关内容，然后基于这些内容回答。

***

## 四、RAG 的两大阶段

RAG 的整个工作流程分两个阶段： **离线建库** 和 **在线检索生成**。

![](<什么是 RAG？-97d0546d6a6f5b74a3ba238e84b646e6.png>)

离线建库是一次性准备工作（数据更新时重做），在线检索是每次用户提问时触发的实时流程。

### 离线阶段

目标是把私有数据处理成大模型能快速检索的格式，存进向量数据库。共四步：

![](<什么是 RAG？-9d45b0f41b7d675e798b88062c47f188.png>)

**Step 1：加载文档**

把数据源统一接入：PDF 文档、Word 文件、Markdown 笔记、网页内容、数据库记录、代码文件等，统一解析成纯文本。

**Step 2：文本切块（Chunking）**

拿到文本后不能直接整篇存储，需先切成小块。原因有二：一篇文档几千字涉及多个主题，检索时可能只需其中一个主题，无需召回整篇；每个 chunk 要转化为向量存储，chunk 太长，向量无法精确代表那段文字的核心含义，检索准确率会下降。

切块好比图书馆整理书籍：不是整本书放一个标签，而是按章节、小节分别标注，读者想找某个知识点能直接找到那几页，而不必翻整本书。

**Step 3：向量化（Embedding）**

这是 RAG 中较难理解的一步，重点展开。

切好的每个 chunk 通过一个「Embedding 模型」转化成一串数字，这串数字称为 **向量（Vector）**。

这串数字编码了这段文字的 **语义含义**。意思相近的文字，转化出的向量在数学空间里距离也相近。

类比城市坐标：每个城市有经度纬度，北京约北纬 40°、东经 116°；天津约北纬 39°、东经 117°，两组数字接近，地图上两城相邻。广州北纬 23°、东经 113°，坐标差别大，与北京相距甚远。

向量就是文字的「语义坐标」，「数据库响应慢」和「查询性能问题」虽然词语不同但意思相近，转化出的向量在空间里也挨着；而「数据库响应慢」与「今天天气不错」意思毫不相关，向量距离很远。

**Step 4：存入向量数据库**

转化好的向量连同对应原文一起存入向量数据库（如 Milvus、Pinecone、Weaviate 等）。向量数据库专门优化了「在海量向量里找最近邻」操作，能在几毫秒内从百万级向量中找出最相似的几条。

***

### 在线阶段

每次用户提问，实时触发以下四步：

![](<什么是 RAG？-442c6cd39f19bfc5d5b47040ec7d6c30.png>)

**Step 1：问题向量化**

用同一个 Embedding 模型，把用户问题也转化为向量。

**Step 2：语义搜索**

拿着问题的向量，去向量数据库里找「最相似的几个 chunk 的向量」，即语义搜索。找到后取出对应的原文 chunk，通常取 3-5 个最相关的片段。

注意，这里找的不是「包含相同关键词」的内容，而是「语义最相近」的内容。这是语义搜索与关键词搜索的本质区别。

**Step 3：构造增强 Prompt**

把检索回来的几段原文，加上用户原始问题，拼成一个增强后的 Prompt：

```json
以下是相关背景资料：

[检索到的 chunk 1]

[检索到的 chunk 2]

[检索到的 chunk 3]

根据以上资料，请回答：[用户的原始问题]
```

**Step 4：大模型生成回答**

将该 Prompt 发给大模型，大模型基于提供的背景资料生成有据可查的精准回答。

## 五、关键概念再讲透：语义搜索与关键词搜索的差别

这里展开说一下语义搜索，因为这是 RAG 能工作的核心，也是最容易混淆的地方。

**传统关键词搜索（如 SQL 的 LIKE 查询）**：逐字匹配。搜索「数据库慢」，就找包含「数据库慢」这几个字的文档，找不到就返回空。如果文档里写的是「query performance degradation」或「查询响应时间过长」，关键词搜索就找不到，哪怕说的是同一件事。

**语义搜索**：找意思相近的，不要求字面相同。搜索「数据库慢」，语义搜索能找到「查询性能问题」「SQL 响应延迟」「慢查询优化」等片段，因为它们的向量距离近，语义上相关。

再举一个对比例子：

| 用户的问题   | 文档里的原文                               | 关键词搜索能找到？  | 语义搜索能找到？   |
| ------- | ------------------------------------ | ---------- | ---------- |
| 数据库连接失败 | connection pool exhausted            | ✗（无相同关键词） | ✓（语义相关）    |
| 如何重启服务  | service restart procedure            | ✗          | ✓          |
| 昨晚报警原因  | 2024-01-15 23:00 alert: high latency | ✗          | ✓（若时间能对上） |

语义搜索让 RAG 能真正「理解」问题，而不只是机械地找字符串。这也是为什么 RAG 系统的检索准确率通常比普通关键词搜索高得多。

## 七、RAG 在 Agent 里的位置

学完 RAG 原理后可能会问：它和 Agent、MCP、Function Calling 是什么关系？

非常简单： **RAG 本质上就是一个特殊的工具**。

回顾 Agent 章节：Agent = 大模型（大脑）+ 工具（双手）+ 执行循环。「查询知识库」这个动作被封装成 Agent 里的一个 Tool。

当 Agent 接到需要私有知识的任务，大模型通过 Function Calling 下达「调用知识库检索工具，查询：XXX」的指令，Agent 执行该工具调用，触发 RAG 的在线流程，检索结果回传给大模型，大模型基于检索结果继续推理。

这就是在 MCP 和 Agent 中预告 RAG 时说的： **「把知识库检索封装成工具」**。

## 八、一张表看懂：没有 RAG vs 有 RAG

| 对比维度     | 没有 RAG          | 有 RAG               |
| -------- | --------------- | ------------------- |
| 私有数据访问   | 无法访问，模型只有通用知识   | 可访问，基于私有知识库生成回答    |
| 知识更新     | 需重新训练模型，慢且贵    | 更新文档重新建库即可，快速生效     |
| Token 消耗 | 要么全量塞入（超限）或放弃 | 只召回相关几段，token 消耗极低 |
| 回答准确性    | 依赖训练数据，私有领域易瞎编 | 基于检索到的真实文档，有据可查     |
| 可追溯性     | 无法知道回答依据是什么     | 每个回答可附上来源文档       |
| 扩展性      | 知识库扩大=重新训练    | 直接往向量数据库里加数据即可      |

## 总结

整理核心认知：

* **RAG 是什么**：Retrieval-Augmented Generation，检索增强生成。先从知识库找到相关内容，再将其加进 Prompt，让大模型基于私有数据生成有据可查的回答。

* **为什么需要它**：大模型的知识静态封闭，而业务数据动态私有。全量塞入 Prompt 行不通——超 token 限制、费钱、注意力稀释。RAG 用「按需检索 + 动态注入」绕开此困境。

* **两大阶段**：离线阶段建知识库（加载→切块→向量化→存库），在线阶段查询生成（问题向量化→语义搜索→构造增强 Prompt→大模型生成回答）。

* **向量化和语义搜索**：文字转化为代表语义的数字坐标（向量），语义相近的内容向量距离近。语义搜索不靠关键词匹配，靠语义相似度，能找到「意思相关但词语不同」的内容。

* **在 Agent 里的位置**：RAG 就是一个特殊工具，「检索知识库」被封装成一次 Function Call，是 Agent 能力体系的重要组成部分。
