![](什么是向量数据库？-e3e2c7b799cc5b65291a9c49d28398fe.png)

你可能会疑惑：**为什么要专门用向量数据库？MySQL 不能存储吗？**

本章就来详细解答这个问题。

***

## 一、先别急，普通数据库能否存储向量？

能存储，但存在一个很大问题。

普通数据库存储向量并无难度——向量本质上是一串浮点数，MySQL 中创建一个字段来存储完全可行。

真正的难点在于 **查询**。

***

## 二、普通数据库为什么难以查询向量？

我们先看 MySQL 是如何查询数据的。

执行 `SELECT * FROM users WHERE id = 5`，MySQL 利用 B+ 树索引，经过几次跳转即可快速定位。执行 `WHERE age > 18`，同样走索引进行范围扫描，速度也很快。

MySQL 的索引本质上针对两类操作优化：**精确匹配** 和 **范围比较**。

![](什么是向量数据库？-687e8c304aaf094fd4232c28efc12a82.png)

但向量搜索是完全不同的需求。

向量搜索要做的是：**给定一个向量，找出与其最相似的 top-k 个向量**。

「最相似」意味着需要计算距离（如余弦相似度、欧氏距离等），即拿着查询向量，与库中每一条向量逐一计算距离，然后排序，取最小的几个。

MySQL 的 B+ 树索引对此完全无能为力——它无法在多维空间中寻找「最近邻」。

**那么，进行暴力遍历呢？**

我们来感受一下规模。

假设使用某个常见的文本嵌入模型，每个 chunk 转化后的向量维度为 **1536 维**。如果你的知识库有 100 万条 chunk，那么每次查询需要进行的浮点运算量为：

1536 维 × 100 万条 = 15.36 亿次浮点运算

这仅仅是计算距离这一步。每次用户提问，都需要触发这个计算量，普通数据库完全无法承受。

当数据量增长到 1 亿条时，浮点运算量达到 1536 亿次，一次查询可能耗费数秒，完全不可用。

**总结：普通数据库可以存储向量，但完全没有对向量相似度查询进行优化，数据量一上去就崩溃了。**

***

## 三、向量数据库是什么

向量数据库正是为解决这个问题而设计的——**在海量向量中，毫秒级找到最相似的 top-k 条**。

![](什么是向量数据库？-4959b38811f55e10e4471089570f9f10.png)

它存储的内容与普通数据库类似：向量 + 对应的原文（元数据）。但它的核心在于专为向量搜索设计的索引结构，能够将上述「15.36 亿次浮点运算」的暴力遍历优化到几十毫秒甚至几毫秒完成。

关键问题来了：**它是如何做到的？**

***

## 四、向量数据库如何实现「又快又准」

秘诀在于 **ANN（Approximate Nearest Neighbor，近似最近邻）** 搜索。

注意关键词：**近似**。

向量数据库并不保证找到绝对最相似的几条，而是找到「大致最相似的」几条，用精度换取速度。但在实际场景中，近似结果与精确结果的效果几乎没有区别，因为语义检索本身并不要求绝对精确。

那么它使用什么算法？目前最主流的是 **HNSW**（Hierarchical Navigable Small World，分层可导航小世界图）。

![](什么是向量数据库？-9db6e67886233db2fc10dd6c57c47bce.png)

名称虽复杂，但原理用一个例子就能讲清楚。

### 图书馆的多级目录类比

假设你去一个大图书馆，想找一本叫《MySQL 索引优化》的书。

**笨方法**：从第一排书架的第一本书开始，一本一本翻阅，直到找到。面对 100 万本书的图书馆，这将会耗费大量时间。

**图书馆的实际做法**：

* 第一步，查看大类目录牌：理工科 → 计算机科学 → 数据库技术。三步跳转，已排除 90% 的书架区域。
* 第二步，查看中类目录：性能优化 → 索引与查询。再两步，进一步缩小范围。
* 第三步，直接在这一小块书架上查找。扫几眼，拿到书。

整个过程不超过 2 分钟，而总共只检查了几十本书的标签，而非 100 万本。

**HNSW 就是这个逻辑。**

它将所有向量组织成一个多层的图结构：

* **高层（稀疏层）**：只有少量「节点」，每个节点连接着几个「邻居」。高层负责大范围的快速跳转，帮助你快速缩小搜索范围。
* **低层（稠密层）**：包含所有向量，用于精细定位最终近邻候选。

查询时，从高层入口进入，快速跳转几步找到大致区域，然后下到低层精细扫描。全程只需访问整个图的一小部分节点，而非全部节点。

结果：**牺牲极少量精度（通常召回率在 95% 以上），换来 100 倍以上的速度提升**。对于 100 万条向量，只需几毫秒即可完成查询。

## 五、主流向量数据库介绍

市面上已有多种向量数据库可选，这里介绍五个最常见的。

### Chroma

本地轻量级向量数据库，提供 Python 原生 API，几行代码即可运行，无需任何部署配置。

适用场景：**本地开发、功能验证、快速原型验证**。如果你想跑通 RAG 完整流程，Chroma 是摩擦最小的选择——安装 pip 包即可直接使用。

缺点：不适合生产环境，缺乏高可用、分布式等特性。

### Pinecone

全托管云向量数据库，由服务商负责所有基础设施（服务器、扩容、备份等），开发者只需调用 API。

适用场景：**快速上线，无需自己运维**。对于创业公司、小团队，希望将 RAG 功能上线但缺乏专职 DBA 的情况，Pinecone 是最快捷的路径。

缺点：数据存储在第三方，存在数据合规顾虑的场景不适合；按用量收费，规模较大时成本不低。

### Milvus

开源生产级向量数据库，功能最全，支持多种索引类型、分布式部署、数据持久化。背后有活跃的社区维护，文档完善。

适用场景：**私有化部署的生产环境**。对于数据不能出内网、需要精细控制、规模较大的场景，Milvus 是目前开源中功能最完整的选择。

缺点：部署和运维有一定复杂度，学习曲线较 Chroma 陡峭。

### Weaviate

开源向量数据库，特色在于内置了 Embedding 集成——可以直接将原始文本传入，Weaviate 自动调用嵌入模型将其转换为向量，无需自己处理。同时支持图片、音频等多模态数据。

适用场景：**需要多模态搜索，或希望简化嵌入步骤**的场景。

### Qdrant

使用 Rust 实现的高性能向量数据库，内存占用低，查询速度快，适合资源受限或高并发场景。接口设计简洁，支持 HTTP 和 gRPC。

适用场景：**对性能和资源消耗敏感**的生产环境，例如在有限硬件上运行大规模向量检索。

***

## 六、如何选择？

介绍了五个选项，该如何选择？给出一个明确的决策树：

**学习 / 构建原型 → 使用 Chroma**

零配置，pip 安装，几行代码即可跑通完整 RAG 流程。如果你正在学习 RAG，直接使用 Chroma，无需过多考虑。

**生产环境，不想管理运维 → 使用 Pinecone**

不想操心服务器、扩容、备份等工作，数据放在云上没有问题，Pinecone 拿来即用。

**生产环境，需要私有化部署 → 使用 Milvus 或 Qdrant**

数据必须部署在自己服务器上，选择这两个。团队有运维能力且需要最全功能，选 Milvus；对性能和资源敏感、希望部署更简单，选 Qdrant。

用厨房类比这四个选择：

* **Chroma**：家用厨房。够用、方便，无需专门装修，在家做饭首选。
* **Pinecone**：叫外卖。你只管点菜，后厨、配送、洗碗全不用管，但需支付外卖费。
* **Milvus**：专业餐厅厨房。功能齐全、可定制，但需要专业厨师管理。
* **Qdrant**：高效快餐厨房。出菜快、省资源，适合高并发大量出餐的场景。

## 七、普通数据库 vs 向量数据库

| 对比维度 | 普通数据库（MySQL） | 向量数据库（Milvus/Pinecone 等） |
| --------- | ----------------------- | -------------------------------- |
| 核心用途 | 结构化数据存储和精确查询 | 向量存储和相似度搜索 |
| 索引结构 | B+ 树（适合精确匹配/范围查询） | ANN 索引，如 HNSW（适合近邻搜索） |
| 查询类型 | id = 5、age > 18、LIKE 匹配 | 找 top-k 个最相似向量 |
| 向量相似度查询 | 不支持（只能暴力全表扫描） | 原生支持，毫秒级 |
| 百万级向量查询速度 | 数秒（暴力遍历，不可用） | 毫秒级（ANN 索引加速） |
| 数据形式 | 表格（行列结构） | 向量 + 元数据 |
| 适合 RAG 吗 | 可以存储，但查询效率很低 | 专为此场景设计 |

***

## 总结

本章的核心认知：

* **普通数据库可以存储向量，但完全没有对向量相似度查询进行优化**。百万级向量 + 高维（1536 维）的暴力遍历，每次查询涉及几十亿次浮点运算，根本无法运行。
* **向量数据库专为解决「海量向量中毫秒级找到最近邻」这个问题**，依靠的是 ANN 索引。
* **HNSW 是最主流的 ANN 索引**，核心思路是多层图结构：高层大范围快速跳转，低层精细定位，就像图书馆的多级目录，无需翻遍所有书就能找到目标区域。代价是牺牲极少量精度，换来 100 倍以上的速度提升。
* **选型建议**：学习用 Chroma，生产不想运维用 Pinecone，生产私有化部署用 Milvus 或 Qdrant。

理解了向量数据库，RAG 的离线建库链路就完整了：文档 → 切块 → 向量化 → **存入向量数据库**。
