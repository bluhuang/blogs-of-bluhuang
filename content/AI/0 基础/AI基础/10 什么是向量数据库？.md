## 一、先别急，普通数据库能存储向量吗？

能存，但有一个严重的问题。

在普通数据库中存放向量毫无难度——向量本质上是一串浮点数，MySQL 中建一个字段即可存储。

真正的困难在于**查询**。

---

## 二、为什么普通数据库无法高效查询向量？

我们先看看 MySQL 是如何查询数据的。

执行 `SELECT * FROM users WHERE id = 5`，MySQL 通过 B+ 树索引快速定位到目标行；执行 `WHERE age > 18` 时，同样利用索引进行范围扫描，效率极高。

MySQL 的索引结构主要针对两类操作优化：**精确匹配** 和 **范围比较**。

![](什么是向量数据库？-687e8c304aaf094fd4232c28efc12a82.png)

但向量搜索是完全不同的场景。

向量搜索需要完成的任务是：**给定一个向量，找出与它最相似的 top-k 个向量**。

“最相似”意味着需要计算距离——余弦相似度、欧氏距离等。这类计算需要将查询向量与库中每条向量逐一计算距离，然后排序，选出最小的几个。

MySQL 的 B+ 树索引对此无能为力，它无法在多维空间中寻找“最近邻”。

**那就只能暴力遍历了？**

让我们感受一下数据规模：

OpenAI 的 text-embedding-ada-002 模型，每个 chunk 转换后的向量维度是 **1536 维**。假设知识库中有 100 万条 chunk，那么每次查询所需的浮点运算量为：

1536 维 × 100 万条 = 15.36 亿次浮点运算

这仅仅是计算距离这一步骤。用户每次提问都需要触发这样的计算量，普通数据库根本无法承受。

当数据量增长到 1 亿条时，1536 亿次浮点运算的查询耗时可能达到数秒，完全不可用。

**总结：普通数据库存储向量没有问题，但在向量相似度查询方面完全没有优化，规模一上去就崩溃了。**

---

## 三、向量数据库是什么

向量数据库正是为解决这一问题而设计的——**在海量向量中，毫秒级找到最相似的 top-k 条**。

![](什么是向量数据库？-4959b38811f55e10e4471089570f9f10.png)

它存储的内容与普通数据库类似：向量 + 对应的原文（元数据）。但它的索引结构专门针对向量搜索进行了优化，能够将上述“15.36 亿次浮点运算”的暴力遍历，优化到几十毫秒甚至几毫秒完成。

关键问题是：**它是如何做到的？**

---

## 四、向量数据库如何实现“又快又准”

秘诀在于 **ANN（Approximate Nearest Neighbor，近似最近邻）** 搜索。

注意“近似”二字：向量数据库并不保证找到绝对最相似的几条，而是找到“差不多最相似的”几条，以精度换取速度。在实际场景中，“差不多最相似的”和“绝对最相似的”效果几乎没有区别，因为语义检索本身不需要那么精确。

那么它使用了什么算法？目前最主流的是 **HNSW**（Hierarchical Navigable Small World，分层可导航小世界图）。

![](什么是向量数据库？-9db6e67886233db2fc10dd6c57c47bce.png)

名字虽然复杂，但原理用一个例子就能讲清楚。

### 图书馆的多级目录类比

你去一个大图书馆，想找一本叫《MySQL 索引优化》的书。

**笨办法**：从第一排书架的第一本书开始，一本一本地翻，直到找到它。面对 100 万本书的图书馆，这种方法效率极低。

**图书馆的实际做法**：

* 第一步，看大类目录牌：理工科 → 计算机科学 → 数据库技术。三步跳转，就排除了 90% 的书架区域。
* 第二步，看中类目录：性能优化 → 索引与查询。再两步，进一步缩小范围。
* 第三步，直接在这一小块书架上寻找。扫几眼，就能拿到书。

整个过程不超过 2 分钟，而你总共只“看过”几十本书的标签，而不是 100 万本。

**HNSW 就是这样的逻辑。**

它将所有向量组织成一个多层的图结构：

* **高层（稀疏层）**：只有少量“节点”，每个节点连接着几个“邻居”。高层负责大范围的快速跳转，帮助快速缩小搜索范围。
* **低层（稠密层）**：包含所有向量，用于精细定位最终的近邻候选。

查询时，从高层入口进入，快速跳转几步找到大致区域，然后下到低层精细扫描。整个过程只访问图的一小部分节点，而不是全部节点。

结果是：**牺牲极少量精度（通常召回率在 95% 以上），换来 100 倍以上的速度提升**。对于 100 万条向量，查询可在几毫秒内完成。

## 五、主流向量数据库介绍

目前市面上已有多种向量数据库可供选择，下面介绍五个最常见的。

### Chroma

本地轻量级向量数据库，提供 Python 原生 API，几行代码即可运行，无需任何部署配置。

适用场景：**本地开发、功能验证、快速原型验证**。如果你只想跑通 RAG 的完整流程，Chroma 是最低摩擦的选择，安装一个 pip 包即可使用。

缺点：不适合生产环境，缺乏高可用、分布式等特性。

### Pinecone

全托管的云向量数据库，用户无需关心基础设施——服务器、扩容、备份全部由 Pinecone 处理，只需调用 API 即可。

适用场景：**快速上线，不想自行运维**。对于创业公司或小团队，希望将 RAG 功能部署到生产环境但缺少专职 DBA 时，Pinecone 是最快捷的路径。

缺点：数据存放在第三方，不适合有数据合规要求的场景；按用量收费，规模较大时成本不低。

### Milvus

开源的生产级向量数据库，功能最为全面，支持多种索引类型、分布式部署、数据持久化。由 Zilliz 公司（国产）维护，社区活跃，文档完善。

适用场景：**私有化部署的生产环境**。当数据不能出内网、需要精细控制、规模较大时，Milvus 是目前开源方案中功能最完整的选择。

缺点：部署和运维有一定复杂度，学习曲线比 Chroma 陡峭。

### Weaviate

开源向量数据库，特色在于内置 Embedding 集成——可以直接将原始文本丢进去，Weaviate 会自动调用 Embedding 模型将文本转为向量，无需自行处理。同时支持图片、音频等多模态数据。

适用场景：**需要多模态搜索，或者希望简化 Embedding 步骤**的场景。

### Qdrant

使用 Rust 实现的高性能向量数据库，内存占用低，查询速度快，适合资源受限或高并发场景。接口设计简洁，同时支持 HTTP 和 gRPC。

适用场景：**对性能和资源消耗敏感**的生产环境，例如在有限硬件上运行大规模向量检索。

## 六、如何选择？

以上介绍了五个数据库，该如何选择？这里提供一个明确的决策树：

**学习 / 搭建原型 → 使用 Chroma**

零配置，pip 安装，几行代码即可跑通完整 RAG 流程。如果你正在学习 RAG，直接使用 Chroma 即可，不必想得太多。

**生产环境，不想管理运维 → 使用 Pinecone**

不想操心服务器、扩容、备份等事务，数据放在云上也没有问题，Pinecone 拿来即用。

**生产环境，需要私有化部署 → 使用 Milvus 或 Qdrant**

数据必须存放在自有服务器上，选择这两个。团队有运维能力、需要最全面功能时选 Milvus；对性能和资源敏感、希望部署更简单时选 Qdrant。

用厨房来类比这四个选择：

* **Chroma**：家用厨房。够用，方便，无需专门装修，在家做饭的首选。
* **Pinecone**：叫外卖。你只管点菜，后厨、配送、洗碗全都不用管，只是需要支付外卖费。
* **Milvus**：专业餐厅厨房。功能齐全、可定制，但需要有专业厨师来管理。
* **Qdrant**：高效快餐厨房。出菜快、省资源，适合高并发大量出餐的场景。

## 七、普通数据库 vs 向量数据库

| 对比维度       | 普通数据库（MySQL）               | 向量数据库（Milvus / Pinecone 等） |
| ---------- | ---------------------------- | ---------------------------- |
| 核心用途       | 结构化数据存储和精确查询                 | 向量存储和相似度搜索                   |
| 索引结构       | B+ 树（适合精确匹配 / 范围查询）          | ANN 索引，如 HNSW（适合近邻搜索）      |
| 查询类型       | id = 5、age > 18、LIKE 匹配      | 查找 top-k 个最相似向量             |
| 向量相似度查询    | 不支持（只能暴力全表扫描）                | 原生支持，毫秒级                     |
| 百万级向量查询速度  | 数秒（暴力遍历，不可用）                 | 毫秒级（ANN 索引加速）               |
| 数据形式       | 表格（行列结构）                     | 向量 + 元数据                     |
| 是否适合 RAG | 存储可以，查询不行                    | 专为此场景设计                      |

## 总结

本章的核心认知：

* **普通数据库存储向量没有问题，但在向量相似度查询方面完全没有优化**。百万级向量加上高维（1536 维）的暴力遍历，每次查询涉及几十亿次浮点运算，根本无法运行。
* **向量数据库专门解决“在海量向量中毫秒级找到最近邻”的问题**，依靠的是 ANN 索引。
* **HNSW 是最主流的 ANN 索引**，其核心思想是多层图结构：高层大范围快速跳转，低层精细定位，就像图书馆的多级目录，无需翻遍所有书就能找到目标区域。代价是牺牲极少量精度，换来 100 倍以上的速度提升。
* **选型建议**：学习用 Chroma，生产环境不想运维用 Pinecone，生产环境需要私有化部署用 Milvus 或 Qdrant。

理解了向量数据库，RAG 离线建库的链路就完整了：文档 → 切块 → 向量化 → **存入向量数据库**。
