![](/images/AI/0%20%E5%9F%BA%E7%A1%80/AI%E5%9F%BA%E7%A1%80/%E4%BB%80%E4%B9%88%E6%98%AF%E5%90%91%E9%87%8F%E6%95%B0%E6%8D%AE%E5%BA%93%EF%BC%9F-e3e2c7b799cc5b65291a9c49d28398fe.png)

你可能会问： **为什么需要专门的向量数据库？MySQL 无法存储吗？**

本章将详细解答这个问题。

***

## 一、普通数据库能否存储向量？

可以，但存在显著问题。

普通数据库存储向量本身没有问题，向量本质上是一串浮点数，MySQL 中创建一个字段即可存储。

难点在于 **查询**。

***

## 二、普通数据库为何无法高效查询向量？

先来理解 MySQL 的数据查询方式。

执行 `SELECT * FROM users WHERE id = 5` 时，MySQL 利用 B+ 树索引，通过几次跳转即可快速定位。执行 `WHERE age > 18` 时，同样通过索引进行范围扫描，速度很快。

MySQL 的索引主要针对两类操作优化： **精确匹配** 和 **范围比较**。

![](/images/AI/0%20%E5%9F%BA%E7%A1%80/AI%E5%9F%BA%E7%A1%80/%E4%BB%80%E4%B9%88%E6%98%AF%E5%90%91%E9%87%8F%E6%95%B0%E6%8D%AE%E5%BA%93%EF%BC%9F-687e8c304aaf094fd4232c28efc12a82.png)

但向量搜索是完全不同的场景。

向量搜索的目标是： **给定一个向量，找出与之最相似的 top-k 个向量**。

“最相似”意味着需要计算距离，如余弦相似度、欧氏距离等。这类计算需要将查询向量与库中每个向量逐一计算距离，然后排序，筛选出最小的几个。

MySQL 的 B+ 树索引无法应对此类操作，它无法在多维空间中寻找“最近邻”。

**那么，采用暴力遍历呢？**

来看一个具体规模：

OpenAI 的 text-embedding-ada-002 模型将每个 chunk 转化为 **1536 维** 向量。若知识库包含 100 万条 chunk，每次查询的浮点运算量为：

1536 维 × 100 万条 = 15.36 亿次浮点运算

这仅计算距离这一步。每次用户提问都需要触发此计算量，普通数据库难以承受。

当数据量增至 1 亿条时，浮点运算量达到 1536 亿次，单次查询可能需要数秒，性能不可接受。

**总结：普通数据库可以存储向量，但查询向量相似度时缺乏优化，数据规模一旦增大就会性能崩溃。**

***

## 三、向量数据库的定义

向量数据库正是为解决此问题而设计的， **能够在海量向量中毫秒级找到最相似的 top-k 条**。

![](/images/AI/0%20%E5%9F%BA%E7%A1%80/AI%E5%9F%BA%E7%A1%80/%E4%BB%80%E4%B9%88%E6%98%AF%E5%90%91%E9%87%8F%E6%95%B0%E6%8D%AE%E5%BA%93%EF%BC%9F-4959b38811f55e10e4471089570f9f10.png)

它存储的内容与普通数据库类似：向量加上对应的原文（元数据）。但它具备专为向量搜索设计的索引结构，能够将“15.36 亿次浮点运算”的暴力遍历优化到几十毫秒甚至几毫秒完成。

关键问题在于： **它是如何实现的？**

***

## 四、向量数据库如何实现“快且准”

其核心是 **ANN（Approximate Nearest Neighbor，近似最近邻）** 搜索。

注意“近似”一词。

向量数据库并不保证找到绝对最相似的条目，而是找到“近似最相似”的条目，以精度换取速度。但在实际应用中，“近似最相似”与“绝对最相似”的效果差异微乎其微，因为语义检索本身不需要绝对精确。

常用的算法是 **HNSW**（Hierarchical Navigable Small World，分层可导航小世界图）。

![](/images/AI/0%20%E5%9F%BA%E7%A1%80/AI%E5%9F%BA%E7%A1%80/%E4%BB%80%E4%B9%88%E6%98%AF%E5%90%91%E9%87%8F%E6%95%B0%E6%8D%AE%E5%BA%93%EF%BC%9F-9db6e67886233db2fc10dd6c57c47bce.png)

名称复杂，但通过一个示例即可理解其原理。

### 图书馆的多级目录类比

假设你在一个大型图书馆中寻找一本名为《MySQL 索引优化》的书。

**低效方法**：从第一排书架的第一本书开始逐本翻阅，直到找到目标。面对 100 万本书的图书馆，此方法耗时极长。

**图书馆的实际做法**：

* 第一步，查看大类目录：理工科 → 计算机科学 → 数据库技术。三次跳转，已排除 90% 的书架区域。

* 第二步，查看中类目录：性能优化 → 索引与查询。再两次跳转，进一步缩小范围。

* 第三步，直接在指定区域浏览，迅速找到目标。

整个过程不超过 2 分钟，且仅查看了几十本书的标签，而非全部 100 万本。

**HNSW 采用类似逻辑。**

它将所有向量组织成多层图结构：

* **高层（稀疏层）**：仅包含少量“节点”，每个节点连接若干“邻居”。高层负责快速跳转，帮助缩小搜索范围。

* **低层（稠密层）**：包含所有向量，用于精细定位最终近邻候选。

查询时，从高层入口进入，快速跳转至大致区域，然后进入低层进行精细扫描。整个过程仅需访问图结构的一小部分节点，而非全部。

结果： **以极少的精度损失（通常召回率 95%+），换取 100 倍以上的速度提升**。对于 100 万条向量，查询可在几毫秒内完成。

## 五、主流向量数据库介绍

市场上已有多种向量数据库可选，以下介绍五个常见选择。

### Chroma

本地轻量级向量数据库，提供 Python 原生 API，几行代码即可运行，无需任何部署配置。

适用场景： **本地开发、功能验证、快速原型搭建**。若需快速运行 RAG 完整流程，Chroma 是摩擦最小的选择，只需安装 pip 包即可使用。

缺点：不适合生产环境，缺乏高可用、分布式等特性。

### Pinecone

全托管云向量数据库，无需管理基础设施，服务器、扩容、备份均由 Pinecone 负责，仅需调用 API。

适用场景： **快速上线，无需自行运维**。适合创业公司或小团队，希望快速将 RAG 功能投入生产但无专职 DBA 的情况。

缺点：数据存储在第三方，存在数据合规顾虑的场景不适用；按用量收费，规模较大时成本较高。

### Milvus

开源的生产级向量数据库，功能最全面，支持多种索引类型、分布式部署、数据持久化。由 Zilliz 公司（国产）维护，社区活跃，文档完善。

适用场景： **私有化部署的生产环境**。数据无法出内网、需要精细控制、规模较大的场景，Milvus 是目前开源中功能最完整的选择。

缺点：部署和运维有一定复杂度，学习曲线比 Chroma 陡峭。

### Weaviate

开源向量数据库，特色是内置 Embedding 集成功能，可直接将原始文本输入，Weaviate 自动调用 Embedding 模型将其转换为向量，无需手动处理。同时支持图片、音频等多模态数据。

适用场景： **需要多模态搜索或希望简化 Embedding 步骤** 的场景。

### Qdrant

基于 Rust 实现的高性能向量数据库，内存占用低，查询速度快，适合资源受限或高并发场景。接口设计简洁，支持 HTTP/gRPC。

适用场景： **对性能和资源消耗敏感** 的生产环境，例如在有限硬件上运行大规模向量检索。

***

## 六、如何选择？

面对五个选项，给出明确的决策标准：

**学习/原型开发 → 使用 Chroma**

零配置，pip 安装，几行代码即可运行完整 RAG 流程。当前正处于学习阶段，直接选用 Chroma。

**生产环境，无需运维 → 使用 Pinecone**

无需操心服务器、扩容、备份，数据可放置在云上，Pinecone 可直接使用。

**生产环境，需私有化部署 → 使用 Milvus 或 Qdrant**

数据必须部署在自有服务器上，选择这两个。若团队具备运维能力且需要最全功能，选择 Milvus；若对性能和资源敏感、希望部署更简单，选择 Qdrant。

以厨房类比：

* **Chroma**：家用厨房。够用，方便，无需专门装修，适合日常使用。

* **Pinecone**：叫外卖。只需点菜，后厨、配送、洗碗均无需操心，但需支付外卖费。

* **Milvus**：专业餐厅厨房。功能齐全、可定制，但需专业厨师管理。

* **Qdrant**：高效快餐厨房。出餐快、资源省，适合高并发大量出餐场景。

## 七、普通数据库与向量数据库对比

| 对比维度      | 普通数据库（MySQL）            | 向量数据库（Milvus/Pinecone…） |
| --------- | ----------------------- | ----------------------- |
| 核心用途      | 结构化数据存储和精确查询            | 向量存储和相似度搜索              |
| 索引结构      | B+ 树（适合精确匹配/范围查询）       | ANN 索引，如 HNSW（适合近邻搜索）   |
| 查询类型      | id = 5、age > 18、LIKE 匹配 | 找出 top-k 个最相似向量          |
| 向量相似度查询   | 不支持（仅能暴力全表扫描）           | 原生支持，毫秒级                |
| 百万级向量查询速度 | 数秒（暴力遍历，不可用）            | 毫秒级（ANN 索引加速）           |
| 数据形式      | 表格（行列结构）                | 向量 + 元数据                |
| 适合 RAG 吗  | 可存储，查询无法满足              | 专为此场景设计                |

***

## 总结

本章的核心要点：

* **普通数据库可以存储向量，但查询向量相似度时缺乏优化**。百万级向量与高维（1536 维）的暴力遍历，每次查询需数十亿次浮点运算，无法实际运行。

* **向量数据库专门解决“海量向量中毫秒级寻找最近邻”问题**，依赖 ANN 索引。

* **HNSW 是最主流的 ANN 索引**，核心思路是多层图结构：高层快速跳转，低层精细定位，类似图书馆的多级目录，无需翻阅所有书籍即可找到目标区域。通过牺牲极少量精度，换取 100 倍以上的速度提升。

* **选型建议**：学习阶段使用 Chroma，生产环境无需运维使用 Pinecone，生产环境需私有化部署使用 Milvus 或 Qdrant。

理解向量数据库后，RAG 的离线建库链路便完整了：文档 → 切块 → 向量化 → **存入向量数据库**。
