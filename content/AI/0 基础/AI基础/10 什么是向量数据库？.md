![](什么是向量数据库？-e3e2c7b799cc5b65291a9c49d28398fe.png)

你可能当时就想问： **为什么要专门用向量数据库？MySQL 不能存吗？**

这一章就来专门把这个问题讲清楚。

***

## 一、普通数据库能不能存向量？

能存，但存在一个很大的问题。

普通数据库存储向量本身没有问题，向量本质上是一串浮点数，MySQL 中建立一个字段来存放完全可行。

困难在于 **查询**。

***

## 二、为什么普通数据库无法高效查询向量？

先来看看 MySQL 是如何查询数据的。

执行 `SELECT * FROM users WHERE id = 5` ，MySQL 利用 B+ 树索引，经过几次跳转就能快速找到结果。执行 `WHERE age > 18` ，同样通过索引进行范围扫描，速度也很快。

MySQL 的索引主要针对两类操作进行了优化： **精确匹配** 和 **范围比较**。

![](什么是向量数据库？-687e8c304aaf094fd4232c28efc12a82.png)

但向量搜索完全是另一回事。

向量搜索要做的是： **给定一个向量，找出与之最相似的 top-k 个向量**。

“最相似”意味着需要计算距离，例如余弦相似度、欧氏距离……这类计算要求拿着查询向量，与库中每一条向量逐一计算距离，然后排序，选出最小的几个。

MySQL 的 B+ 树索引完全无法胜任这一任务。它不知道如何在高维空间中寻找“最近邻”。

**那能不能进行暴力遍历呢？**

让我们来感受一下规模：

某个常用的文本嵌入模型，每个文本块转化出的向量维度为 **1536 维**。假设知识库中有 100 万个文本块，那么每次查询需要进行的浮点运算量为：

1536 维 × 100 万条 = 15.36 亿次浮点运算

这还只是计算距离这一步。用户每次提问都需要触发这样的计算量，普通数据库根本无法承受。

如果数据量增加到 1 亿条呢？1536 亿次浮点运算，一次查询可能需要好几秒，完全不可用。

**总结：普通数据库可以存储向量，但在向量相似度查询上没有任何优化，数据规模一上去就会崩溃。**

***

## 三、向量数据库是什么

向量数据库就是专门为解决这一问题而设计的， **能在海量向量中，毫秒级找到最相似的 top-k 条**。

![](什么是向量数据库？-4959b38811f55e10e4471089570f9f10.png)

它存储的内容与普通数据库类似：向量 + 对应的原始文本（元数据）。但它的核心优势在于拥有专为向量搜索设计的索引结构，能把那个“15.36 亿次浮点运算”的暴力遍历，优化到几十毫秒甚至几毫秒完成。

关键问题是： **它是如何做到的？**

***

## 四、向量数据库如何实现“又快又准”

秘诀在于 **ANN（Approximate Nearest Neighbor，近似最近邻）** 搜索。

注意这个词： **近似**。

向量数据库并不保证找到绝对最相似的那几条，而是找出“差不多最相似的”几条，以牺牲少量精度换取大幅速度提升。在实际场景中，“差不多最相似的”和“绝对最相似的”效果几乎没有差别，因为语义检索本身就不需要完全精确。

那么它使用的是什么算法？目前最主流的是 **HNSW**（Hierarchical Navigable Small World，分层可导航小世界图）。

![](什么是向量数据库？-9db6e67886233db2fc10dd6c57c47bce.png)

名字听起来复杂，但原理用一个例子就能说清楚。

### 图书馆的多级目录类比

你走进一个大图书馆，想找一本名为《MySQL 索引优化》的书。

**笨方法**：从第一排书架的第一本书开始，一本一本地翻，直到找到它。面对 100 万本书的图书馆，这几乎不可行。

**图书馆的实际做法**：

* 第一步，查看大类目录牌：理工科 → 计算机科学 → 数据库技术。三步跳转，已经排除了 90% 的书架区域。

* 第二步，查看中类目录：性能优化 → 索引与查询。再两步，进一步缩小范围。

* 第三步，直接在这一小块书架上寻找。扫几眼，拿到书。

整个过程不超过 2 分钟，而你总共只翻阅了几十本书的标签，而不是 100 万本。

**HNSW 正是这个逻辑。**

它将所有向量组织成一个多层的图结构：

* **高层（稀疏层）**：只有少量“节点”，每个节点连接着几个“邻居”。高层负责大范围的快速跳转，帮助快速缩小搜索范围。

* **低层（稠密层）**：包含所有向量，用于精细定位最终的近邻候选。

查询时，从高层入口进入，快速跳转几步找到大致区域，然后下到低层进行精细扫描。整个过程只需访问整个图的一小部分节点，而不是全部节点。

结果： **以极少量精度（通常召回率在 95%+ 以上）为代价，换来 100 倍以上的速度提升**。对于 100 万条向量，可以在几毫秒内完成。

## 五、主流向量数据库介绍

目前市面上已经有多种向量数据库可供选择，这里介绍五个最常用的。

### 轻量级本地库

一个轻量级向量数据库，提供 Python 原生 API，几行代码就能运行，无需任何部署配置。

适用场景： **本地开发、功能验证、快速上手原型**。如果想跑通 RAG 的完整流程，这是阻力最小的选择，通过 pip 安装即可直接使用。

缺点：不适合生产环境，不具备高可用、分布式等特性。

### 全托管云服务

一款全托管的云向量数据库，无需关心任何基础设施，服务器、扩容、备份等均由服务商负责，只需调用 API。

适用场景： **快速上线，不想自行运维**。适合创业公司、小团队，希望将 RAG 功能快速部署到生产环境，但没有专职 DBA 的情况。

缺点：数据存放在第三方，不适合对数据合规性有顾虑的场景；按用量计费，规模大时成本较高。

### 开源生产级数据库

一款开源的生产级向量数据库，功能全面，支持多种索引类型、分布式部署、数据持久化。背后由一家公司主导维护，社区活跃，文档完善。

适用场景： **私有化部署的生产环境**。当数据不能离开内网、需要精细控制、规模较大时，这是目前开源功能最完整的选择。

缺点：部署和运维有一定复杂度，学习曲线比轻量级库更陡。

### 集成嵌入功能的开源库

一款开源向量数据库，特色在于内置了嵌入集成功能。可以直接将原始文本输入，该库会自动调用嵌入模型将其转为向量，无需自行处理这一步骤。同时支持图片、音频等多模态数据。

适用场景： **需要多模态搜索，或希望简化嵌入步骤** 的场景。

### 高性能 Rust 实现

一款用 Rust 实现的高性能向量数据库，内存占用低，查询速度快，适合资源受限或高并发场景。接口设计简洁，同时支持 HTTP 和 gRPC。

适用场景： **对性能和资源消耗敏感** 的生产环境，例如在有限硬件上运行大规模向量检索。

***

## 六、如何选择？

介绍了这五款，该如何选择？这里提供一个明确的决策树，避免模棱两可的答案：

**学习 / 原型验证 → 选择轻量级本地库**

零配置，通过 pip 安装，几行代码即可运行完整的 RAG 流程。如果正在学习 RAG，直接使用它即可，不需要考虑太多。

**生产环境，不想管理运维 → 选择全托管云服务**

如果不想操心服务器、扩容、备份等事务，数据放在云上也没有问题，全托管服务拿来就用。

**生产环境，需要私有化部署 → 选择开源生产级数据库或高性能 Rust 实现**

数据必须部署在自己的服务器上，选择这两者。如果团队有运维能力且需要最全面的功能，选择开源生产级数据库；如果对性能和资源敏感、希望部署更简单，选择高性能 Rust 实现。

用厨房类比这四种选择：

* **轻量级本地库**：家用厨房。够用、方便，不需要专门装修，在家做饭的首选。

* **全托管云服务**：叫外卖。只管点菜，后厨、配送、洗碗都不用操心，只是需要支付外卖费。

* **开源生产级数据库**：专业餐厅厨房。功能齐全、可定制，但需要有专业厨师来管理。

* **高性能 Rust 实现**：高效快餐厨房。出菜快、省资源，适合高并发大量出餐的场景。

## 七、普通数据库 vs 向量数据库

| 对比维度      | 普通数据库（MySQL）            | 向量数据库（各类主流选项） |
| --------- | ----------------------- | ----------------------- |
| 核心用途      | 结构化数据存储和精确查询            | 向量存储和相似度搜索              |
| 索引结构      | B+ 树（适合精确匹配/范围查询）       | ANN 索引，如 HNSW（适合近邻搜索）   |
| 查询类型      | id = 5、age > 18、LIKE 匹配 | 找 top-k 个最相似向量          |
| 向量相似度查询   | 不支持（只能暴力全表扫描）           | 原生支持，毫秒级                |
| 百万级向量查询速度 | 数秒（暴力遍历，不可用）            | 毫秒级（ANN 索引加速）           |
| 数据形式      | 表格（行列结构）                | 向量 + 元数据                |
| 适合 RAG 吗  | 可以存储，但查询不行                 | 专为此场景设计                |

***

## 总结

本章的核心要点：

* **普通数据库可以存储向量，但在向量相似度查询上没有任何优化**。百万级向量加上高维（1536 维）的暴力遍历，每次查询涉及几十亿次浮点运算，根本无法运行。

* **向量数据库专门解决“海量向量中毫秒级寻找最近邻”这一问题**，其核心依赖 ANN 索引。

* **HNSW 是目前最主流的 ANN 索引**，核心思路是多层图结构：高层进行大范围快速跳转，低层进行精细定位，类似于图书馆的多级目录，无需翻阅所有书籍即可找到目标区域。代价是牺牲极少量精度，换来 100 倍以上的速度提升。

* **选型建议**：学习阶段用轻量级本地库，生产不想运维用全托管云服务，生产私有化部署用开源生产级数据库或高性能 Rust 实现。

理解了向量数据库，RAG 的离线建库链路就完整了：文档 → 切块 → 向量化 → **存入向量数据库**。
