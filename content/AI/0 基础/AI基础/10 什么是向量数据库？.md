上一章 RAG 里，在介绍 RAG 工作阶段时，提到将向量存入「向量数据库」，当时是简要说明。 

![](/images/AI/0%20%E5%9F%BA%E7%A1%80/AI%E5%9F%BA%E7%A1%80/%E4%BB%80%E4%B9%88%E6%98%AF%E5%90%91%E9%87%8F%E6%95%B0%E6%8D%AE%E5%BA%93%EF%BC%9F-e3e2c7b799cc5b65291a9c49d28398fe.png)

你可能当时会疑惑： **为什么一定要用向量数据库？MySQL 不能存储吗？**

这一章就专门把这个问题讲清楚。

***

## 一、先别急，普通数据库能存向量吗？

能存，但有一个很大的问题。

普通数据库存储向量没问题，向量本质上是一串浮点数，MySQL 创建一个字段来存储完全可行。

难的是 **查询**。

***

## 二、普通数据库为什么不能高效查询向量？

先看看 MySQL 是如何查询数据的。

执行 `SELECT * FROM users WHERE id = 5` 时，MySQL 利用 B+ 树索引，几次跳转就能定位，非常快。执行 `WHERE age > 18` 时，同样走索引，范围扫描，也很快。

MySQL 的索引本质上是为两类操作优化的： **精确匹配** 和 **范围比较**。

![](/images/AI/0%20%E5%9F%BA%E7%A1%80/AI%E5%9F%BA%E7%A1%80/%E4%BB%80%E4%B9%88%E6%98%AF%E5%90%91%E9%87%8F%E6%95%B0%E6%8D%AE%E5%BA%93%EF%BC%9F-687e8c304aaf094fd4232c28efc12a82.png)

但向量搜索是完全不同的场景。

向量搜索要完成的任务是： **给定一个向量，找出与它最相似的 top-k 个向量**。

「最相似」意味着需要计算距离，如余弦相似度、欧氏距离等。这类计算需要将查询向量与库中的每个向量逐一计算距离，然后排序，取最小的几个。

MySQL 的 B+ 树索引完全无法支持这类操作，它不知道如何在高维空间中寻找「最近邻」。

**那就暴力遍历所有向量？**

来感受一下规模：

OpenAI 的 text-embedding-ada-002 模型，每个 chunk 转换后的向量是 **1536 维**。如果你的知识库有 100 万条 chunk，那么每次查询所需的浮点运算量为：

1536 维 × 100 万条 = 15.36 亿次浮点运算

这还只是计算距离这一步。每次用户提问都要触发如此大的计算量，普通数据库无法承受。

当数据量增加到 1 亿条时，运算量为 1536 亿次浮点运算，一次查询可能需要好几秒，完全不可用。

**总结：普通数据库存储向量没问题，但查询向量相似度没有优化，一旦数据量增大就会崩溃。**

***

## 三、向量数据库是什么

向量数据库就是专门为解决这个问题而设计的， **在海量向量中，毫秒级找到最相似的 top-k 条**。

![](/images/AI/0%20%E5%9F%BA%E7%A1%80/AI%E5%9F%BA%E7%A1%80/%E4%BB%80%E4%B9%88%E6%98%AF%E5%90%91%E9%87%8F%E6%95%B0%E6%8D%AE%E5%BA%93%EF%BC%9F-4959b38811f55e10e4471089570f9f10.png)

它存储的内容与普通数据库类似：向量 + 对应的原文（元数据）。但它拥有专门为向量搜索设计的索引结构，可以将那个「15.36 亿次浮点运算」的暴力遍历优化到几十毫秒甚至几毫秒完成。

关键问题在于： **它是如何做到的？**

***

## 四、向量数据库如何实现「又快又准」

秘诀是 **ANN（Approximate Nearest Neighbor，近似最近邻）** 搜索。

注意这个词： **近似**。

向量数据库并不保证找到绝对最相似的几条，而是找到「差不多最相似的」几条，用精度换取速度。但在实际场景中，「差不多最相似的」与「绝对最相似的」在效果上几乎没有差别，因为语义检索本身就不需要那么高的精确度。

那么它使用什么算法？目前最主流的是 **HNSW**（Hierarchical Navigable Small World，分层可导航小世界图）。

![](/images/AI/0%20%E5%9F%BA%E7%A1%80/AI%E5%9F%BA%E7%A1%80/%E4%BB%80%E4%B9%88%E6%98%AF%E5%90%91%E9%87%8F%E6%95%B0%E6%8D%AE%E5%BA%93%EF%BC%9F-9db6e67886233db2fc10dd6c57c47bce.png)

名字复杂，但原理用一个例子就能讲清楚。

### 图书馆的多级目录类比

你去一个大型图书馆，想找一本叫《MySQL 索引优化》的书。

**笨方法**：从第一排书架的第一本书开始，一本一本翻，直到找到它。在拥有 100 万本书的图书馆里，这几乎不可能完成。

**图书馆的实际做法**：

* 第一步，看大类目录牌：理工科 → 计算机科学 → 数据库技术。三步跳转，你已经排除了 90% 的书架区域。

* 第二步，看中类目录：性能优化 → 索引与查询。再两步，进一步缩小范围。

* 第三步，直接在这一小块书架上找。扫几眼，拿到书。

整个过程不超过 2 分钟，而你总共只「看过」几十本书的标签，而不是 100 万本。

**HNSW 就是这个逻辑。**

它将所有向量组织成一个多层的图结构：

* **高层（稀疏层）**：只包含少量「节点」，每个节点连接着几个「邻居」。高层负责大范围的快速跳转，帮助快速缩小搜索范围。

* **低层（稠密层）**：所有向量都在这里，精细定位最终的近邻候选。

查询时，从高层入口进入，快速跳转几步找到大致区域，然后下到低层精细扫描。全程只需访问整个图的一小部分节点，而不是所有节点。

结果： **牺牲极少量精度（通常 95%+ 的召回率），换来 100 倍以上的速度提升**。100 万条向量，几毫秒就能完成。

## 五、主流向量数据库介绍

市面上已经有许多向量数据库选择，下面介绍五个最常见的。

### Chroma

本地轻量级向量数据库，提供 Python 原生 API，几行代码就能运行，无需任何部署配置。

适合场景： **本地开发、功能验证、快速原型验证**。如果你想快速跑通 RAG 的完整流程，Chroma 是最低摩擦的选择，安装 pip 包即可使用。

缺点：不适合生产环境，缺乏高可用、分布式等特性。

### Pinecone

全托管云向量数据库，无需管理任何基础设施，服务器、扩容、备份等均由 Pinecone 负责，你只需调用 API。

适合场景： **快速上线，不想自己运维**。创业公司、小团队希望将 RAG 功能上线但没有专职 DBA 时，Pinecone 是最快的路径。

缺点：数据存放在第三方，有数据合规顾虑的场景不适合；按用量收费，规模大了成本不低。

### Milvus

开源的生产级向量数据库，功能最全，支持多种索引类型、分布式部署、数据持久化。由 Zilliz 公司（国产）维护，社区活跃，文档完善。

适合场景： **私有化部署的生产环境**。数据不能出内网、需要精细控制、规模较大的场景，Milvus 是目前开源中功能最完整的选择。

缺点：部署和运维有一定复杂度，学习曲线比 Chroma 陡峭。

### Weaviate

开源向量数据库，特色是内置 Embedding 集成。你可以直接将原始文本传入，Weaviate 会自动调用 Embedding 模型将其转换为向量，无需自己处理。同时支持图片、音频等多模态数据。

适合场景： **需要多模态搜索，或者想简化 Embedding 步骤** 的场景。

### Qdrant

使用 Rust 实现的高性能向量数据库，内存占用低，查询速度快，适合资源受限或高并发场景。接口设计简洁，同时支持 HTTP 和 gRPC。

适合场景： **对性能和资源消耗敏感** 的生产环境，例如在有限硬件上运行大规模向量检索。

***

## 六、如何选择？

介绍了五个数据库，该选哪个？提供一个明确的决策树，不说「看情况」：

**学习 / 原型开发 → 使用 Chroma**

零配置，pip 安装，几行代码即可跑通完整 RAG 流程。你正在学习 RAG，直接使用 Chroma，无需过多考虑。

**生产环境，不想管理运维 → 使用 Pinecone**

不想操心服务器、扩容、备份等事务，数据可以放在云端，Pinecone 拿来即用。

**生产环境，需要私有化部署 → 使用 Milvus 或 Qdrant**

数据必须放在自己的服务器上，选择这两个方案。团队有运维能力、需要最全功能选 Milvus；对性能和资源敏感、希望部署更简单选 Qdrant。

用厨房来类比这四个选择：

* **Chroma**：家用厨房。够用，方便，无需专门装修，家庭烹饪首选。

* **Pinecone**：叫外卖。只管点菜，后厨、配送、洗碗全不用管，但要支付外卖费。

* **Milvus**：专业餐厅厨房。功能齐全、可定制，但需要专业厨师来管理。

* **Qdrant**：高效快餐厨房。出菜快、资源省，适合高并发大量出餐的场景。

## 七、普通数据库 vs 向量数据库

| 对比维度      | 普通数据库（MySQL）            | 向量数据库（Milvus/Pinecone…） |
| --------- | ----------------------- | ----------------------- |
| 核心用途      | 结构化数据存储和精确查询            | 向量存储和相似度搜索              |
| 索引结构      | B+ 树（适合精确匹配/范围查询）       | ANN 索引，如 HNSW（适合近邻搜索）   |
| 查询类型      | id = 5、age > 18、LIKE 匹配 | 找 top-k 个最相似向量          |
| 向量相似度查询   | 不支持（只能暴力全表扫描）           | 原生支持，毫秒级                |
| 百万级向量查询速度 | 数秒（暴力遍历，不可用）            | 毫秒级（ANN 索引加速）           |
| 数据形式      | 表格（行列结构）                | 向量 + 元数据                |
| 适合 RAG 吗  | 存储可以通过，但查询不行            | 专为这个场景设计                |

***

## 总结

本章的核心认识：

* **普通数据库可以存储向量，但查询向量相似度完全没有优化**。百万级向量 + 高维（1536 维）的暴力遍历，每次查询涉及数十亿次浮点运算，根本无法运行。

* **向量数据库专门解决「海量向量中毫秒级找最近邻」的问题**，依靠的是 ANN 索引。

* **HNSW 是最主流的 ANN 索引**，核心思路是多层图结构：高层大范围快速跳转，低层精细定位，像图书馆的多级目录一样，无需翻遍所有书就能找到目标区域。代价是牺牲极少量精度，换来 100 倍以上的速度提升。

* **选型建议**：学习用 Chroma，生产不想运维用 Pinecone，生产私有化部署用 Milvus 或 Qdrant。

理解了向量数据库，RAG 的离线建库链路就完整了：文档 → 切块 → 向量化 → **存入向量数据库**。
