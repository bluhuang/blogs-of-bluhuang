### 📌 本章重点总结（Harness Engineering）

1. **概念来源**：由一位工程师在 2026 年 2 月提出，随后某公司官方博客推广。核心思想是“设计一套包裹模型的外部环境，让 Agent 稳定交付”。
2. **AI 工程重心的三次演进**：
   - **Prompt Engineering**：让模型“听懂”任务（表达）。
   - **Context Engineering**：让模型“知道”该用什么信息（供给）。
   - **Harness Engineering**：让模型在真实执行中“持续做对”（驾驭）。
   - 三者是包含关系：Prompt ⊂ Context ⊂ Harness。
3. **Harness 的简洁定义**：Agent 系统里除了模型本身之外，所有决定稳定性的东西。
4. **Harness 六层核心组件（六问对应）**：
   - ① 上下文精细化：模型这一轮该看到什么？
   - ② 工具系统：模型用什么动手？
   - ③ 任务执行编排：模型下一步该干啥？
   - ④ 记忆与状态：模型跨轮该记住什么？
   - ⑤ 评估与观测：模型做得好不好有没有尺子？
   - ⑥ 约束与恢复：模型出错了能不能爬起来？
5. **五大难题与主流解法（对应五条原则）**：
   - **难题1：Agent 跑久了越走越偏** → 解决方案：Context Reset，状态外化到文件系统，每轮用干净上下文接手。原则：**重启胜过修补，状态沉到文件里**。
   - **难题2：Agent 自评总是偏乐观** → 解决方案：Planner + Generator + Evaluator 三角分工，验收与生产分离。原则：**生产和验收必须分家，验收方要能摸到真实世界**。
   - **难题3：Agent 反复失败，工程师该干啥** → 解决方案：不调提示词，而是补环境能力（如接 lint、单测、运行环境）。原则：**别问模型能不能更努力，要问环境还缺什么**。
   - **难题4：规范文件越写越长，Agent 反而更糊涂** → 解决方案：渐进式披露，主文件只保留索引（约100行），详细内容按需加载。原则：**规则宁缺毋滥，少即是多**。
   - **难题5：Agent 写的代码越堆越烂（AI slop），技术债怎么还** → 解决方案：将人类经验写成“Golden Principles”，用后台 Agent 定期自动扫描修复。原则：**技术债不是攒一堆集中还，而是每天让 Agent 自动偿还一点**。
6. **反直觉发现**：Agent 对“老技术”（稳定、文档齐全、训练数据多）掌握更好，选技术栈不必追新。
7. **工程师角色转变**：从“写代码”转向“设计 Agent 的运行环境（写规则、流程、校验、评估）”。未来主战场是 **Harness 工程**。
8. **核心公式**：`Agent Quality ≈ Model Capability + Harness Design`。模型决定天花板，Harness 决定落地稳定性。

## 这个新词到底从哪儿冒出来的？

在开讲之前，我想先带你去追个源。很多人跟风聊 Harness Engineering 时，没搞清楚这个概念最早是谁提出来的。等到知道源头，你就会明白为什么它这次真的能火，而不是又一个换皮概念。

Harness Engineering 这个词首次被正式提出，是在 2026 年 2 月 5 日的一篇博客里。作者是一位资深工程师。

![](什么是Harness工程？-3f3b8a9dfaab9691a799b1c5d5b68243.png)

标题叫《My AI Adoption Journey》，中文大概是「我接纳 AI 的历程」。

讲的是他作为一个老派工程师，如何一步步从「不信 AI」到「每天让 Agent 替我干活」的心路历程。

他把整个过程拆成了 6 个 Step，前面几步都挺反直觉，我挑几个有意思的讲讲。

第一步，直接扔掉对话框。他建议一上来别用聊天界面，要用能自主执行任务的 Agent。因为聊天界面会给你一种「我和 AI 讨论」的幻觉，实际上什么也没干，Agent 才是真正让 AI 动起来的形态。只有把 Agent 放开让它自己执行，才能真正感知到它的能力边界。

第二步更狠，他强迫自己用 Agent 去重做一部分自己早已手写过的代码。听起来有点傻？明明自己两下就能写完的活，非要等 Agent 慢慢磨。他原话说这个过程「painful」，折磨人。但目的明确：只有亲自用 AI 重做最熟悉的任务，才能精准校准「它到底哪里行、哪里不行」。

到了第五步，他给自己这套做法起了个名字，就叫 Engineer the Harness，打磨这套马具。

![](什么是Harness工程？-bc354bb8eb4ec5df72b4c64b248b4774.png)

他给出的定义特别简洁，原话翻译过来：绝大多数人遇到 Agent 犯错时，骂两句，手动改掉，祈祷下次别犯。但这位工程师每次 Agent 犯错，都会停下来问：能不能把这个错误永久性地修到环境里，让它在结构上不可能再犯？可以给 AGENTS.md 加一条规则，加一个 linter，补一个自动化测试，或者搞一个 Git Hook。关键是修补必须沉淀到环境里，而不是留在人脑子里。

这套做法威力在于「复利」：每次 Agent 犯错，环境变强一点；环境变强，Agent 下次更少犯错；犯错变少，改进速度更快。时间一长，Harness 越来越坚固，Agent 在项目中越跑越稳。

![](什么是Harness工程？-cb1ce54acdbbb401bb6d27891a60ecff.png)

博客发出来一周后，某公司紧接着也发布了一篇官方博客，标题就叫《Harness engineering: leveraging Codex in an agent-first world》。

![](什么是Harness工程？-c682ce95059ca83def279c4b4c1da9b8.png)

这篇博客讲的是他们内部一个从 3 人起步的小团队，从一个空仓库出发，用 5 个月时间，靠 Agent 写出了 100 万行代码、合并了 1500 个 PR，全程没人手动写过一行代码。

这篇博客一出，Harness Engineering 的概念直接被推到风口浪尖。所以你能看清这个概念的发展路径：这种出身决定了它不会像很多 AI 新词一样「炒一波就凉」，它更像是在真实工程土壤里长出来的。

好，交代完来源，进入正题。

## 从提示词到 Harness

要讲清楚 Harness Engineering 解决什么问题，不能一上来就讲它。它不是凭空冒出来的新概念，而是 AI 工程这几年一步一步「被逼出来」的结果。

复盘过去两年 AI 圈的变化，会发现一件有意思的事：AI 工程的重心其实悄悄换过三次。

![](什么是Harness工程？-a06bcd7574692a92eb546f6a9ff99b4b.png)

一开始大家都在聊 Prompt Engineering（提示词工程）。那时所有人都相信：模型不是不会，只是你没把话讲明白，只要提示词足够好，啥都能搞定。

后来大家发现事情不对。Agent 火起来后，模型要做的事情越来越复杂，光「把话讲清楚」远远不够，还得「知道」该用什么信息。于是 Context Engineering（上下文工程）接棒成为主角。

但这事还没完。当大家把上下文管得越来越精细后，又发现一个更扎心的问题：信息都对，模型在长链路任务里还是会跑偏。提示词没毛病，上下文也没毛病，可它就是做不稳。正是在这个背景下，那篇博客和那个百万行代码实验几乎同时出现，Harness Engineering 就这样被推到了台前。

有没有看出这条脉络？三个阶段不是谁取代谁，而是每一步都在上一步撞到天花板之后，继续往前啃出来的：

* Prompt Engineering 解决：怎么让模型「听懂」你想干啥
* Context Engineering 解决：怎么让模型「知道」该用什么信息
* Harness Engineering 解决：怎么让模型在真实执行中「持续做对」一连串的事

![](什么是Harness工程？-6776c7b7db30351a3e26b94429f1fda4.png)

听起来三句话差不多，但这三件事的难度和工作量层层放大。

把一句话讲明白难吗？不难。把一整套信息在合适时机送给模型，就有门槛了。而要搭出一整套能让模型「持续稳定交付」的运行环境，完全是另一个量级的工程活。

这也解释了很多人的疑惑：同样是用某大模型，为什么有的团队做的 Agent 又稳又能打，到别人手里一跑就跑偏？差的往往不是模型，而是围绕模型搭起来的那套东西有没有做到位。

![](什么是Harness工程？-fad77e86b29c42c8173009c617a31132.png)

接下来，我就按照「从提示词到 Harness」这条路径，带你一个阶段一个阶段往下走。先看 Prompt Engineering 当年解决了啥问题、撞上了啥天花板；再看 Context Engineering 怎么接棒、在哪儿遇到新瓶颈；最后讲 Harness Engineering 如何在这两个天花板之上又往前顶了一大截。走完这条路，你对 Harness 到底是什么，心里会有一个清晰的底。

### 第一阶段：Prompt Engineering，先让模型「听懂」你

要讲清楚 Prompt Engineering，得先聊一个更基础的问题：大模型到底在干啥？

平时用聊天工具也好，用某个 AI 工具也好，看到的都是一个对话框，输入一句话，下面输出一段话。但剥开外壳，里面其实就是一个很大的参数文件，存在硬盘上，加载到显卡内存里。

![](什么是Harness工程？-4003575f13ade98b2eaefe5e82b1d352.png)

这个文件本身什么也不是。配一个 HTTP 接口，就成了所谓的「大模型 API 服务」。给这个 API 套一个聊天界面，就成了聊天工具；套一个代码编辑器，就成了 AI IDE。

那这个参数文件本身怎么工作？说白了就一件事：根据输入的内容，预测下一个字最有可能是啥。注意是「预测」，不是「思考」。这个区别很重要。它本质上在猜你想要什么，然后把它觉得最可能的字一个一个往外吐。输入越模糊，猜的范围越大；输入越具体，猜的范围越收敛。

![](什么是Harness工程？-cbab69f2fc16802e2655a132d067ac40.png)

知道了这个原理，就能理解为什么同一个问题，换个说法效果能差十倍。

举个例子。你丢一段代码给大模型说「加个排序」。它大概率会回一段排序代码片段，告诉你「就这么写」。但你拿到一看，没说放哪儿，也没说要不要改其他函数。换一种说法：「这是我的完整代码，请帮我加上对 users 列表按年龄从大到小的排序，注意保留原有所有逻辑，最后输出完整代码」。结果一下就靠谱了。

为什么？因为大模型本质上是一个对上下文极度敏感的概率生成器。给它什么输入，它就沿着那个方向生成。给角色身份，如「你是一个资深 Java 工程师」，它就会偏向用 Java 工程师的思路回答；给几个示例，它会沿范式补全；强调约束，如「不要修改已有代码」，它会把这个约束当成重点。

你会发现，写提示词的本质不是在「命令」模型，而是在塑造它的概率空间。每句话都在悄悄把输出往某个方向推。

大家慢慢摸索出一套「提示词配方」，一个较正式的提示词通常包含：

![](什么是Harness工程？-714976c10cd28c858c42e9cfd4166649.png)

* 角色设定：你是谁？比如「你是一个有十年经验的后端工程师」
* 背景信息：当前在干啥？比如「我正在用 Go 写一个订单系统」
* 参考资料：相关的文档、历史对话、代码片段
* 明确任务：具体要你干啥
* 约束条件：哪些不能做，比如「不要修改其他文件」
* 输出格式：希望以什么形式返回，JSON、Markdown 还是表格

把这些按一定结构组装起来，就是一份比较完整的提示词。这种有意识地去设计和调整提示词、让模型稳定输出的技术活，就叫 Prompt Engineering（提示词工程）。它解决的核心问题就一个：模型不是不会，而是你没把问题说明白。

提示词工程在大模型刚火起来的那一两年作用很大。那时大家做的事情很简单：聊天、写文案、翻译、问答，都是短链路，一句问一句答，提示词写好了就搞定。

但很快，大家想做的事变复杂了，提示词工程就开始撑不住。比如让大模型「分析一下我们公司去年的财报」，它没看过财报，怎么能分析？让它「按照公司内部代码规范帮我写新功能」，它没看过规范，怎么写？让它「在已有的几十个 API 之间做一些调用组合」，它根本不知道有哪些 API。

![](什么是Harness工程？-dfa0d5b0fb3eb08bb0af70330286f2c0.png)

这时你会发现一个尴尬的事实：提示词写得再漂亮，也替代不了「事实」本身。提示词擅长把任务表达清楚、把约束讲明白，激发模型已有能力。但它不擅长「凭空补出模型不知道的知识」，不擅长「管理动态变化的信息」，也不擅长「在长链路任务里维持稳定状态」。

说白了，提示词工程解决的是「表达」的问题，不是「信息」的问题。于是第二阶段来了：Context Engineering。

### 第二阶段：Context Engineering，让模型「知道」该用什么信息

为什么 Context Engineering 会突然火起来？因为做的产品形态变了。之前做聊天机器人，问一句答一句，链路短、状态少。后来 Agent 火了，模型不再只是「回答问题」，而是要进入真实环境里「干活」。它要多轮对话，调用工具，写代码，查数据库，在多个步骤之间传递中间结果，根据外部反馈不断修正计划。
