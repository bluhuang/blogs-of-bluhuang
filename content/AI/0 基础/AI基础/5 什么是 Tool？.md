### 📌 本章重点总结（Tool 基础）

1. **问题背景**：大模型被“关在盒子里”，只能输入输出文字，无法与外部世界交互。Tool 给大模型“装上手”，让它能执行真实操作。
2. **Agent、大模型、Tool 的关系**：
   - 大模型：决策者（动脑），决定下一步做什么、调用哪个工具。
   - Tool：执行者（动手），真正去查数据库、发通知、读写文件等。
   - Agent：调度员，协调用户、大模型、工具之间的任务传递和流程推进。
3. **Tool 的完整组成（四要素）**：
   - 函数本体：具体实现功能的代码（大模型看不到，Agent 执行）。
   - `name`（名称）：大模型识别工具的标签，需望名知意。
   - `description`（描述）：最重要的字段，写清楚工具能做什么、什么场景用、返回什么信息。
   - `parameters`（参数定义）：用 JSON Schema 定义参数名、类型、必填项、示例，类似“填写表单”。
4. **大模型如何“认识”工具**：Agent 在每次对话开始时，将所有可用工具的 `name` + `description` + `parameters` 打包成工具清单，通过 API 的 `tools` 参数传给大模型。大模型根据清单判断调用哪个工具。
5. **工具分类（按风险从低到高）**：
   - **查询类（只读）**：查天气、读文件、搜索网页 → 风险低，可自主调用。
   - **写入类（有副作用）**：发通知、写数据库、改配置 → 风险中，高风险操作需人工确认。
   - **执行类（高风险）**：执行 shell 命令、重启服务、部署代码 → 风险高，必须人工审批。
   - **AI 辅助类**：RAG 检索、调用子模型 → 风险低～中，通常可自主，需关注结果质量。
6. **核心原则**：工具描述的清晰度决定了 Agent 选工具的准确率，而不是模型本身的聪明程度。`description` 必须写清楚使用场景，否则模型可能误选或漏选。

***

你是否曾遇到过这种情况：

让 AI 帮你整理电脑里的文件，它却给你写出一套完整的整理方案，分类规则头头是道，但最后仍需你自己一个个打开文件夹、手动移动；让它帮你查今天的天气，它回答：“我的知识截止到某年某月，无法获取实时天气”；让它帮你订明天的机票，它只能告诉你去哪个网站、怎么操作，然后你默默打开了购票平台。

这不是大模型不够聪明。大模型非常聪明， **但它天生就被关在一个“小盒子”里**：它只能接收文字、输出文字，它的“手”根本伸不出来，无法与外部世界产生任何交互。

这就引出了我们这一章的主角： **Tool（工具）**。Tool 就是给大模型“装上手”的方案，让它从“只动嘴的参谋”变成“能落地干活的实干家”。

***

## 一、Agent + Tool：两个角色如何配合干活

在聊 Tool 之前，先澄清另一个容易混淆的概念： **Agent**。

很多人以为“Agent 就是更厉害的大模型”，这个理解是偏差的。 **Agent 本质上是我们开发者编写的一套程序**，它不是更聪明的 AI，而是一个全程在线的“调度员”，负责在用户、大模型、工具之间协调任务、传递信息、推进流程。

用一个外卖平台来类比这三个角色的关系：

![](<attachments/什么是 Tool？-b93812c1bdffe664a7f782203b584bfd.png>)

* **你（用户）**：下单的人，提出需求。
* **大模型**：后厨主厨，负责决策——先做哪道菜、下一步做什么、何时上桌。
* **Agent**：外卖平台的调度系统，协调主厨、骑手和顾客，确保整个流程跑通。
* **Tool**：骑手和各个执行部门，真正出去跑腿、干具体事情的单位。

大模型只“动脑”，工具才“动手”。Agent 就是把这两者打通的中间层。

***

具体来说，当你给 Agent 下达一条指令：“帮我读取 C 盘目录下的 hello\_world.cpp 文件，移动到 D 盘目录下，最后给我总结一下这个文件的核心内容”，整个执行流程如下：

![](<attachments/什么是 Tool？-b73968c9e7bab4051db98a900d33e42a.png>)

1. **Agent 将需求与工具清单打包，发给大模型**：“用户想做这件事，你有这些工具可用，第一步该怎么做？”
2. **大模型做出决策，返回指令**：“调用【读取文件】工具，路径是 C://hello\_world.cpp”。
3. **Agent 执行指令，调用工具**：真正去磁盘上读取文件。
4. **Agent 把结果回传给大模型**：“文件读取成功，内容是……”
5. **大模型根据结果决定下一步**：“好，现在调用【移动文件】工具，把它移到 D 盘”。
6. **循环执行，直到任务完成**：所有步骤跑完后，大模型生成最终总结。
7. **Agent 把结果反馈给你**：任务完成。

你看，在整个过程中，“决策”始终在大模型，“执行”始终在工具，而 Agent 就是那个来回传话、推进任务的协调员。

***

## 二、Tool 到底是什么？光写函数不够？

好，现在聚焦到工具本身。

你可能会想：“工具不就是函数嘛，我写一个 Python 函数，Agent 直接调用就行了？”

听起来很合理，但这里有个关键问题： **大模型根本看不到你的 Python 代码。**

大模型不是程序员，它不会去扫描你的代码库，然后发现“哦，你这里有个 `get_weather` 函数”。它能读取的，只有你放进它对话上下文里的文字。

所以，哪怕你把函数写得再优雅，只要没有专门告诉大模型“这个函数叫什么、干什么用、参数怎么传”，大模型就永远不知道这个工具的存在。

**结论：要让大模型使用工具，必须额外给它写一份“说明书”。**

函数是“手”，说明书才是“让大模型学会用这只手的指南”。两者缺一不可。

这份说明书由四个部分组成，就是 Tool 的四要素。

***

## 三、Tool 的四要素

![](<attachments/什么是 Tool？-7e900cf103d8944b7e37298eaa898931.png>)

### 函数本体：真正干活的代码

这是实现具体功能的代码：查数据库就是查数据库，发通知就是发通知。

这部分 **大模型看不到**，但 Agent 最终会执行它。大模型只负责“决策调用哪个工具、传什么参数”，至于这个工具内部如何实现，大模型完全不关心。

### name（名称）：大模型的识别标签

大模型决定“调哪个工具”时，第一步靠的就是名称。名字要 **望名知意**。

`get_weather` 一眼就能猜到是“查天气”；`func_001` 就算添加再多描述，大模型也更难联想到它的用途。起名原则很简单：让大模型看名字就能猜出大概。

### description（描述）：整个工具定义里最重要的字段

没有之一。

大模型每轮决策的核心问题是：“当前这一步，该不该调这个工具？”它做这个判断的 **唯一依据**，就是工具的 description。

描述写清楚了，大模型准确选工具；描述写模糊了，大模型要么选错工具，要么该用时没用，要么不该用时乱用。

一个好的 description 应包含三件事：

* **能做什么**：这个工具的核心功能是什么。
* **什么场景用**：遇到哪类问题、哪种情况该选它。
* **返回什么**：调用后会得到哪些信息。

### parameters（参数定义）：告诉大模型如何“填参数”

有了函数，大模型还得知道：调用这个工具需要传哪些参数、每个参数的类型是什么、哪些是必填的。

这些信息使用 **JSON Schema** 格式定义。

JSON Schema 听起来很技术，但你可以把它理解成 **网站上的一张“填写表单”**：

你在网上购物填写收货地址时，表单会提示你：“姓名”“地址”“手机号”是必填项（标有 * 号），“备注”是选填的；“手机号”只能填数字，不能填文字。

JSON Schema 所做的正是同样的事：定义该工具有哪些“格子”需要填、每个格子填什么类型的数据、哪些格子必须填。大模型看到这份定义，就知道该如何构造调用指令了。

***

用一个完整例子把这四个部分串联起来。假设我们要给 Agent 提供一个查询天气的工具：

**先写函数本体**

```json
# ===== 第一部分：函数本体（大模型看不到，Agent 负责执行）=====
import requests

def get_weather(city: str, date: str) -> dict:
    """调用天气 API，查询指定城市指定日期的天气"""
    response = requests.get(
        "https://api.weather.com/v1/forecast",
        params={"city": city, "date": date}
    )
    data = response.json()
    return {
        "city": city,
        "date": date,
        "weather": data["condition"],   # 晴/多云/雨
        "temperature": data["temp_c"],  # 摄氏度
        "humidity": data["humidity"]    # 湿度百分比
    }
```

这段代码没什么特别，就是调用了一个天气 API，把结果整理成字典返回。注意： **大模型看不到这段代码**，它只负责决定“要调这个工具、传什么参数”，至于你用什么 API、代码怎么写，大模型完全不关心。

**再写工具说明书**

函数有了，接下来写大模型能看到的部分：name + description + parameters：

```json
// ===== 第二三四部分：工具说明书（大模型看到的部分，靠此决定是否调用）=====
{
  "name": "get_weather",
  "description": "查询指定城市在指定日期的天气情况。当用户询问某地天气、出行建议、是否需要带伞等问题时使用此工具，返回天气状况、气温和湿度信息。",
  "parameters": {
    "type": "object",
    "properties": {
      "city": {
        "type": "string",
        "description": "要查询天气的城市名称，例如：北京、上海、广州"
      },
      "date": {
        "type": "string",
        "description": "查询日期，格式：YYYY-MM-DD，例如：2025-03-21"
      }
    },
    "required": ["city", "date"]
  }
}
```

逐行拆解这份说明书：

* **`name` 字段**：`get_weather`，望名知意，大模型一看就猜到这是查天气的工具。
* **`description` 字段**：这是最关键的部分。注意它写的不是“这是一个天气 API”，而是写清楚了 **使用场景**：“当用户询问某地天气、出行建议、是否需要带伞等问题时使用”。这就是在告诉大模型：你遇到这类问题，就来用我。如果只写“查询天气”，大模型在面对“我明天去杭州要带伞吗”这种问法时，可能就不确定该不该调用。
* **`parameters` 字段**：定义了两个参数：`city`（城市名，字符串类型）和 `date`（日期，字符串类型），两个都在 `required` 里，即“必填格子”，大模型构造调用指令时不会漏填。每个参数的 `description` 里还给出了例子（“北京、上海、广州”“2025-03-21”），这是个好习惯——大模型按什么格式填参数，全靠这里的说明。

这就是函数本体和工具说明书的完整对照。用户问“明天上海天气怎么样”，大模型读完说明书，就知道：该调 `get_weather`，`city` 填“上海”，`date` 填明天的日期。

***

## 四、大模型如何“认识”这些工具？

工具写好了，下一个问题：大模型怎么知道有哪些工具？

答案是： **你得主动告诉它。**

Agent 在每次对话开始前，会把所有可用工具的 name + description + parameters 打包成一个列表，通过 API 的 `tools` 参数传给大模型。这个列表就叫 **工具清单**。

大模型每次做决策，实际上是在阅读这份清单，然后判断：“当前任务需要什么操作？哪个工具能完成？该如何调用？”

![](<attachments/什么是 Tool？-51a3768bafe818a2cdc44826eeb6ea56.png>)

用一个场景帮你理解：你入职一家新公司，第一天 HR 给你发了一份《内部系统清单》。

* **OA 系统**：用于提交请假申请、报销单据。当你需要请假或报销时使用，填写“开始日期”“结束日期”“事由”。
* **代码仓库（GitLab）**：用于提交代码、发起 MR。当你完成功能开发需要合并代码时使用，填写“分支名”“目标分支”。
* **监控平台**：用于查看服务状态、报警记录。当排查线上问题时使用，填写“服务名”“时间范围”。

拿到这份清单，你自然就知道：“哦，我下周要请假，得用 OA 系统，填开始日期和结束日期”。

大模型收到工具清单，完全是同样的逻辑——它遇到用户的问题，就在清单中查找“哪个工具能处理这个场景”，然后按照 parameters 定义填好参数，告诉 Agent 去调用。

***

这里有一个结论很重要，请记牢：

![](<attachments/什么是 Tool？-214fc576dc2b5ca32007e34df550ea27.png>)

**大模型选对工具的能力，不只取决于模型有多聪明，更取决于工具描述写得有多清晰。**

描述太模糊、两个工具描述太相似、工具太多但没有区分场景——这些问题，换再强的模型也没用。根本原因在于工具描述本身写得不够好。这就是为什么前面将 description 列为“最重要的字段”。

工具清单越丰富、描述越清晰，Agent 能做的事情越多、越准确。

***

## 五、工具有哪些类型？风险从低到高

工具并非只有一种，按照“对系统的影响程度”，从低风险到高风险分为四类。

这个“风险从低到高”的顺序不是随意排列的，它决定了每类工具在 Agent 中该如何使用、是否需要加入工审批。

### 查询类（只读）

查天气、搜索网页、读取文件、查数据库记录……只读取数据，不改变任何状态。查完数据库，数据库还是那个数据库；读完文件，文件没有任何变化。

**风险等级：低。** 这类工具可以放心让 Agent 自主调用，无需人工确认。出错了顶多是拿到无用的数据，不会产生不可逆的后果。

### 写入类（有副作用）

向数据库插入记录、发送通知消息、发送邮件、更新配置……会改变系统状态，而且有些操作不可逆——发出去的通知收不回来，写进数据库的记录即使删除也会留下痕迹。

**风险等级：中。** 对于高风险的写入操作（如发通知给成百上千人、修改线上配置），建议添加一个人工确认步骤，而不是让 Agent 完全自主执行。

### 执行类（高风险）

执行 shell 命令、运行脚本、重启服务、部署代码……能直接操作系统。一条错误的 shell 命令可能删掉整个目录，一次错误部署可能把线上服务打挂。这类工具的影响范围最大，破坏性最强。

**风险等级：高。** 必须做到两件事：严格限制权限范围（比如只允许执行白名单中的命令）；重要操作必须走人工审批，绝对不能让 Agent 自主决策。

### AI 辅助类

这是很多同学容易忽略的一类： **AI 能力本身也能封装成工具。**

例如，为 Agent 配备一个 RAG 检索工具，让它能随时查询内部知识库、历史故障案例；或者把一个专门的分类模型封装成工具，Agent 调用它对日志进行分类，只获取结论，而不需自己处理所有细节。

**风险等级：低到中。** 操作本身不会改变外部系统状态，主要关注检索结果的质量和子模型的可靠性。

***

这四类工具，风险依次递增。在设计 Agent 系统时，每个工具的风险等级直接决定两件事： **它能否自主调用？是否需要人工确认？** 这是保证 Agent 安全可靠运行的基本原则，不要等问题出现后再补充。

***

## 总结

整理一下本章的核心认知：

**工具是 Agent 的“双手”**——没有工具，Agent 只是一个只会输出文字的大模型；有了工具，Agent 才能真正与外部世界交互、完成具体任务。

**一个工具 = 函数本体 + 名称 + 描述 + 参数定义**。大模型看不到函数本体，它依靠 name + description + parameters 来判断是否该用这个工具以及如何使用。其中 **description 最关键**，是大模型选工具的唯一依据。

**四类工具，风险从低到高**：

| 类型     | 典型场景          | 风险  | Agent 能否自主调用？ |
| ------ | ------------- | --- | ------------ |
| 查询类    | 查天气、读文件、搜索网页  | 低   | 可以           |
| 写入类    | 发通知、改配置、写数据库  | 中   | 高风险操作需人工确认   |
| 执行类    | 跑脚本、重启服务、部署代码 | 高   | 必须人工审批       |
| AI 辅助类 | RAG 检索、调用子模型  | 低～中 | 通常可以，关注结果质量  |

**工具描述的清晰度决定 Agent 的准确率**——不是换更聪明的模型，而是把 description 写清楚。

后面几章将继续深入这条链路：

* **Function Calling**：大模型如何将“我要调哪个工具、传什么参数”这个决策，用标准化格式告诉 Agent——这是工具调用的底层机制。本章只看到了结果，下一章将讲解原理。
* **RAG**：将知识库检索引擎封装成工具，让 Agent 能访问私有
