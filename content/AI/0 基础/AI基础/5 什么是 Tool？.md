### 📌 本章重点总结（Tool 基础）

1. **问题背景**：大模型被“关在盒子里”，只能输入输出文字，无法与外部世界交互。Tool 给大模型“装上手”，让它能执行真实操作。
2. **Agent、大模型、Tool 的关系**：
   - 大模型：决策者（动脑），决定下一步做什么、调用哪个工具。
   - Tool：执行者（动手），真正去查数据库、发通知、读写文件等。
   - Agent：调度员，协调用户、大模型、工具之间的任务传递和流程推进。
3. **Tool 的完整组成（四要素）**：
   - 函数本体：具体实现功能的代码（大模型看不到，Agent 执行）。
   - `name`（名称）：大模型识别工具的标签，需望名知意。
   - `description`（描述）：最重要的字段，写清楚工具能做什么、什么场景用、返回什么信息。
   - `parameters`（参数定义）：用 JSON Schema 定义参数名、类型、必填项、示例，类似“填写表单”。
4. **大模型如何“认识”工具**：Agent 在每次对话开始时，将所有可用工具的 `name` + `description` + `parameters` 打包成工具清单，通过 API 的 `tools` 参数传给大模型。大模型根据清单判断调用哪个工具。
5. **工具分类（按风险从低到高）**：
   - **查询类（只读）**：查天气、读文件、搜索网页 → 风险低，可自主调用。
   - **写入类（有副作用）**：发通知、写数据库、改配置 → 风险中，高风险操作需人工确认。
   - **执行类（高风险）**：执行 shell 命令、重启服务、部署代码 → 风险高，必须人工审批。
   - **AI 辅助类**：RAG 检索、调用子模型 → 风险低～中，通常可自主，需关注结果质量。
6. **核心原则**：工具描述的清晰度决定了 Agent 选工具的准确率，而不是模型本身的聪明程度。`description` 必须写清楚使用场景，否则模型可能误选或漏选。

***

你是否遇到过这种情况：

让 AI 帮你整理电脑里的文件，它却写出一整套整理方案，分类规则条条在理，但最后仍需你手动处理；让它查询今天的天气，它回答“我的知识截止到某年某月，无法获取实时天气”；让它帮你预订明天的机票，它只能告知去哪家网站、如何操作，然后你默默打开旅行 APP。

这并非大模型不够聪明。大模型非常聪明， **但它天生就被关在一个“小盒子”里**，只能接收文字、输出文字，它的“手”无法伸出，无法与外部世界交互。

由此引出本章的核心概念： **Tool（工具）**。Tool 就是为大模型“装上手”的方案，让它从“只动嘴的参谋”转变为“能落地干活的实干家”。

***

## 一、Agent + Tool：两个角色如何协同

在讨论 Tool 之前，先厘清另一个易混淆的概念： **Agent**。

很多人以为“Agent 就是更厉害的大模型”，这个理解有偏差。 **Agent 本质上是开发者编写的一套程序**，它不是更聪明的 AI，而是一个全程在线的“调度员”，负责在用户、大模型、工具之间协调任务、传递信息、推进流程。

用一个外卖平台类比三者的关系：

![](<attachments/什么是 Tool？-b93812c1bdffe664a7f782203b584bfd.png>)

* **你（用户）**：下单的人，提出需求
* **大模型**：后厨主厨，负责决策：先做哪道菜、下一步做什么、何时上桌
* **Agent**：外卖平台的调度系统，协调主厨、骑手和顾客，确保流程顺畅
* **Tool**：骑手和各执行部门，真正跑腿、干具体事务

大模型只“动脑”，工具才“动手”。Agent 则是打通二者的中间层。

***

具体来说，当你向 Agent 下达指令：“帮我读取 C 盘目录下的 hello\_world.cpp 文件，移动到 D 盘目录，最后总结文件的核心内容”，执行流程如下：

![](<attachments/什么是 Tool？-b73968c9e7bab4051db98a900d33e42a.png>)

1. **Agent 将需求与工具清单打包，发送给大模型**：“用户有需求，你有这些工具可用，第一步该如何做？”
2. **大模型做决策，返回指令**：“调用【读取文件】工具，路径为 C://hello\_world.cpp”
3. **Agent 执行指令，调用工具**：实际读取磁盘文件
4. **Agent 将结果回传给大模型**：“文件读取成功，内容是……”
5. **大模型根据结果决定下一步**：“好的，现在调用【移动文件】工具，移至 D 盘”
6. **循环执行直至任务完成**：所有步骤完成后，大模型生成最终总结
7. **Agent 将结果反馈给你**：任务完成

可以看出，整个过程中，“决策”始终由大模型负责，“执行”始终由工具承担，Agent 是来回传递信息、推进任务的协调者。

***

## 二、Tool 到底是什么？仅写函数不够？

现在聚焦到工具本身。

你可能想：“工具不就是函数吗？我写一个 Python 函数，Agent 直接调用就行了？”

听起来合理，但有一个关键问题： **大模型根本看不到你的 Python 代码。**

大模型不是程序员，它不会扫描你的代码库并发现“你有一个 `get_weather` 函数”。它能读的只有放入其对话上下文中的文字。

因此，即便函数写得再优雅，只要没有专门告诉大模型“这个函数叫什么、做什么、参数如何传”，大模型就永远不知道此工具的存在。

**结论：要让大模型使用工具，必须额外提供一份“说明书”。**

函数是“手”，说明书才是“让大模型学会使用这只手的指南”，两者缺一不可。

这份说明书由四部分组成，即 Tool 的四要素。

***

## 三、Tool 的四要素

![](<attachments/什么是 Tool？-7e900cf103d8944b7e37298eaa898931.png>)

### 函数本体——真正干活的代码

这是实现具体功能的代码，比如查数据库、发通知等。这部分 **大模型看不到**，但 Agent 会执行它。大模型只负责“决策调用哪个工具、传入什么参数”，不关心工具内部实现。

### name（名称）——大模型的识别标签

大模型决定“调用哪个工具”时，首先依赖名称。名字需要 **望名知意**。

`get_weather` 一目了然是“查天气”；`func_001` 即使加再多描述，大模型也难以联想其用途。命名原则很简单：让大模型从名称就能猜出大概。

### description（描述）——整个工具定义中最重要的字段

没有之一。

大模型每轮决策的核心问题是：“当前步骤是否该调用此工具？”判断的 **唯一依据** 就是工具的 description。

描述清晰，大模型准确选工具；描述模糊，大模型可能误选、漏选或滥用。

一个好的 description 应包含三方面：

* **能做什么**：核心功能
* **什么场景用**：遇到哪类问题、何种情况应选用
* **返回什么**：调用后会得到哪些信息

### parameters（参数定义）——告诉大模型如何“填写参数”

有了函数，大模型还需知道调用该工具需哪些参数、参数类型、是否必填。

这些信息使用 **JSON Schema** 格式定义。

JSON Schema 可以理解为 **网站上的“表单”**：

网购填写收货地址时，表单会指示“姓名”“地址”“手机号”是必填项（标 *），备注为选填；手机号只能输入数字。

JSON Schema 做同样的事：定义工具有哪些“格子”需填写、每个格子应填什么类型的数据、哪些格子必须填。大模型看到定义，就知道如何构造调用指令。

***

用一个完整示例将四个部分串联起来。假设要为 Agent 提供一个查询天气的工具：

**先编写函数本体：**

```json
# ===== 第一部分：函数本体（大模型看不到，Agent 负责执行）=====
import requests

def get_weather(city: str, date: str) -> dict:
    """调用天气 API，查询指定城市指定日期的天气"""
    response = requests.get(
        "https://api.weather.com/v1/forecast",
        params={"city": city, "date": date}
    )
    data = response.json()
    return {
        "city": city,
        "date": date,
        "weather": data["condition"],   # 晴/多云/雨
        "temperature": data["temp_c"],  # 摄氏度
        "humidity": data["humidity"]    # 湿度百分比
    }
```

这段代码很简单，就是调用天气 API 并返回结果。注意： **大模型看不到这段代码**，它只负责决定“调用此工具并传入参数”。

**再编写工具说明书：**

函数有了，接下来写大模型能看到的部分：name + description + parameters：

```json
// ===== 第二三四部分：工具说明书（大模型看到的部分，依据其决定是否调用）=====
{
  "name": "get_weather",
  "description": "查询指定城市在指定日期的天气情况。当用户询问某地天气、出行建议、是否需要带伞等问题时使用此工具，返回天气状况、气温和湿度信息。",
  "parameters": {
    "type": "object",
    "properties": {
      "city": {
        "type": "string",
        "description": "要查询天气的城市名称，例如：北京、上海、广州"
      },
      "date": {
        "type": "string",
        "description": "查询日期，格式：YYYY-MM-DD，例如：2025-03-21"
      }
    },
    "required": ["city", "date"]
  }
}
```

逐行解读此说明书：

* **`name` 字段**：`get_weather`，望名知意，大模型一看便知这是查天气的工具。
* **`description` 字段**：最关键的部分。它写的不仅是“这是一个天气 API”，而是明确了 **使用场景**：“当用户询问某地天气、出行建议、是否需要带伞等问题时使用”。这告诉大模型：遇到此类问题就来调用。如果只写“查询天气”，大模型面对“我明天去杭州要带伞吗”这种问法时，可能不确定是否应调用。
* **`parameters` 字段**：定义两个参数 `city`（字符串型）和 `date`（字符串型），均在 `required` 中，即“必填格子”，大模型构造调用指令时不会漏填。每个参数的 `description` 中含有示例（“北京、上海、广州”“2025-03-21”），这是好习惯——大模型按什么格式填写参数，完全依赖这里的说明。

函数本体与工具说明书的完整对照已呈现。用户问“明天上海天气怎么样”，大模型读完说明书，就知道应调用 `get_weather`，`city` 填“上海”，`date` 填明天的日期。

***

## 四、大模型如何“认识”这些工具？

工具编写完成后，下一个问题：大模型如何知道有哪些可用工具？

答案是： **你必须主动告知它。**

Agent 在每次对话开始前，将所有可用工具的 name + description + parameters 打包成一个列表，通过 API 的 `tools` 参数传递给大模型。这个列表称为 **工具清单**。

大模型每次做决策时，实际上是在阅读这份清单，然后判断：“当前任务需要什么操作？哪个工具能完成？如何调用？”

![](<attachments/什么是 Tool？-51a3768bafe818a2cdc44826eeb6ea56.png>)

用一个场景帮助你理解：入职新公司第一天，HR 发给你一份《内部系统清单》：

* **OA 系统**：用于提交请假申请、报销单据。当需要请假或报销时使用，填写“开始日期”“结束日期”“事由”。
* **代码仓库（GitLab）**：用于提交代码、发起 MR。当完成功能开发需要合并代码时使用，填写“分支名”“目标分支”。
* **监控平台**：用于查看服务状态、报警记录。排查线上问题时使用，填写“服务名”“时间范围”。

拿到这份清单，你就知道：“哦，下周要请假，得用 OA 系统，填开始日期和结束日期”。

大模型收到工具清单，遵循完全相同的逻辑：遇到用户问题，在清单中寻找“哪个工具能处理此场景”，然后按照 parameters 定义填写参数，告知 Agent 去调用。

***

这里有一个重要结论，需牢记：

![](<attachments/什么是 Tool？-214fc576dc2b5ca32007e34df550ea27.png>)

**大模型选中正确工具的能力，不仅取决于模型的聪明程度，更取决于工具描述的清晰程度。**

描述太模糊、两个工具描述过于相似、工具太多但未区分场景——这些问题即使换再强的模型也无济于事。根本原因在于工具描述本身不够好。这就是为何前面将 description 列为“最重要的字段”。

工具清单越丰富、描述越清晰，Agent 能完成的任务就越多、越准确。

***

## 五、工具有哪些类型？风险从低到高

工具并非单一类型，按照“对系统的影响程度”，可划分为从低风险到高风险的四个类别。

这个“风险从低到高”的顺序并非随意排列，它决定了每类工具在 Agent 中应如何使用、是否需人工审批。

### 查询类（只读）

查天气、搜索网页、读取文件、查询数据库记录……仅读取数据，不改变任何状态。查询后数据库无变化；读取后文件不变。

**风险等级：低。** 此类工具可放心让 Agent 自主调用，无需人工确认。出错顶多获取无效数据，不会造成不可逆后果。

### 写入类（有副作用）

向数据库插入记录、发送通知消息、发送邮件、更新配置……会改变系统状态，且部分操作不可逆（发出的通知无法召回，写入数据库的记录即便删除也会留下痕迹）。

**风险等级：中。** 对于高风险写入操作（如群发通知给数百人、修改线上配置），建议增加人工确认步骤，而非让 Agent 完全自主执行。

### 执行类（高风险）

执行 shell 命令、运行脚本、重启服务、部署代码……可直接操作系统。一条错误的 shell 命令可能删除整个目录，一次错误部署可能使线上服务宕机。这类工具的影响范围最大，破坏性最强。

**风险等级：高。** 必须做到两点：严格限制权限范围（例如仅允许执行白名单中的命令）；重要操作必须经过人工审批，绝不能让 Agent 自主决策。

### AI 辅助类

这是许多人所未想到的一类： **AI 能力本身也可封装为工具。**

例如，为 Agent 配置一个 RAG 检索工具，使其能随时查询内部知识库、历史故障案例；或者将一个专门的分类模型封装为工具，Agent 调用它对日志进行分类，仅获取结论，无需自行处理所有细节。

**风险等级：低到中。** 操作本身不改变外部系统状态，主要关注检索结果的质量及子模型的可靠性。

***

这四类工具，风险依次递增。在设计 Agent 系统时，每个工具的风险等级直接决定了两件事： **它能否自主调用？是否需要人工确认？** 这是确保 Agent 安全可靠运行的基本原则，应提前考虑，而非等问题出现后再补救。

***

## 总结

整理本章的核心认知：

**工具是 Agent 的“双手”**，没有工具，Agent 仅是一个输出文字的大模型；有了工具，Agent 才能真正与外部交互、完成具体任务。

**一个工具 = 函数本体 + 名称 + 描述 + 参数定义**。大模型看不到函数本体，它依靠 name + description + parameters 判断是否该使用该工具以及如何使用。其中 **description 最为关键**，是大模型选择工具的唯一依据。

**四类工具，风险从低到高**：

| 类型     | 典型场景          | 风险  | Agent 能否自主调用？ |
|------|---------------|-----|--------------|
| 查询类    | 查天气、读文件、搜索网页  | 低   | 可以           |
| 写入类    | 发通知、改配置、写数据库  | 中   | 高风险操作需人工确认  |
| 执行类    | 跑脚本、重启服务、部署代码 | 高   | 必须人工审批      |
| AI 辅助类 | RAG 检索、调用子模型  | 低～中 | 通常可以，关注结果质量 |

**工具描述的清晰度决定了 Agent 的准确率**，关键在于将 description 写清楚，而非更换更聪明的模型。

* **RAG**：将知识库检索封装为工具，使 Agent 能访问私有数据，重要到需单独安排一章。
