### 📌 本章重点总结（Tool 基础）

1. **问题背景**：大模型被“关在盒子里”，只能输入输出文字，无法与外部世界交互。Tool 给大模型“装上手”，让它能执行真实操作。
2. **Agent、大模型、Tool 的关系**：
   - 大模型：决策者（动脑），决定下一步做什么、调用哪个工具。
   - Tool：执行者（动手），真正去查数据库、发通知、读写文件等。
   - Agent：调度员，协调用户、大模型、工具之间的任务传递和流程推进。
3. **Tool 的完整组成（四要素）**：
   - 函数本体：具体实现功能的代码（大模型看不到，Agent 执行）。
   - `name`（名称）：大模型识别工具的标签，需望名知意。
   - `description`（描述）：最重要的字段，写清楚工具能做什么、什么场景用、返回什么信息。
   - `parameters`（参数定义）：用 JSON Schema 定义参数名、类型、必填项、示例，类似“填写表单”。
4. **大模型如何“认识”工具**：Agent 在每次对话开始时，将所有可用工具的 `name` + `description` + `parameters` 打包成工具清单，通过 API 的 `tools` 参数传给大模型。大模型根据清单判断调用哪个工具。
5. **工具分类（按风险从低到高）**：
   - **查询类（只读）**：查天气、读文件、搜索网页 → 风险低，可自主调用。
   - **写入类（有副作用）**：发通知、写数据库、改配置 → 风险中，高风险操作需人工确认。
   - **执行类（高风险）**：执行 shell 命令、重启服务、部署代码 → 风险高，必须人工审批。
   - **AI 辅助类**：RAG 检索、调用子模型 → 风险低～中，通常可自主，需关注结果质量。
6. **核心原则**：工具描述的清晰度决定了 Agent 选工具的准确率，而不是模型本身的聪明程度。`description` 必须写清楚使用场景，否则模型可能误选或漏选。

***

你是否遇到过这种情况：让 AI 帮你整理电脑里的文件，它却只给你写出一套整理方案，分类规则头头是道，但最后仍需要你手动操作；让你查今天的天气，它却说“知识截止到某年某月，无法获取实时天气”；让你订明天的机票，它只能引导你去哪个网站、怎么操作，然后你只能自己打开订票平台。

这不是大模型不够聪明。大模型很聪明， **但它天生就被关在一个“小盒子”里**，只能接收文字、输出文字，它的“手”根本伸不出来，无法与外部世界交互。

这就引出了本章的主角： **Tool（工具）**。Tool 就是给大模型“装上手”的方案，让它从“只动嘴的参谋”变成“能落地干活的实干家”。

***

## 一、Agent + Tool：两个角色如何配合

在讨论 Tool 之前，先厘清另一个容易混淆的概念： **Agent**。

很多人以为“Agent 就是更厉害的大模型”，这个理解有偏差。 **Agent 本质上是开发者编写的一套程序**，它不是更聪明的 AI，而是一个全程在线的“调度员”，负责在用户、大模型、工具之间协调任务、传递信息、推进流程。

用一个外卖平台来类比这三个角色的关系：

![](<attachments/什么是 Tool？-b93812c1bdffe664a7f782203b584bfd.png>)

* **你（用户）**：下单的人，提出需求
* **大模型**：后厨主厨，负责决策——先做哪道菜、下一步做什么、什么时候上桌
* **Agent**：外卖平台的调度系统，协调主厨、骑手和顾客，确保整体流程推进
* **Tool**：骑手和各执行部门，真正出去跑腿、干具体事情

大模型只“动脑”，工具才“动手”。Agent 就是打通两者的中间层。

***

具体来说，当你给 Agent 下达指令：“帮我读取 C 盘目录下的 hello\_world.cpp 文件，移动到 D 盘目录，最后总结该文件的核心内容”，整个执行流程如下：

![](<attachments/什么是 Tool？-b73968c9e7bab4051db98a900d33e42a.png>)

1. **Agent 将需求与工具清单打包发给大模型**：“用户想完成这件事，你有这些工具可用，第一步该怎么做？”
2. **大模型做决策，返回指令**：“调用【读取文件】工具，路径是 C://hello\_world.cpp”
3. **Agent 执行指令，调用工具**：实际从磁盘读取文件
4. **Agent 将结果回传给大模型**：“文件读取成功，内容是……”
5. **大模型依据结果决定下一步**：“现在调用【移动文件】工具，将其移到 D 盘”
6. **循环执行直至任务完成**：所有步骤完成，大模型生成最终总结
7. **Agent 将结果反馈给用户**：任务完成

整个过程里，“决策”始终由大模型负责，“执行”始终由工具负责，而 Agent 就是来回传递信息、推进任务的协调员。

***

## 二、Tool 到底是什么？只写函数是不够的

现在聚焦到工具本身。

你可能会想：“工具不就是函数吗？我写一个 Python 函数，Agent 直接调用就行了？”

听起来合理，但关键问题在于： **大模型根本看不到你的 Python 代码。**

大模型不是程序员，它不会去扫描你的代码库然后发现“哦，这里有个 `get_weather` 函数”。它能读的，只有你放进它对话上下文里的文字。

所以，哪怕函数写得再优雅，只要没有专门告诉大模型“这个函数叫什么、有什么用、参数怎么传”，大模型永远不知道这个工具的存在。

**结论：要让大模型使用工具，必须额外给它写一份“说明书”。**

函数是“手”，说明书才是“让大模型学会用这只手的指南”。两者缺一不可。

这份说明书由四个部分组成，即 Tool 的四要素。

***

## 三、Tool 的四要素

![](<attachments/什么是 Tool？-7e900cf103d8944b7e37298eaa898931.png>)

### 函数本体：真正执行功能的代码

这是实现具体功能的代码，比如查数据库、发通知等。

这部分 **大模型看不到**，但 Agent 最终会执行它。大模型只负责“决策调用哪个工具、传递什么参数”，至于工具内部如何实现，大模型完全不关心。

### name（名称）：大模型的识别标签

大模型决定“调哪个工具”时，第一步依赖的就是名称。名称要 **望名知意**。

`get_weather` 一眼就能知道是“查天气”；而 `func_001` 即使加入再多的描述，大模型也很难联想到它的用途。起名原则很简单：让大模型看到名字就能猜出大致功能。

### description（描述）：整个工具定义里最重要的字段

没有之一。

大模型每轮决策的核心问题是：“当前这一步，是否应该调用这个工具？”它做判断的 **唯一依据**，就是工具的 description。

描述清晰，大模型就能准确选工具；描述模糊，大模型要么选错工具，要么该用时不用，要么不该用时乱用。

一个好的 description 应包含三方面内容：

* **能做什么**：该工具的核心功能
* **什么场景用**：遇到哪类问题、哪种情况应选择该工具
* **返回什么**：调用后会得到哪些信息

### parameters（参数定义）：告诉大模型如何“填参数”

有了函数，大模型还需要知道：调用这个工具需要传递哪些参数、每个参数是什么类型、哪些是必填的。

这些信息用 **JSON Schema** 格式定义。

JSON Schema 可以理解成 **网站上的一张“填写表单”**：例如网购填收货地址时，表单会提示“姓名”“地址”“手机号”是必填项（带星号），“备注”是选填的；“手机号”只能填数字，不能填文字。

JSON Schema 做的就是同样的事：定义这个工具有哪些“格子”需要填写、每个格子填什么类型的数据、哪些格子必须填写。大模型看到定义后，就能知道如何构造调用指令。

***

用一个完整的例子将这四个部分串联起来。假设我们要为 Agent 提供一个查询天气的工具：

**先写函数本体**

```python
# ===== 第一部分：函数本体（大模型看不到，Agent 负责执行）=====
import requests

def get_weather(city: str, date: str) -> dict:
    """调用天气 API，查询指定城市指定日期的天气"""
    response = requests.get(
        "https://api.weather.com/v1/forecast",
        params={"city": city, "date": date}
    )
    data = response.json()
    return {
        "city": city,
        "date": date,
        "weather": data["condition"],   # 晴/多云/雨
        "temperature": data["temp_c"],  # 摄氏度
        "humidity": data["humidity"]    # 湿度百分比
    }
```

这段代码只是调用天气 API，将结果整理成字典返回。注意： **大模型看不到这段代码**，它只负责决定“要调用这个工具、传递什么参数”，至于你用什么 API、代码如何编写，大模型完全不关心。

**再写工具说明书**

函数写好之后，接下来编写大模型能看到的 name + description + parameters：

```json
// ===== 第二、三、四部分：工具说明书（大模型看到的部分，以此决定是否调用）=====
{
  "name": "get_weather",
  "description": "查询指定城市在指定日期的天气情况。当用户询问某地天气、出行建议、是否需要带伞等问题时使用此工具，返回天气状况、气温和湿度信息。",
  "parameters": {
    "type": "object",
    "properties": {
      "city": {
        "type": "string",
        "description": "要查询天气的城市名称，例如：北京、上海、广州"
      },
      "date": {
        "type": "string",
        "description": "查询日期，格式：YYYY-MM-DD，例如：2025-03-21"
      }
    },
    "required": ["city", "date"]
  }
}
```

逐行拆解这份说明书：

* **`name` 字段**： `get_weather` ，望名知意，大模型一看就能猜到这是查天气的工具。
* **`description` 字段**：最关键的部分。注意它写的不是“这是一个天气 API”，而是明确 **使用场景**：“当用户询问某地天气、出行建议、是否需要带伞等问题时使用”。这告诉大模型：遇到这类问题，就来调用我。如果只写“查询天气”，大模型在面对“我明天去杭州要带伞吗？”这样的问法时，可能不确定是否该调用。
* **`parameters` 字段**：定义了两个参数， `city` （城市名，字符串类型）和 `date` （日期，字符串类型），参数都在 `required` 中，即“必填格子”，大模型构造调用指令时不会漏填。每个参数的 `description` 中都给出了示例（如“北京、上海、广州”“2025-03-21”），这是好习惯，大模型按什么格式填参数，全凭这里的说明。

这就是函数本体和工具说明书的完整对应关系。用户问“明天上海天气怎么样”，大模型读完说明书，就知道：应该调用 `get_weather` ， `city` 填“上海”， `date` 填明天的日期。

***

## 四、大模型如何“认识”这些工具？

工具写好了，下一个问题：大模型怎么知道有哪些工具？

答案是： **你必须主动告诉它。**

Agent 在每次对话开始前，会将所有可用工具的 name + description + parameters 打包成一个列表，通过 API 的 `tools` 参数传给大模型。这个列表叫做 **工具清单**。

大模型每次做决策时，实际上是在读取这份清单，然后判断：“当前任务需要什么操作？哪个工具能完成？应该如何调用？”

![](<attachments/什么是 Tool？-51a3768bafe818a2cdc44826eeb6ea56.png>)

用生活场景帮助你理解：入职一家新公司，第一天 HR 发给你一份《内部系统清单》：

* **OA 系统**：用于提交请假申请、报销单据。当需要请假或报销时使用，填写“开始日期”“结束日期”“事由”。
* **代码仓库（GitLab）**：用于提交代码、发起合并请求。当完成功能开发需要合并代码时使用，填写“分支名”“目标分支”。
* **监控平台**：用于查看服务状态、报警记录。当排查线上问题时使用，填写“服务名”“时间范围”。

拿到这份清单，你自然知道：“哦，我下周要请假，应该用 OA 系统，填写开始日期和结束日期。”

大模型收到工具清单，逻辑完全相同。它遇到用户的问题后，便在清单中寻找“哪个工具能处理这个场景”，然后按照 parameters 定义填写参数，告诉 Agent 去调用。

***

这里有一个重要结论需要牢记：

![](<attachments/什么是 Tool？-214fc576dc2b5ca32007e34df550ea27.png>)

**大模型选对工具的能力，不仅取决于模型本身有多聪明，更取决于工具描述写得有多清晰。**

描述过于模糊、两个工具描述太相似、工具数量太多但未区分场景——这些问题，无论换多么强大的模型都难以解决。根本原因在于工具描述本身不够好。这就是为何前面将 description 列为“最重要的字段”。

工具清单越丰富、描述越清晰，Agent 能完成的任务就越多、准确率也越高。

***

## 五、工具有哪些类型？风险从低到高

工具并非只有一种类型，按照对系统的影响程度，从低风险到高风险可分为四类。

这个“风险从低到高”的顺序并非随意排列，它决定了每类工具在 Agent 中应如何使用、是否需要加入人工审批。

### 查询类（只读）

查天气、搜索网页、读取文件、查数据库记录……只读取数据，不改变任何状态。查询后数据库还是原样，文件也没有变化。

**风险等级：低。** 这类工具可以放心让 Agent 自主调用，无需人工确认。即使出错，最多获取无用的数据，不会造成不可逆的后果。

### 写入类（有副作用）

往数据库插入记录、发送通知消息、发送邮件、更新配置等操作会改变系统状态，且部分操作不可逆（如已发出的通知无法收回，即使删除记录也留痕迹）。

**风险等级：中。** 对于高风险写入操作（例如向几百人发送通知、修改线上配置），建议加入人工确认步骤，而非让 Agent 完全自主执行。

### 执行类（高风险）

执行 shell 命令、运行脚本、重启服务、部署代码等能直接操作系统。一条错误的 shell 命令可能删除整个目录，一次错误的部署可能使线上服务崩溃。这类工具影响范围最大、破坏性最强。

**风险等级：高。** 必须做到两件事：严格限制权限范围（例如只允许执行白名单中的命令）；关键操作必须经过人工审批，绝不能让 Agent 自主决策。

### AI 辅助类

这也是很多同学容易忽略的一类： **AI 能力本身也可封装成工具。**

例如，为 Agent 配置一个 RAG 检索工具，使其能随时查阅内部知识库、历史故障案例；或将一个专门的分类模型封装成工具，Agent 调用它对日志进行分类，只获取结论，无需自行处理所有细节。

**风险等级：低到中。** 此类操作本身不改变外部系统状态，主要需关注检索结果的质量和子模型的可靠性。

***

这四类工具风险依次递增。在设计 Agent 系统时，每个工具的风险等级直接决定了两件事： **它能否自主调用？是否需要人工确认？** 这是确保 Agent 安全可靠运行的基本原则，应预先考虑而非等出了问题再补充。

***

## 总结

整理本章的核心认知：

**工具是 Agent 的“双手”**，没有工具，Agent 只是一个只能输出文字的大模型；有了工具，Agent 才能真正与外部世界交互并完成具体任务。

**一个工具 = 函数本体 + 名称 + 描述 + 参数定义**。大模型看不到函数本体，它依赖 name + description + parameters 来判断是否该使用该工具以及如何使用。其中 **description 最关键**，是大模型选择工具的唯一依据。

**四类工具，风险从低到高**：

| 类型     | 典型场景          | 风险  | Agent 能否自主调用？ |
| ------ | ------------- | --- | ------------- |
| 查询类    | 查天气、读文件、搜索网页  | 低   | 可以            |
| 写入类    | 发通知、改配置、写数据库  | 中   | 高风险操作需人工确认    |
| 执行类    | 运行脚本、重启服务、部署代码 | 高   | 必须人工审批        |
| AI 辅助类 | RAG 检索、调用子模型  | 低～中 | 通常可以，需关注结果质量 |

**工具描述的清晰度决定了 Agent 的准确率**，并非换更聪明的模型，而是将 description 写清楚。
