### 📌 本章重点总结（Function Calling）

1. **Function Calling 是什么**：大模型与 Agent 之间的**标准化工具调用协议**，解决“大模型做出决策后如何精准传递指令给 Agent”的问题。
2. **为什么需要 Function Calling**：传统方式用自然语言在 System Prompt 里描述工具，导致大模型回复格式不可控（参数错乱、编造答案、不调用工具等），开发者需大量解析和纠错代码。Function Calling 用固定 JSON 格式彻底告别“猜谜”。
3. **Function Calling 的三部分结构**：
   - **工具定义（Tool Definition）**：开发者提供标准 JSON，包含 `name`、`description`、`parameters`（含类型、格式、必填项）。大模型据此判断是否调用及如何调用。
   - **AI 调用格式（Function Call）**：大模型返回固定 JSON（如 `{"function_call": {"name": "...", "parameters": {...}}}`），Agent 直接解析，无需猜测。
   - **工具返回结果（Tool Response）**：Agent 执行工具后，将结果按规范格式回传大模型，用于下一步决策。
4. **对应 Agent 执行循环中的三步**：
   - 第1步 → 工具定义（Agent 传工具清单给大模型）
   - 第2步 → AI 调用格式（大模型返回调用指令）
   - 第4步 → 工具返回结果（Agent 回传执行结果）
   - （第3步“执行工具”不属于 Function Calling 范围）
5. **核心优势对比**：工具描述规范、调用格式固定、参数错误率极低、开发成本低、模型兼容性好（主流大模型通用）。
6. **与 Tool 的关系**：
   - Tool 是“能力层”（定义有什么工具、能做什么）。
   - Function Calling 是“协议层”（规定大模型和 Agent 之间怎么传递调用指令）。

***

上一章你已经知道，一个工具 = 函数本体 + 名称 + 描述 + 参数定义，大模型靠工具描述来判断是否要调用这个工具。

但这里有一个关键问题尚未解决：**大模型做出「要调用这个工具」的决策之后，它如何告诉 Agent 去执行？**

大模型只会“说话”，它的输出永远是文字。但 Agent 要调用工具，必须明确知道：调用哪个工具？传入什么参数？格式是什么？这中间的信息交换如何确保准确性？

这正是 Function Calling 要解决的核心问题。在讲解它之前，我们先看看没有它时，开发者的处境。

***

## 没有 Function Calling 之前：靠自然语言“猜”

在 Function Calling 出现之前，开发者只能将工具的描述和调用规范全部用**自然语言写进 System Prompt（系统提示词）**。

例如，若想使 AI 能调用天气查询工具，System Prompt 需这样写：

```json
你是一个智能助手，你可以使用以下工具：

工具名：check_weather
功能：查询某个城市的天气
参数：
  - city：城市名，中文，比如"上海"
  - date：日期，格式必须是 YYYY-MM-DD，比如"2026-03-19"
  - date 是可选的，不填默认查今天

当用户需要查天气时，你要调用这个工具，告诉我工具名和参数。
```

当用户需要查天气时，你要调用这个工具，告诉我工具名和参数。

听起来还不错？但问题在于，大模型是自由发挥的选手，很难约束。你让它查询「上海明天的天气」，它可能返回：

* **散文式回复**：“好的，我来帮你查询上海明天的天气，需要使用 check_weather 工具，城市是上海，时间是明天～”

* **参数顺序颠倒**： `{"date": "明天", "city": "上海"}` （“明天”完全不是 YYYY-MM-DD 格式，直接传入工具就会报错）

* **直接编造天气**：不调用工具，根据训练数据生成一条“明天上海天气预报”

* **JSON 里混入自然语言**： `调用工具: check_weather, 参数 city=上海, date=2026-03-20`

* **完全无视要求**：输出一篇介绍上海气候特点的科普文章

这就是传统 System Prompt 模式的本质问题：**完全依赖 AI 猜测**。猜是否调用工具、猜参数格式、猜回复结构。猜对了就正常运行，猜错了整个流程崩溃。

而开发者需要编写大量正则表达式和解析代码，试图从 AI 五花八门的回复中“扒”出工具名和参数。工具越多，解析代码往往比业务代码还长。而且切换模型后，还需重写一遍。这种开发体验无疑是噩梦。

***

## Function Calling 的出现：告别猜谜，统一规范

这便是 Function Calling 的诞生背景。

**Function Calling 的本质，是一套大模型和 Agent 之间的标准化工具调用协议**。我们不再用自然语言告诉 AI“你可以用这个工具”，而是用一套固定的 JSON 格式将工具定义清楚；大模型也不再自由发挥，而是严格按照固定的 JSON 结构返回调用指令。

![](<attachments/什么是 Function Call？-eae4436ac998b58db23067f53ef24db8.png>)

整个过程变为：你给我标准格式的工具说明书，我给你标准格式的调用指令，双向约定，零歧义，零猜测。

这里很多同学会疑惑：Tool 和 Function Calling 有什么关系？简单来说，**Tool 是“能力实体”，Function Calling 是“调用机制”**。大模型通过 Function Calling 这个协议去调用 Tool 这个具体功能。两者解决完全不同的层面：

* **工具（Tool）= 能力层，解决“有什么”**：一个工具需要哪些要素才算完整，才能让大模型认识并使用它。函数本体是真正执行任务的，名称让大模型能精准识别，描述告诉大模型何时该用它，参数定义告诉大模型如何构造调用参数。这是在定义一个能力本身。

* **Function Calling = 协议层，解决“怎么传”**：工具写好之后，大模型和 Agent 之间要用什么格式交换信息？大模型如何告诉 Agent 要调用哪个工具、传入什么参数？Agent 执行完工具后如何将结果回传给大模型？这是一套标准化通信规范。

打个比方：工具是外卖骑手（有姓名、有技能、能送餐），Function Calling 是派单系统（规定了订单如何下达、骑手如何接单、送达后如何确认）。骑手和派单系统缺一不可，但它们解决的是完全不同层面的两件事：骑手是“能力”，派单系统是“通信规范”。

所以上一章讲的“工具四要素”是从概念层面告诉你一个工具应该包含什么；本章讲的 Function Calling 是从协议层面告诉你这些要素以怎样的标准化格式在大模型和 Agent 之间流转。

两者的协作流程，以“查询北京明天天气”为例：

1. 用户提问：“北京明天天气怎么样？”

2. 大模型分析：需要调用天气 Tool，生成 Function Call 格式的指令。

3. 系统解析指令：调用 `get_weather("北京", "2026-03-21")` 这个 Tool。

4. Tool 执行并返回结果：“北京明天晴，10~20℃”。

5. 大模型将结果整理成自然语言，回复给用户。

## Function Calling 三部分核心结构

接下来，我们以天气查询场景为例，将 Function Calling 完整的三部分结构拆解清楚，每一行都说明其作用。

![](<attachments/什么是 Function Call？-1620207ed0fd1ff12167942d26d4411b.png>)

### 第一部分：工具定义（Tool Definition），给大模型的“工具说明书”

这一步由开发者编写，相当于给大模型一份严格规范的工具说明书。大模型会完全按照这份说明书判断是否需要调用工具及如何调用。

```json
{
  "name": "check_weather",
  "description": "获取指定城市指定日期的天气情况，包括温度区间、晴雨状况、风力风向",
  "parameters": {
    "type": "object",
    "properties": {
      "city": {
        "type": "string",
        "description": "需要查询天气的城市中文名称，示例：北京、上海、广州"
      },
      "date": {
        "type": "string",
        "format": "YYYY-MM-DD",
        "description": "需要查询的日期，格式为年-月-日，示例：2026-03-19，不填默认查询当天"
      }
    },
    "required": ["city"]
  }
}
```

每个字段都有明确作用：

* `name` ：工具的唯一标识，大模型调用时必须与此名字完全一致。

* `description` ：工具功能说明，**是大模型判断“是否要调用这个工具”的核心依据**。描述越精准，大模型做出正确决策的概率越高。

* `parameters` ：告诉大模型该工具需要哪些参数、什么类型、什么格式。大模型会严格按照这里的约束生成参数值。

* `required` ：必填参数清单。如果用户未提供必填信息，大模型会主动询问用户，而不是凭空猜测。

对比之前 System Prompt 中用自然语言描述的“松散约定”，这里的 JSON 格式是严格的机器可读规范。大模型在服务端就会进行格式校验，不合规的参数直接拒绝，从源头杜绝参数乱传的问题。

### 第二部分：AI 调用格式（Function Call），大模型给 Agent 的“标准化执行指令”

当大模型判断需要调用工具时，会严格按照固定格式返回 JSON，不再有任何自由发挥的自然语言。Agent 直接解析这个结构，获取工具名和参数，无需额外猜测处理。

```json
{
  "function_call": {
    "name": "check_weather",
    "parameters": {
      "city": "上海",
      "date": "2026-03-19"
    }
  }
}
```

注意 `function_call` 字段，它是一个固定标识，告诉 Agent：**这不是给用户的回复，而是一条工具调用指令，去执行它**。Agent 看到这个字段，就知道要去工具注册表中查找 `check_weather` 这个函数，并将 `city` 和 `date` 作为参数传入。

你会发现，这里的 `date` 字段大模型自动将“明天”转换成了 `2026-03-19`，完全符合我们在工具定义中约定的 `YYYY-MM-DD` 格式。这就是标准化规范的威力：大模型知道格式要求，会自行转换，不再将模糊的“明天”直接丢给工具。

### 第三部分：工具返回结果（Tool Response），Agent 将结果回传给大模型

Agent 接收到大模型的调用指令后，执行对应的工具，然后将工具的执行结果按规范格式回传给大模型。大模型基于这个结果，决定下一步是继续调用其他工具，还是直接给用户返回最终答案。

```json
{
  "city": "上海",
  "date": "2026-03-19",
  "temperature": "16-22℃",
  "condition": "多云转晴",
  "wind": "3级西北风"
}
```

这一步是整个循环的闭环。大模型并非一次性完成任务，它需要看到工具的执行结果后才能做出下一步决策。例如天气查询成功，它会将结果整理成自然语言回复用户；如果工具报错，它会决定换一种方式或告知用户。

## 对应 Agent 执行流程

将这三部分放回之前讲过的 Agent 执行循环，对应关系就清晰了。

先回顾上一篇文章中的 7 步执行流程：

```json
第 1 步：Agent 将“用户需求 + 工具清单”打包，发给大模型
第 2 步：大模型做出决策，返回调用指令
第 3 步：Agent 执行指令，调用工具函数
第 4 步：Agent 将工具执行结果回传给大模型
第 5 步：大模型根据结果，决定下一步
第 6 步：循环执行，直到任务完成
第 7 步：Agent 将最终结果反馈给用户
```

Function Calling 规范的是其中有“数据交换”的三步：

**第 1 步 → 工具定义（Tool Definition）**

Agent 需要将工具清单传给大模型，这份清单就是用 Function Calling 规定的 JSON 格式编写的。每个工具都有标准化的 name、description、parameters 字段。大模型收到的不是一段随意的文字描述，而是严格规范的结构化数据。

**第 2 步 → AI 调用格式（Function Call）**

大模型做出“调用工具”的决策后，返回给 Agent 的不是一句自然语言（如“你去帮我查一下天气”），而是严格的 JSON 格式指令：`function_call.name` 告诉 Agent 调用哪个工具，`function_call.parameters` 告诉 Agent 传入什么参数。Agent 直接解析，无需猜测。

**第 4 步 → 工具返回结果（Tool Response）**

Agent 执行完工具（第 3 步）后，拿到结果，按规范格式打包回传给大模型。大模型收到结果，才能决定下一步是继续调用工具，还是直接回答用户。

**第 3 步不在 Function Calling 的管辖范围内**，那一步是 Agent 实际执行函数，是真正“干活”的部分，不涉及大模型和 Agent 之间的通信格式。

用一张图将对应关系标出：

![](<attachments/什么是 Function Call？-230b54c325e0db01696d9c5ed1af6a50.png>)

Function Calling 将第 1、2、4 步的数据格式全部标准化。这三步恰好是大模型和 Agent 之间所有的“信息交换点”。有了这套规范，双方使用同一种语言，不再依赖猜测。

1. **解析工具名**：从 `function_call.name` 得到 `"check_weather"`

2. **查找对应函数**：在工具注册表中找到 `check_weather` 对应的实际函数

3. **传入参数执行**：将 `function_call.parameters` 中的 `city` 和 `date` 原样传入函数

4. **拿到结果回传**：函数执行完毕，将返回的天气数据回传给大模型

整个过程干净利落，无需任何猜测和解析，因为 Function Calling 已保证调用指令的格式固定、可预期。Agent 只需按格式拆解、对号入座、执行、回传，即可完成自己在这一轮循环中的全部工作。

## 一张表看懂：System Prompt 传统模式 vs Function Calling 标准化模式

| 对比维度 | System Prompt 传统模式 | Function Calling 标准化模式 |
| ------ | ---------------------- | --------------------------- |
| 工具描述方式 | 自然语言随意写，无统一规范 | 固定 JSON 格式，强制规范 name/description/parameters 必填项 |
| 调用返回格式 | 完全靠 AI 自由发挥，五花八门，无固定结构 | 严格固定 JSON 结构，字段统一，可直接解析 |
| 参数错误率 | 极高，经常出现参数顺序错、格式错、模糊值 | 极低，大模型严格按参数规范生成，格式和必填项有服务端校验 |
| 开发成本 | 极高，需编写大量解析、纠错、重试逻辑 | 极低，直接解析固定格式，无需处理额外兼容问题 |
| 模型兼容性 | 极差，切换模型需重写整套提示词 | 极好，主流大模型通用，一套工具定义可跨模型使用 |

***

## 总结

整理一下本章的核心认知：

* **Function Calling 是什么**：大模型和 Agent 之间的标准化工具调用协议，解决“大模型做出调用决策后，如何精准传递指令”的问题，是整个 Agent 开发的底层基础。

* **为什么需要它**：没有 Function Calling 之前，只能使用自然语言在 System Prompt 中描述工具，大模型的回复格式完全不可控，开发者需编写大量解析和纠错代码；有了 Function Calling，双方都遵循固定的 JSON 规范，彻底告别猜谜。

* **三部分结构**：工具定义（我能用什么）→ AI 调用格式（我要调哪个）→ 工具返回结果（调完得到什么），对应 Agent 执行循环的第 1、2、4 步。

后续章节呼应：

* **RAG**：一种特殊工具，专门解决“大模型看不到你私有数据”的问题，重要到单独一章。

* **MCP**：工具的标准化协议，不用每次都自己编写工具定义，可直接接入现成生态。
