# RAG技术要点汇总

## 模块1：基础概念

### 1. 什么是RAG？为什么需要RAG？

#### LLM 的三大知识缺陷

**① 知识截止**——训练数据有截止日期，昨天发生的事它不知道。例如询问“2026年3月发布的某框架有什么特性”，它要么编造信息，要么回答不知道。

**② 私有数据无法触达**——公司的内部文档、客户数据、业务规则等，LLM 从未见过，直接询问会产生错误回答。

**③ 容易幻觉**——当 LLM 不确定但又想回答时，它会编造看似合理但完全错误的信息。在没有外部知识验证时，这个问题尤为严重。

#### RAG 的核心思路

RAG（Retrieval-Augmented Generation，检索增强生成）的本质是：**在 LLM 生成回答之前，先从外部知识库检索相关信息，将检索结果放入 Prompt，让 LLM 基于事实回答。**

- 没有 RAG：用户问题 → LLM → 回答（可能幻觉）
- 有 RAG：用户问题 → 检索相关知识 → [问题 + 检索结果] → LLM → 回答（基于事实）

**关键理解**：RAG 不是替代 LLM，而是为 LLM 补充外部知识。LLM 负责理解和生成，RAG 负责提供事实依据。

### 2. RAG的完整链路是怎样的？

#### RAG 七步链路

![](/images/AI/2%20RAG/8ca59c40371bbdaf.png)

**Query → 文档处理 → Chunking → Embedding → 检索 → Rerank → 生成**

每一步的关键决策：

| 步骤 | 作用 | 关键决策 |
|------|------|----------|
| 文档处理 | 解析 PDF/Word/Markdown，提取文本 | PDF 表格如何处理？是否需要 OCR？ |
| Chunking | 将长文档切分成小块 | 切分长度？overlap 多少？按语义切还是固定长度？ |
| Embedding | 将文本块转换为向量 | 使用什么模型？维度多少？中文还是英文？ |
| 检索 | 根据用户问题检索最相关的文本块 | 纯向量还是混合检索？Top-K 设多少？ |
| Rerank | 对检索结果重排序 | 使用什么 Rerank 模型？重排后取 Top-N |
| 生成 | 将检索结果与问题一起送入 LLM 生成回答 | Prompt 怎么写？如何约束幻觉？ |

**核心要点**：不应只罗列七个步骤，而应说明每一步的**关键决策点**，例如：为什么选用某种向量数据库而不选另一种，检索延迟要求，为什么 Top-K 设为某个值。

### 3. 传统RAG的三大痛点是什么？

#### 一个例子说明 RAG 的局限

假设有一个公司内部知识库，包含项目文档、技术方案、会议纪要。用户问：“我们公司所有项目的技术栈趋势是什么？”

传统 RAG 将问题转换成向量，在向量库中查找最相似的文本块，找到的是零散片段：“项目 A 用了 Spring Boot”“项目 B 迁移到了 Go”“项目 C 在试 Rust”……然后把这些片段交给 LLM 拼接回答。结果是一堆事实的堆砌，而非真正的“趋势”。因为缺乏全局视角，LLM 拿到的只是碎片，无法拼出全貌。

这不是 RAG 的缺陷，而是**向量检索的本质限制**。

#### 传统 RAG 的三个天花板

**① 碎片化检索——查到的是文本块，不是知识**

传统 RAG 将文档切成 chunk，每个 chunk 独立向量化。检索时获得的是“与问题最相似的文本块”，但许多问题的答案需要跨多个文本块的信息关联。例如“员工A和员工B在哪个项目上有合作”，信息可能分散在三个文档中：文档1提到员工A负责项目 X，文档2提到员工B参与了项目 X，文档3介绍项目 X 的具体内容。传统 RAG 最多能捞取其中一个，难以同时关联三者。

**② 全局问题难以回答——问“整体”只能拼局部**

像“核心技术主题有哪些”“整体技术路线如何演变”这类全局性问题，需要的**整个知识库的理解**，而非几个相似文本块。Rerank 和混合检索提升的是检索精度，但优化的是“找更相似的文本块”，而非“将碎片拼成全貌”。即便将 Top-5 增加到 Top-20，得到的仍是更多碎片。

**③ 跨文档关系断裂——A 与 B 的联系丢失**

“公司A收购了公司B”在文档1中，“公司B与公司C有合作”在文档2中。那么公司A和公司C之间是否存在间接关系？传统 RAG 无法回答——因为每个 chunk 独立 embedding，chunk 之间没有“关系”概念。

#### 这不是调参能解决的问题

混合检索、Rerank、Query 改写等手段都是在优化“找更好的文本块”。但有些问题需要的不是更好的文本块，而是**实体之间的关系**和**全局的结构性理解**。这正是 GraphRAG 要解决的问题。

![](/images/AI/2%20RAG/823575cb1d227b3f.png)

## 模块2：检索策略

### 4. 向量检索的原理与关键词检索的区别，为什么需要混合检索？

#### 向量检索的本质

将文本转换为高维空间中的点，语义相似的文本在该空间中距离相近。检索时找出距离问题向量最近的几个文档向量。

例如：

```
“如何优化数据库查询” → [0.12, -0.34, 0.56, ...]  ← 这些向量在空间中距离很近
“数据库性能调优方法” → [0.11, -0.32, 0.55, ...]
“今天天气不错”       → [-0.45, 0.78, -0.23, ...]  ← 与上面距离远
```

#### 相似度计算

常用**余弦相似度**，计算两个向量的夹角余弦值：

```
cos(A, B) = (A · B) / (|A| × |B|)
```

值域 [-1, 1]，越大越相似。1 表示方向完全相同，0 表示无关，-1 表示方向相反。

**为何不用欧氏距离？** 向量的模长受文本长度影响，长文本的模长大，但语义不一定更相关。余弦相似度仅关注方向，对语义检索更合适。

#### ANN 检索（近似最近邻）

当文档量达到百万级时，逐次计算相似度太慢。ANN 的思路是：**不要求绝对最近，找到足够近的即可，以换速度。**

主流 ANN 算法：

| 算法 | 原理 | 特点 |
|------|------|------|
| HNSW | 多层跳表图，从上层粗搜到下层精搜 | 查询快，内存占用大 |
| IVF | 先聚类，只搜索最近的几个簇 | 可控精度，适合超大规模 |
| PQ（乘积量化） | 压缩向量维度，降低内存 | 节省内存，精度有损 |

**加分点**：能说出 HNSW 的核心参数 `ef_construction`（建图时搜索宽度，越大图质量越高但建图越慢）和 `M`（每个节点的邻居数，越大图越密但内存越大），表明有实际调优经验。

#### 纯向量检索的三个致命问题

**① 精确匹配不足**——用户搜索“RFC 7231”，向量检索可能返回“HTTP 协议规范”这类语义相关但不包含 RFC 7231 的文档。因为依赖语义相似度，而非精确匹配。

**② 专业术语召回差**——“K8s 的 HPA 怎么配置”，向量检索可能找到“Kubernetes 自动扩缩容”，而真正包含 HPA 配置细节的文档可能排位靠后。专业术语的向量表示与口语描述的距离可能很远。

**③ 专有名词遗漏**——产品名、人名、缩写等，向量检索容易丢失。

#### 关键词检索（BM25）

BM25 是 TF-IDF 的改进版，依靠词频统计，精确匹配能力强但对同义词无能为力。适用于专有名词、代码、精确查询。

#### 混合检索 = 向量检索 + 关键词检索

混合检索同时运行两路：

- **向量检索**：捕捉语义相关的文档（如“数据库优化”与“SQL 调优”匹配）
- **关键词检索（BM25）**：精确匹配文档（如“RFC 7231”可以精确命中）

两路结果合并，取长补短。

![](/images/AI/2%20RAG/b15f2ae968dc8fa8.png)

#### 合并策略：RRF（Reciprocal Rank Fusion）

常用合并方法，公式如下：

```
RRF_score(d) = Σ 1 / (k + rank_i(d))
```

`k` 通常设为 60，`rank_i(d)` 是文档 d 在第 i 路检索中的排名。排名越靠前，贡献分数越高。

```python
def rrf_merge(vector_results, bm25_results, k=60):
    scores = {}
    for rank, doc in enumerate(vector_results):
        scores[doc.id] = scores.get(doc.id, 0) + 1 / (k + rank + 1)
    for rank, doc in enumerate(bm25_results):
        scores[doc.id] = scores.get(doc.id, 0) + 1 / (k + rank + 1)
    return sorted(scores.items(), key=lambda x: x[1], reverse=True)
```

**关键理解**：能清晰说明纯向量检索的三个问题、关键词检索的盲区（同义词无效），以及混合检索如何互补，合并策略采用 RRF。向量检索并不“什么都比关键词检索好”，两者是互补关系，正确做法是混合检索，而非二选一。

### 5. 混合检索的权重、Top-K设置及模糊问题处理

**Q：混合检索权重如何设定？向量检索和 BM25 各占多少？**

常见做法有两种：一是手动调权重（如向量 0.7 + BM25 0.3），在验证集上寻找最佳比例；二是使用 RRF 合并，不设固定权重，依赖排名融合，更稳健。生产环境推荐 RRF，因为不同 query 的最佳权重差异大，固定权重不一定优于 RRF。

**Q：Top-K 设多少？过小或过大会带来什么问题？**

设太小（如 K=3）：可能漏掉相关文档，召回不足。设太大（如 K=20）：引入过多无关信息，增加幻觉风险和 Token 消耗。通常 K=5-10 是平衡点。如果使用 Rerank，可先以 K=20 检索，然后 Rerank 取 Top-5。

**Q：用户问题模糊导致检索效果差，应如何处理？**

- **Query 改写**：用 LLM 将模糊问题改写成更具体的检索 query。
- **多路召回**：同时使用原始 query、改写 query、提取关键词分别检索，再合并结果。
- **追问确认**：若问题过于模糊，Agent 可先追问用户以澄清需求。

## 模块3：重排与生成

### 6. Rerank是什么？为什么检索后还需要重排序？

#### 检索和 Rerank 的区别

**检索**是粗筛——从百万文档中快速捞取 Top-20，速度快但精度有限。使用向量相似度或 BM25 打分，这种打分为**近似**，不一定反映真实相关性。

**Rerank** 是精排——对 Top-20 重新计算相关性分数，使用更精确的模型（通常是 Cross-Encoder）逐个打分，将真正最相关的文档排在前面。

#### 为什么检索的打分不够准确？

向量检索使用 Bi-Encoder：问题和文档分别编码成向量，再计算相似度。**问题和文档在编码时互相不知道对方的存在**，因此只能算“大概相关”。

Rerank 使用 Cross-Encoder：将问题和文档拼接在一起送入模型，模型可以同时看到双方内容，进行更精确的相关性判断。**代价是慢**——Cross-Encoder 不能预计算，每个 (问题, 文档) 对都要过一遍模型，因此只能对少量候选进行精排。

![](/images/AI/2%20RAG/df961d0423768c29.png)

#### Rerank 的效果

实际项目中，Rerank 带来的提升明显：

| 指标 | 检索后（无 Rerank） | Rerank 后 |
|------|---------------------|-----------|
| Top-5 召回率 | 71% | 89% |
| Top-3 准确率 | 65% | 84% |

#### 常用 Rerank 模型

| 模型 | 特点 |
|------|------|
| BGE-Reranker (bge-reranker-v2-m3) | 中文效果好，开源免费 |
| Cohere Rerank | API 调用，效果好，英文为主 |
| bce-reranker-base_v1 | 中文场景，轻量级 |

**关键理解**：“检索是粗筛快捞，Rerank 是精排提准。检索使用 Bi-Encoder 快但粗，Rerank 使用 Cross-Encoder 慢但准。先用检索从百万级捞取 Top-20，再用 Rerank 精排取 Top-5，这是生产环境的标配流程。”

### 7. Bi-Encoder和Cross-Encoder的区别

| 特性 | Bi-Encoder | Cross-Encoder |
|------|------------|----------------|
| 编码方式 | 问题和文档独立编码 | 问题和文档拼接后联合编码 |
| 交互程度 | 浅（只在最后计算相似度） | 深（Transformer 每层都互相注意） |
| 计算效率 | 快（文档向量可预计算） | 慢（每次查询都需对所有候选文档实时计算） |
| 精度 | 较低 | 高（State-of-the-art） |
| 适用阶段 | 召回（粗筛） | 重排（精筛） |

**形象比喻**：
- Bi-Encoder 像 HR 初筛简历：只看关键词和学历，快速过滤。
- Cross-Encoder 像技术面：仔细看项目细节，判断真实匹配度。

#### Cross-Encoder 工作原理

输入：`[CLS] 问题文本 [SEP] 文档文本 [SEP]`，经过 Transformer（如 BERT、RoBERTa）编码，取 `[CLS]` 的输出通过一个全连接层得到相关性分数（0~1 或 logits）。

为什么更准？因为每一层 self-attention 可以让问题中的词与文档中的词直接交互，捕捉到例如“否定词”、“条件状语”、“指代消解”等复杂语义关系。例如：
- 问题：“哪些产品**不支持**退货？”
- 文档片段：“产品A**支持**退货。”
  Cross-Encoder 通过“不支持”与“支持”的注意机制判断为不相关；而 Bi-Encoder 可能因为共享“退货”一词给出较高的向量相似度。

## 模块4：幻觉处理

### 8. RAG的幻觉怎么处理？

#### 幻觉的两种类型

**① 内在幻觉**——检索结果中有正确信息，但 LLM 生成的内容与检索结果矛盾。例如检索说“准确率 91%”，LLM 说“准确率 95%”。

**② 外在幻觉**——LLM 生成了检索结果中根本没有的内容。检索只提到 A，LLM 自己编造了 B。

#### 六种幻觉处理策略

**1、Prompt 约束**——在 Prompt 中明确要求“只能基于检索结果回答，检索结果中没有的信息不要编造”。

**2、输出自校验**——LLM 生成回答后，再次使用 LLM 检查：回答的每一条是否都能在检索结果中找到依据？找不到的依据标注为“未验证”。

```
VERIFICATION_PROMPT = """请检查以下回答是否每一条都能在参考资料中找到依据。对于每条声明，标注：✅ 有依据 / ❌ 无依据 / ⚠️ 部分依据
回答：{answer}
参考资料：{context}"""
```

**3、引用标注**——要求 LLM 在回答时标注每条信息的来源 chunk，便于人工核查。

**4、温度调低**——temperature 设为 0.1-0.3，降低 LLM 的随机性，减少“编造”倾向。

**5、检索结果与生成结果的对齐**——生成回答后，将回答与检索结果进行相似度对比，如果回答中存在大段内容与所有检索结果都不相关，很可能产生幻觉。

**6、兜底回答**——当检索结果的相似度均低于阈值时，直接回答“未找到相关信息”，而不是让 LLM 强行编造。

**关键理解**：不应仅说“使用了 Prompt 约束”，而应说明使用了多种策略组合及其效果，例如“Prompt 约束 + 输出自校验 + 温度调低，幻觉率从 30% 降至 12%”。

## 模块5：评估指标

### 9. 如何评估RAG系统的好坏？

从检索和生成两个维度评估。

| 指标 | 计算方式 | 说明 |
|------|----------|------|
| Hit Rate | 召回结果中包含正确答案的比例 | 召回覆盖能力 |
| MRR | 1/(正确答案排名) 的平均值 | 排序质量 |
| NDCG | 考虑多级相关性 | 排序质量更精细 |
| Faithfulness | 生成答案是否与检索片段矛盾 | 幻觉程度 |
| Answer Relevance | 答案是否回答了问题 | 生成质量 |
| Context Relevancy | 检索片段是否与问题相关 | 检索质量 |

**关键理解**：能说明检索侧和生成侧的指标，并知道如何使用 Ragas 等框架自动化评估。

## 模块6：分块策略

### 10. 分块策略怎么选？chunk size和overlap如何调优？

#### 常见分块策略

| 策略 | 做法 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|----------|
| 固定大小分块 | 按固定字符/token数切分 | 简单可控 | 极易切断语义边界 | 通用基线 |
| 段落分块 | 按`\n\n`或自然段落切分 | 保留段落完整性 | 段落长度差异大 | 结构化文档 |
| 句子分块 | 按句号/感叹号切分 | 语义单元最完整 | 可能过于细碎 | 高精度检索 |
| 递归分块 | 先段落，段落超限再按句子 | 兼顾完整与长度 | 实现稍复杂 | 生产环境常用 |
| 语义分块 | 用模型检测主题边界 | 边界精准 | 计算成本高 | 高质量知识库 |

#### chunk大小的权衡

- **太小**：上下文缺失，检索时信息不全；模型可能找不到足够证据。
- **太大**：噪声增加，相似度计算被无关词稀释；可能超过 Embedding 模型输入限制（如 512 tokens）。

**工程经验**：常用范围 256–512 个 token。可设置 **重叠（overlap）** 10%~20%，让相邻 chunk 共享边界信息，避免信息丢失。

#### 不同文档类型的处理策略

| 文档类型 | 处理策略 |
|----------|----------|
| Markdown | 按标题层级切分，保留标题层级信息 |
| PDF | 先解析表格和图片，再按段落切分 |
| 代码 | 按函数/类切分，保留完整代码块 |
| FAQ | 每个问答对作为一个 chunk，不要拆开 |

**关键理解**：能说明 chunk 大小的权衡（大→信息稀释，小→上下文丢失），以及 overlap 的作用。最好能举例说明实际调参经历，如“chunk_size 从 1000 降到 500，召回率提升了 15%”。

## 模块7：工程优化

### 11. RAG系统的端到端延迟怎么优化？

优化链路：使用 vLLM 部署推理服务（减少 LLM 推理延迟）、KV Cache 复用（相似问题不重复计算）、流式输出（用户无需等待全部生成完毕）、Prompt 压缩（减少 Token 数降低延迟）、HNSW 索引优化（向量检索延迟压到 50ms 以下）。

### 12. RAG的Token成本怎么控制？

- Prompt 压缩：裁剪检索结果中的冗余内容。
- 上下文窗口管理：只保留当前问题相关的历史。
- 模型路由：简单问题使用小模型，复杂问题使用大模型。
- 缓存：相同或相似问题的检索结果缓存复用。

### 13. 文档更新了，向量索引怎么更新？

三种策略：全量重建（简单但慢，适合日级更新）、增量更新（只重新 embed 变更的文档，适合实时更新）、双写（新文档同时写入旧索引和新索引，切换时零停机）。

## 模块8：Agentic RAG

### 14. Agentic RAG是什么？和普通RAG有什么区别？

#### 普通 RAG 的局限

普通 RAG 是固定流程：用户问 → 检索一次 → 生成回答。如果第一次检索结果不佳，不会自行纠正，直接硬生成。像一个不会反思的人，说错就错到底。

#### Agentic RAG：让 RAG 自行决定如何检索

Agentic RAG 将 Agent 的规划能力引入 RAG——LLM 自行判断：需要检索哪些数据源？检索结果是否足够？不够则换个角度重新检索。

| 维度 | 普通 RAG | Agentic RAG |
|------|----------|-------------|
| 检索次数 | 固定 1 次 | 动态，LLM 决定 |
| 检索策略 | 固定 pipeline | LLM 自主选择 |
| 结果不满意 | 直接生成 | 换策略重新检索 |
| 复杂问题 | 容易答偏 | 可以拆解子问题分步检索 |
| Token 消耗 | 低 | 高（多次推理） |

![](/images/AI/2%20RAG/6f8b11acef17e7f0.png)

#### Agentic RAG 的工作流程

```
用户问题 → Agent 规划：这个问题需要检索什么？
         → 第一次检索 → 结果不够？
         → Agent 判断：换个 query 再检索
         → 第二次检索 → 结果够了？
         → Agent 判断：够了，生成回答
```

**关键理解**：Agentic RAG 适用于复杂知识问答场景（法律、医疗、金融），简单问答使用普通 RAG 即可，不必过度设计。能够做出此判断，表明具有工程判断力。

## 模块9：GraphRAG与LightRAG

### 15. GraphRAG如何解决全局性问题？

GraphRAG 的核心创新在于**社区摘要的预计算**。

1. 先用 LLM 从文档中抽取实体和关系，构建知识图谱。
2. 使用 Leiden 算法将图谱划分成多个层级的社区（紧密连接的实体群）。
3. 对每个社区，用 LLM 生成一份结构化摘要，描述该社区的关键实体、核心关系、主要主题。
4. 查询时，Global Search 使用 Map-Reduce 方式：Map 阶段遍历所有相关社区的摘要，分批生成中间答案；Reduce 阶段汇总所有中间答案，合成最终回答。

**GraphRAG = 知识图谱 + 社区层级 + 预计算摘要 + Map-Reduce 查询**，四个缺一不可。

**Q：GraphRAG 和知识图谱问答（KGQA）有什么区别？**

KGQA 是直接在已有知识图谱上做问答，图谱是事先人工或半人工构建的。GraphRAG 的图谱是**自动从文本中提取**的，不需要预先建好图谱。此外，GraphRAG 还保留了原始文本块，图谱和文本协同检索，不仅仅依赖图谱。这使得它比纯 KGQA 更鲁棒。

**Q：为什么 GraphRAG 使用 Leiden 而非 Louvain？**

Louvain 存在一个已知问题：可能产生“内部不连通”的社区——社区内的节点并不全连通。Leiden 是 Louvain 的改进版，保证社区内部一定连通。对于知识图谱这种节点连接不均匀的图，该保证很重要。

**Q：传统 RAG 加上知识图谱就是 GraphRAG 吗？**

不完全是。添加一个知识图谱作为辅助检索确实能提升效果，但 GraphRAG 的核心创新不在于“有图谱”，而在于**社区摘要的预计算**。如果仅建一个图谱做实体检索，没有社区层级和预计算摘要，全局性问题还是无法很好解决。

### 16. LightRAG和GraphRAG核心区别是什么？

| 维度 | GraphRAG | LightRAG |
|------|----------|----------|
| 开发者 | 微软研究院 | 港大 HKUDS |
| 知识结构 | 知识图谱 + Leiden 社区层级 | 双层图谱（实体层 + 关系层） |
| 全局理解方式 | 预计算社区摘要 → Map-Reduce | 关系层图谱实时检索 |
| 索引成本 | 高（2-5x 源 token） | 中（比 GraphRAG 少约 40-60%） |
| 索引耗时 | 长（百万文档约 3.8 小时） | 短（同规模约 2.1 小时） |
| 增量更新 | 难（需重建社区结构） | 易（直接向图中添加节点和边） |
| 全局查询质量 | 强（预计算摘要，完整性好） | 中上（实时检索，够用但不如预计算） |
| 本地查询质量 | 强 | 强 |
| 部署复杂度 | 高 | 低 |

### 17. 什么场景选GraphRAG，什么场景选LightRAG？

#### 什么场景选 GraphRAG

- **知识库大且相对稳定**——法律档案、研究论文库、历史文档，建一次图可使用很长时间。
- **全局洞察是刚需**——如“所有案件的判决趋势”“跨论文的药物相互作用模式”，GraphRAG 的预计算摘要优势明显。
- **预算充足**——能够承受 10 倍于传统 RAG 的索引成本。
- **更新频率低**——周更或月更，增量更新的痛点不大。

典型场景：律所的案件分析系统、药企的文献检索平台、情报分析系统。

#### 什么场景选 LightRAG

- **知识库动态更新**——新闻聚合、客服知识库、产品文档，每天都有新内容。
- **成本敏感**——创业团队或中小规模项目，GraphRAG 的索引成本难以承受。
- **快速上线**——希望先运行起来观察效果，不想花费数小时建图。
- **查询类型混合**——既有具体问题又有全局问题，但全局问题不需要极致完整。

典型场景：新闻聚合平台的智能问答、客服知识库、研究者的个人论文库。

### 18. GraphRAG的实体提取准确率不够怎么办？

三个方向：一是优化提取 Prompt，为 LLM 提供领域术语表和实体类型定义；二是后处理过滤，使用规则或二次 LLM 调用清洗低置信度的实体和关系；三是引入 NER 模型做初筛，再用 LLM 进行精细提取。实际项目中，纯靠 LLM 提取的准确率在 70-80%，加上后处理可提升至 85%以上。

## 模块10：系统设计

### 19. 设计一个面向10万用户的RAG知识库系统

从五个维度展开：**数据层**（文档解析→Chunk→Embedding→向量库 + ES 双写）、**检索层**（混合检索 + Rerank，Top-20 检索 + Top-5 精排）、**生成层**（vLLM 部署 + Prompt 模板 + 幻觉约束）、**工程层**（Redis 缓存热点查询、异步处理文档更新、监控检索准确率和幻觉率）、**安全层**（文档权限隔离、Prompt Injection 防御、敏感信息过滤）。

### 20. 设计一个法律文档检索系统，GraphRAG还是LightRAG？

选 GraphRAG。理由：法律文档库规模大但更新频率低（法规变动不频繁），全局性问题多（如“近五年合同纠纷案件的判决趋势”），且预算通常充足。法律场景对答案完整性要求高，GraphRAG 的预计算社区摘要优势明显。

### 21. 设计一个新闻聚合平台的智能问答，选哪个？

选 LightRAG。理由：新闻每分钟都在更新，增量插入是刚需；用户查询既有具体的（如“某事件的最新进展”），也有偏全局的（如“本周科技行业的热点话题”），LightRAG 的四种查询模式均能覆盖；并且新闻平台通常对成本敏感，LightRAG 的索引成本仅为 GraphRAG 的一半左右。

### 22. 如果预算有限但又有全局查询需求，怎么办？

三种思路：一是使用 LightRAG 的 Hybrid 模式，大部分场景够用；二是传统 RAG 加上简单图谱辅助（不添加社区摘要，仅在实体检索时使用图谱），成本可控且效果有所提升；三是仅在核心数据子集上使用 GraphRAG 建图，非核心数据采用传统 RAG，形成混合架构。
