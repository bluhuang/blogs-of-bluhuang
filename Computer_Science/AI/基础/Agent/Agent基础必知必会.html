Agent基础必知必会

Agent基础必知必会

Jun 02, 202619 min read

1 什么是Agent

Agent（智能体） 是以 LLM 为核心推理引擎，结合规划、记忆和工具使用能力，它能够自主地感知环境、制定计划、使用工具、执行行动，并且根据执行结果来动态调整后续策略。

换句话说，LLM 在 Agent 架构中不再只是一个”回答问题的机器”，而是充当了整个系统的”大脑”，负责理解任务、推理决策、协调各种外部能力来完成复杂的目标。

一句话总结：Agent = LLM + 工具 + 循环。

Agent vs 普通 LLM 调用的区别：

维度普通 LLM 调用Agent
交互模式”一问一答”，一次输入一次输出”感知-思考-行动”循环，多步迭代
决策能力被动响应，无自主决策主动规划，根据结果动态调整
行动能力只能生成文本能调用工具、执行操作、影响外部世界
记忆能力仅靠上下文窗口短期记忆 + 长期记忆（向量库等）
复杂任务需人工拆解自主拆解子任务并协调执行

2 Agent的核心组件

一个完整的 Agent 系统通常由四个核心模块构成：

  • LLM（大脑）
  • 规划模块（Planning）
  • 记忆模块（Memory）
  • 工具使用（Tools）

这四个模块各司其职又紧密协作，共同支撑了 Agent 的自主决策和任务执行能力。

2.1 LLM（大脑）

中枢系统，负责理解用户意图、逻辑推理、生成行动计划、解读工具返回结果。Agent 的智能水平上限取决于底层 LLM 的能力。

2.2 规划模块（Planning）

规划能力是 Agent 区别于简单 LLM 应用的关键标志。当 Agent 接收到一个复杂任务时，它不会试图一步到位地解决，而是会把任务分解成多个可执行的子步骤，然后按照逻辑顺序逐步执行。

  • 任务拆解：将复杂目标拆解为可执行的子任务（如 Chain-of-Thought、Tree-of-Thoughts）。
  • 反思与修正：Agent 对过去的行为进行修改，实现自我迭代。

目前主流的规划策略主要有两类：

  1. 无反馈的规划：

    • 比如 ReAct（Reasoning + Acting）框架，它让 LLM 在每一步先进行推理思考（Thought），然后决定执行一个动作（Action），接着观察动作的结果（Observation），再进入下一轮的思考-行动循环。ReAct 的优点是实现简单、思路清晰，是目前最广泛使用的 Agent 推理框架。
    • 还有一种是先一次性生成完整的执行计划，然后逐步执行，类似于 Plan-and-Execute 模式。

  2. 带反馈的规划：Agent 在执行过程中会根据中间结果进行反思和调整。比如 Reflexion 框架，Agent 在执行失败后会对失败原因进行自我反思，然后修正策略重新执行。这种方式更接近人类解决问题的真实过程——我们不会一条路走到黑，而是会根据反馈不断调整方案。

2.3 记忆系统（Memory）

Agent记忆分类

Agent 的记忆通常分为两种：

  • 短期记忆：利用上下文窗口记录当前会话流，即当前对话窗口中的内容。
  • 长期记忆：通过外部数据库（向量数据库、知识图谱等）实现海量知识的检索与长效存储。

  1. 短期记忆（Short-term Memory）：本质上就是当前对话的上下文（Context），包括用户的历史消息、Agent 之前的推理过程和工具调用结果等。它存在于 LLM 的上下文窗口中，让 Agent 在一次任务执行过程中能够保持连贯性。但短期记忆受限于 LLM 的上下文窗口长度，当对话太长或推理步骤太多时，早期的信息就会被截断丢失。工程上常见的解决方案包括对话摘要（Summarization）、滑动窗口、以及基于关键信息提取的压缩策略。

  2. 长期记忆（Long-term Memory）：持久化存储的外部知识，通常通过向量数据库来实现。Agent 可以把重要的历史交互、学到的经验、用户偏好等信息存入向量数据库，在需要时通过语义检索（也就是 RAG 的方式）来调取相关记忆。这使得 Agent 能够跨会话地积累和利用知识，表现出”越用越聪明”的特性。

向量数据库 vs Graph RAG（知识图谱）

在 Agent 记忆中，两种主流架构各有适用场景：

  • 向量数据库：将记忆表示为高维空间中的稠密数学向量。通过语义相似度搜索，适合广泛语义匹配和非结构化数据检索。Agent 主要用此方法存储对话历史、相关文档、API 文档等。
  • Graph RAG：将实体和关系表示为图结构。当需要多跳关系、事实准确性和复杂层次结构时表现更优。

选择建议：

  • 需要模糊匹配、处理非结构化文本 → 向量数据库
  • 需要精确关系推理、多跳查询 → Graph RAG
  • 实际生产系统常采用混合架构，结合两者优势

2.4 工具使用（Tools/Function calling）

通过 API 调用外部工具（搜索、代码解释器、SQL 执行等），使 Agent 具备影响外部世界的能力。

工具使用能力是 Agent 能够真正”做事”的关键。LLM 本身只能生成文本，它不能查数据库、不能调 API、不能操作文件系统。但通过工具使用机制，Agent 可以将 LLM 的推理能力与外部世界的执行能力连接起来。

在技术实现上，工具使用主要依赖 LLM 的 Function Calling 能力。我们预先定义好一组工具的描述（包括工具名称、功能说明、参数 schema），放在 System Prompt 或者通过 Function Calling 接口传给 LLM。当 LLM 在推理过程中判断需要使用某个工具时，它会生成一个结构化的函数调用请求（包含工具名和参数），Agent 框架负责解析这个请求并实际执行对应的函数，然后把执行结果返回给 LLM 继续推理。

工具的类型可以非常丰富，常见的包括：搜索引擎（联网检索信息）、数据库查询、API 调用（天气、日历、邮件等）、代码执行器（让 Agent 能写代码并运行）、文件读写操作等。工具的丰富程度直接决定了 Agent 能做的事情的边界——工具越多越强，Agent 的能力就越强。

2.5 工作流程：感知 → 思考 → 行动 → 观察（ReAct 循环）

智能体的工作流程本质上是一个闭环：

  • Step 1 感知：接收用户输入并结合环境反馈。
  • Step 2 规划：LLM 根据记忆和目标，制定下一步行动计划。
  • Step 3 行动：选择并调用工具，执行具体操作。
  • Step 4 观察：获取工具返回的结果，更新状态，并判断是否达成目标。如果未达成，则返回 Step 2 循环。

2.6 Agent与RAG的关系

传统的 RAG 系统遵循线性流程：用户问题 → 检索文档 → 拼接上下文 → 生成答案。这种被动查询的方式，缺少真正的多步决策与行动能力。

Agentic RAG（智能体式 RAG） 在此基础上更进一步：将具备规划、工具使用、记忆管理和迭代检索能力的智能体嵌入 RAG 系统中，使 RAG 系统从静态查询处理器转变为动态行动者。

Agentic RAG 的核心特点

  • 采用 ReAct Agent 架构：系统性地决定是否需要检索信息，仅在需要额外上下文时才激活检索流程。
  • 动态决策：不是每次都检索，而是智能判断何时检索、检索什么。
  • 工具使用：Agent 可以调用多个检索工具，整合不同来源的信息。

2.7 RAG 如何与 Agent 结合

Agent 可以以多种方式增强 RAG：

  1. 检索决策：Agent 自主决定是否需要检索、检索什么内容。
  2. 多轮检索：根据检索结果决定是否进行第二轮检索。
  3. 多源整合：同时从向量库、知识图谱、API 等多个来源检索并整合信息。
  4. 结果验证：Agent 可以验证检索结果的可靠性，必要时重新检索。
  5. 长期记忆：将过往检索经验存入长期记忆，提升未来检索效率。

2.8 Agent设计思路

2.8.1 设计原则

根据相关实践，Agent 设计的核心原则是 “保持简单”：能用单次 LLM 调用解决的问题，就不要用 Agent；能用预定义工作流解决的，就不要让 Agent 自主决策。

2.8.2 主流设计模式

模式适用场景特点
Single Agent（单智能体）任务边界清晰简单直接，易于调试
ReAct Agent需要推理+行动的复杂任务思考-行动-观察循环，最广泛应用
Reflexion（自主反射）代码生成、学术写作引入”裁判”进行多轮质检
Multi-Agent（多智能体协作）需要分工协作的复杂系统主从架构、水平协作等

3 多 Agent 协作

3.1 为什么需要多个Agent

单个 Agent 能力有限。现实场景中，让一个 Agent 同时精通前端、后端、数据库，很容易顾此失彼，上下文越来越长，后面写前端时把前面后端的细节忘了。多 Agent 协作的核心思想：主 Agent 当项目经理，把子任务委派给拥有不同专业能力的 SubAgent，各管一块，互不干扰。

3.2 分工模式

模式说明示例
纵向协作（主从）上下级汇报制，主管 Agent 拆解任务，执行 Agent 完成主节点作为全局协调者，从节点专注执行
水平协作（角色分工）角色分工制，不同 Agent 负责不同领域会计师 Agent + 测试员 Agent 协同工作

3.3 通信与协作框架

在多 Agent 系统中，通信与协作框架是确保各智能体能够高效、可靠地协同工作的基础。下面从协议、消息模式、状态同步和冲突解决四个维度深入说明。

3.3.1 核心协议：A2A（Agent-to-Agent）

A2A 是目前业界主推的多智能体通信协议，旨在标准化不同框架、不同语言实现的 Agent 之间的互操作方式。

A2A 协议的核心要素：

要素说明
能力发现Agent 启动时广播自身能力（工具列表、领域专长），其他 Agent 可动态查询
任务委托主 Agent 将子任务以标准化格式（JSON）发送给从 Agent，包含任务描述、输入参数、预期输出格式
状态追踪每个任务都有唯一 ID，主 Agent 可随时查询子任务执行状态（pending/running/completed/failed）
异步响应从 Agent 执行完任务后，通过回调或消息队列返回结果，支持长时间运行的任务
安全认证基于 API Key 或 OAuth 的身份验证，确保只有授权 Agent 能通信

3.3.2 通信模式

根据任务需求，Agent 之间可以采用不同的通信模式：

模式特点适用场景示例
请求-响应（同步）主 Agent 发送任务后阻塞等待结果简单、快速的任务主 Agent 让数学 Agent 计算 2+3，立即等待结果
异步消息队列主 Agent 发布任务到队列，从 Agent 拉取执行，结果通过另一队列返回耗时任务、高并发多个 Agent 并发处理大量日志分析任务
广播/订阅主 Agent 广播任务，所有订阅该类型的从 Agent 同时执行并返回结果需要多方意见的场景多个代码审查 Agent 同时审查同一段代码，主 Agent 汇总意见
点对点协商两个 Agent 直接对话，通过多轮交互达成一致需要谈判、协调的任务预算 Agent 和资源 Agent 协商如何分配有限的计算资源

3.3.3 状态同步与一致性

多 Agent 协作中，状态同步是难点，尤其当多个 Agent 需要共享同一份数据或执行顺序敏感的任务时。

常用策略：

  • 中心化状态存储：使用 Redis 或数据库作为共享状态中心，所有 Agent 读写同一个状态。简单可靠，但中心节点可能成为瓶颈。
  • 分布式事务：采用两阶段提交（2PC）或 Saga 模式，确保多个 Agent 的操作要么全部成功，要么全部回滚。适用于财务等强一致性场景。
  • 最终一致性 + 补偿：允许中间状态不一致，但最终通过补偿操作（如撤销、冲正）达到一致。适合大多数非严格事务场景，如订票失败后自动退款。

3.3.4 冲突解决机制

当多个 Agent 同时对同一资源（如数据库记录、文件）进行写操作时，可能产生冲突。常见解决策略：

策略说明适用场景
乐观锁每个 Agent 操作前先读取版本号，写时检查版本号是否改变。若改变则重试。冲突概率低的场景
悲观锁（Leader 选举）同一时刻只有一个 Agent 可以修改资源，其他 Agent 排队等待。高冲突、高一致性场景
冲突仲裁器引入一个独立的仲裁 Agent，当冲突发生时，由它根据规则决定哪个操作生效。业务规则复杂，需要人工干预的场景
时间戳优先比较操作的时间戳，最早的操作生效，后来的被拒绝。简单幂等操作

3.3.5 工程实践建议

在实际实现多 Agent 系统时，建议遵循以下原则：

  1. 避免过度通信：每个额外通信都会增加延迟和失败风险。能在一个 Agent 内完成的，不要拆成多个。
  2. 设计幂等操作：Agent 可能因网络重试而多次执行同一任务，操作应设计为幂等（多次执行结果相同）。
  3. 设置超时与熔断：为每个子任务设置合理的超时时间，超时后主 Agent 应降级或人工介入。
  4. 可观测性：记录每个 Agent 的输入、输出、执行时间、失败原因，便于调试和优化。
  5. 先单体，后微服务：初期将所有 Agent 运行在同一个进程中，简化调试；当系统稳定且需要扩展时，再拆分为独立服务。
